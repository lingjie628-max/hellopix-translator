# 0.1.20 Mac arm64 候选 — 「快、准、稳」真机验收手册（第一阶段）

> 本轮**只做一件事**：把已经真机验证通过的 **0.1.19 原生输入发送链**，接上经过测试的
> **60ms 自适应沉降**，并补上**真机分段埋点**，让「按下发送 → 实际触发发送」的
> P50/P95 可以直接从日志里算出来。
>
> 上游结论（连续四版真机）：
>
> | 版本 | 发送写入方式 | 真机结果 |
> |---|---|---|
> | 0.1.16 / 0.1.17 / 0.1.18 | 页面内改 DOM（`execCommand`/`textContent`） | `BODY_MISMATCH` |
> | **0.1.19** | **Chromium 原生输入**（主进程发起、`isTrusted:true`） | **发送成功、编辑器认可** ✅ |
> | **0.1.20（本轮）** | 同上，**只把固定 500ms 观察窗换成 60ms 确认即走**，并加真机埋点 | 待测 |
>
> 本机是 Apple 芯片 → 用 **arm64** 包。**本轮不上架、不建 RELEASE、不动套餐/代理/群组/子账号/Windows。**

## 本轮改了什么 / 没改什么

**改的（只有两处）**
1. **沉降窗**：固定 `500ms` → **“确认即走”**（下限 **60ms**，连续 3 次回读一致即提前放行；上限 400ms 兜底）。
   实测客户端净开销从 **~508ms P50** 降到 **~71ms P50（−86%）**，13/13 安全用例无回归。
2. **真机埋点**：新增 `SEND_PERF`（同一条发送动作上 7 段耗时），以及 翻译中 / 正在发送 / 已发送 的**四态状态**。

**一个字都没动的（本轮硬约束）**
- 原生输入写入链路（`native-composer.js`：`selectAll+delete` → `insertText`）；
- `BODY_MISMATCH` 判定、**fail-closed**、草稿保护（`canSafelyRestore` / `COMPOSER_STILL_SOURCE`）、
  幂等键（`requestId`）、失败重试（`RETRY_TRANSLATE_*`）。

## 1. 验收 A — 正常发送（GPT 与 DeepSeek 各一轮）

**准备**：一个能正常翻译的聊天；实例通道分别设为 **GPT** 和 **DeepSeek** 各测一轮。

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| A1 | 输入一句**中文**，按回车 | 被拦下；输入框短暂显示译文；**对方收到的是英文译文** |
| A2 | 看对方收到几条、内容 | **只有一条**，且是**译文**（不是原文、不是占位符） |
| A3 | 分别用 GPT / DeepSeek 各重复一次 | 两种通道都能正常发出，行为一致 |

预期 trace 顺序（必须先出现 `[PIX_TRACE] SEND_PERF` 才说明装的是本轮包）：

```
SEND_CAPTURED → NATIVE_SEND_BLOCKED → SOURCE_SNAPSHOTTED
  → TRANSLATE_STARTED → TRANSLATE_SUCCEEDED
  → COMPOSER_STILL_SOURCE            （写入前确认框里还是本次原文）
  → NATIVE_INPUT_BEGIN → COMPOSER_CLEARED → NATIVE_TEXT_INSERTED
  → LEXICAL_SETTLED  (ms≈60~71, stable:true, canonicalEqual:true)   ← 本轮优化点
  → INPUT_REPLACED → FINAL_TEXT_VALIDATED(ok:true)
  → PROGRAMMATIC_SEND_BEGIN → PROGRAMMATIC_SEND_DONE
  → SEND_PERF
```

## 2. 验收 B — 失败重试

1. 制造一次翻译失败：**断网**，或后台把该通道停用。
2. 发一条中文 → 应出现**可操作提示**（含真实错误码），**绝不直发原文**。
3. 恢复网络/通道 → 点「**重试翻译**」。

**通过标准**：重试**真正进入发送链并成功发出最终译文**；`RETRY_TRANSLATE_RESULT` 收口为成功；
**不再出现 `BODY_MISMATCH`**。

## 4. 验收 D — 翻译状态及时关闭

| 阶段 | 输入框上方提示 | 通过标准 |
|---|---|---|
| 翻译请求中 | `正在翻译…（翻译期间不会发送任何内容）` | 出现及时 |
| 开始发送 | `正在发送…` | 与 `PROGRAMMATIC_SEND_BEGIN` 同步出现 |
| 发送完成 | `已发送` | 出现后 **约 800ms 自动消失**，**不残留**、不遮挡后续输入 |

> 失败时走 `failed` 态：显示错误码 + 「重试翻译 / 发送原文」两个按钮，不静默。

## 5. 验收 E — 性能：按下发送 → 实际触发发送 的 P50 / P95

**采样协议（每通道 20 条，文本用虚构内容）**

```bash
bash rc020-collect.sh before
# —— GPT 轮：实例通道设 GPT，正常发 20 条不同长度的虚构中文 ——
bash rc020-collect.sh after-gpt
# —— DeepSeek 轮：实例通道设 DeepSeek，正常发 20 条 ——
bash rc020-collect.sh after-deepseek
# 失败重试 / 连续发送 各采一次
bash rc020-collect.sh after-retry
bash rc020-collect.sh after-consecutive
```

脚本会在 `after-gpt` / `after-deepseek` 时**当场算出各阶段 P50/P95**，关键两行：

- **★按下发送→触发发送** ← 需求点：用户点发送到我们真正触发发送（含翻译 API 等待）
- **★总计(点击→提示关闭)** ← 用户实际感知等待

**区分 WhatsApp 最终送达确认时间（重要）**

客户端埋点覆盖到「我们触发发送 → 状态提示关闭」为止。**WhatsApp 自身的“已送达”确认
（✓✓）不由客户端埋点覆盖**（它取决于对方是否在线），需**手工秒表**测：

| 量 | 怎么来 | 说明 |
|---|---|---|
| ① 按下发送 → 我们触发发送 | 脚本 `★按下发送→触发发送` | 真机埋点，精确 |
| ② 我们触发发送 → 提示关闭 | 脚本 `send + uiClose` 段 | 真机埋点，精确 |
| ③ 按下发送 → WhatsApp 显示已送达(✓✓) | **手工秒表** | 至少记 10 条 |
| ④ ≈ WhatsApp 侧送达耗时 | **③ − ① − ②** | 隔离出 WhatsApp 自己的时间 |

填写（脚本跑完直接抄）：

| 指标(ms) | GPT P50 | GPT P95 | DeepSeek P50 | DeepSeek P95 |
|---|---|---|---|---|
| 按下发送→触发发送 | | | | |
| 总计(点击→提示关闭) | | | | |
| WhatsApp 送达(手工,可选) | | | | |

## 6. 安全底线（任一违反即 FAIL）

- ❌ 对方收到**中文原文**（原文抢发）；
- ❌ 对方收到 `[正在翻译中...]` 之类**占位符**；
- ❌ 同一条**发两次** / **重复扣费**；
- ❌ 又出现 `BODY_MISMATCH`（首发送或重试）；
- ❌ 等翻译期间你打了下一条 → 这条**没发**，但**你的新草稿被覆盖/丢失**；
- ❌ 翻译失败时**静默降级发原文**。

对应「正确行为」（不算 bug）：`COMPOSER_LEFT_AS_IS` = 你已改草稿 → 主动放弃覆盖、一个字节都不动。
