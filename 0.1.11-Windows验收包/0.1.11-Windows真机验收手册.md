## 0. 为什么有这一版（0.1.10 → 0.1.11）

0.1.10 **已经上架并被用户安装**，它带着三个 P0：

1. **群聊「翻译通道 = 手动」失效** → 进群聊后消息仍自动翻译、**余额被扣**。
2. **消息提取把 UI 文案当正文** → 时间（`3:25 PM`）、已读图标（`wds-ic-read`）、
   `View group`、链接预览卡片的标题与元数据都被送去翻译 —— **按这些字符多扣费**。
3. **译中占位符 `[正在翻译中...]` 被真实发送** → 真实发出去过「哈喽你好[正在翻译中...]」。

另外修好了代理的实例级串联：**新建应用不再继承上一次的代理**；
每个窗口一套独立代理（详见 §3.7 / §3.8）。

> 这三个 P0 是**计费与内容**缺陷，不是体验问题。所以本版的重点验收项就是它们，
> 而不是新功能。

### 3.2 ★核心★ 群聊手动模式必须 0 自动翻译、0 扣费

这一条是**本版第一优先**。0.1.10 在 WhatsApp 群聊里会无视「手动」设置直接翻。

1. 打开设置，把 **「群组翻译」设为「手动」**
2. **记录当前余额**（截图）
3. 进入一个**真实的 WhatsApp 群聊**，**不要点任何「译」按钮**
4. **停在群里 2~3 分钟**，手动**往上滚动**加载更早的历史消息（这一步很关键）
5. 观察：
   - [ ] 消息**没有**自动出现译文
   - [ ] 每条可翻的消息上只有「**译**」按钮
   - [ ] 余额**没有变化**（与第 2 步一致）
6. 然后**点其中一条的「译」按钮**
   - [ ] 只有**这一条**出现译文
   - [ ] 余额只扣了**这一条**的字符数
7. **让群里别人发一条**新消息（或你从手机发一条进群）
   - [ ] 手动模式下，**新消息也不自动翻**，仍然只有「译」按钮
8. 再把设置切成 **「群组翻译 = 自动」**，等新消息到达
   - [ ] 新消息**自动**出译文（这是预期行为）
   - [ ] **历史消息没有被补翻**（余额不因历史消息变化）

**截图**：① 手动模式下的群聊（只有「译」按钮、无译文）
② 点一条后的译文 + 余额变化 ③ 自动模式下新消息自动翻

**记录**：每步余额、点了几条、群里新消息几条

> 我会在服务端核对：`translate_logs.trigger = 'auto_receive'` 的条数。
> **手动模式下它必须是 0**；历史消息也不该产生 `auto_receive`。

### 3.3 ★核心★ 翻译内容里不得出现时间 / 已读 / UI 文案

0.1.10 会把 `3:25 PM`、`wds-ic-read`、`View group`、预览卡片标题一起送去翻译。

在**一对一会话**里收/发下面几类消息，每条都用划词或「译」翻一次：

| 消息类型 | 要求 |
| --- | --- |
| 纯文字 | 译文只对应文字本身 |
| **纯链接** | **不消耗字符**（不应调翻译接口） |
| **文字 + 链接** | 只翻文字；**链接原样保留、不被翻译** |
| **群邀请链接 / 网页预览卡片** | 卡片的站点名、标题、`Open` 按钮**都不进译文** |
| **回复引用的消息** | 只翻**本条**，被引用的旧消息**不翻** |
| 图片 / 文件 + 说明文字 | 只翻说明文字；文件名、`Download` 按钮**不进译文** |
| 只有 emoji | 无可翻内容（不产生请求） |

- [ ] 以上每一条都没有把时间戳 / 已读图标 / UI 文案带进译文
- [ ] 纯链接消息**没有扣费**
- [ ] 「文字 + 链接」的**链接完整保留**（没被模型翻译或吞掉）

**截图**：至少 3 类（含「文字 + 链接」和「预览卡片」）

### 3.7 ★核心★ 新建应用必须默认「直连」

0.1.10 的缺陷：给某个实例配过代理后，**再点「新增应用」会自动带出上一次的代理**。

1. 给**已有的**某个应用（例如 WhatsApp）配一个代理，确认「检测」出口 IP = **B**
2. 回到主页点 **「新增应用」**，随便选一个（例如 Telegram）
3. **先不要填任何东西**，直接看新增表单里的**代理区域**：

- [ ] 代理类型是「**直连**」（不是上次那种 socks5/http）
- [ ] 主机 / 端口 / 账号 / 密码**全部为空**
- [ ] 直接创建后点「检测」→ 出口 IP = **本机直连 IP**（不是 B）

**截图**：新增表单的代理区域（全空）+ 新实例的检测结果

### 3.8 ★核心★ 每个窗口的代理完全独立

1. **新建** 实例 A（例如 WhatsApp）→ 配**代理 X** → 检测记下 **IP_A**
2. **不要关 A**。**新建** 实例 B（例如 WhatsApp 再一个实例）→ 配**代理 Y** → 记下 **IP_B**
3. **再新建** 实例 C → **不配代理** → 记下 **IP_C**

- [ ] **IP_A ≠ IP_B**（两个实例各走各的代理）
- [ ] **IP_C = 本机直连 IP**，且与 IP_A / IP_B 都不同
- [ ] A 的账号密码**没有**出现在 B 的代理设置里

然后：

4. **改 A** 的代理（换个端口或密码）→ 点「检测」
   - [ ] A 的出口**立即变化**（不重启）
   - [ ] B 的出口**完全不变**
5. **删 A** 的代理 → 点「检测」
   - [ ] A **恢复直连**
   - [ ] **B 仍然走 Y**
6. **完全退出** Hello Pix，再打开
   - [ ] 实例 A 恢复它**自己的最终**代理
   - [ ] 实例 B 恢复 **Y**
   - [ ] 实例 C **仍是直连**
7. 重启后再**新增** 实例 D
   - [ ] D 默认**直连**（不出现 X 或 Y）

**截图**：三步的检测结果（A/B/C 各一张）+ 改 A 后 A/B 各一张 + 重启后各一张

## 6. 已知的未完成项（先告诉你，免得白等）

- **⑪ 三线路真实出口（IP_A ≠ IP_B）在开发侧没跑成**：你给的那条公网代理
  `165.254.160.22:54565` 被**供应商侧拒绝** —— TCP 可达、握手正常，但对每个目标
  都返回 SOCKS5 reply `0x02`（connection not allowed by ruleset，典型的 IP 白名单限制）。
  我用纯 `curl`（完全绕开产品代码）复现了同一错误，确认**不是客户端缺陷**。
  所以 §3.8 需要你在**能用的代理**上跑；若你给的两条代理都在白名单里，我这边也能补跑。
- **macOS 安装包为 ad-hoc 签名、未公证**（无 Developer ID 证书），
  用户首次打开需进「系统设置 → 隐私与安全性 → 仍要打开」。与历史版本一致。
