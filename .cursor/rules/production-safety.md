# 铁律：不得影响线上正常运行

**这条规则优先级最高。与任何"更快交付""顺手优化""先上线再说"冲突时，一律让路。**

## 事实背景

本项目的生产环境是**单一实例、真实收费、有实时业务流量**的系统：

- 服务器 `207.57.167.121:30071`，生产目录 `/opt/hello-pix`，服务 `hello-pix`（systemd）
- 官网 `pixfanyi.com` 是**对外门面**，挂了就是生意挂了
- 商户端、超管后台、桌面客户端更新通道**共用同一个后端的同一份 dist**
- 链上收款监听 `hello-pix-recharge-watcher` 每分钟扫一次，**停了就可能漏单**

## 已经发生过的两次事故（务必引以为戒）

1. **用 `--mode production` 构建**
   绕开了 `vue.config.js` 主配置里的 `pages`，导致官网入口 `landing.html` 没被生成 →
   `pixfanyi.com` 直接 **500「服务器内部错误」**。

2. **只上传部分文件就重建**
   上传了新版 `Landing.vue`（依赖 `--w-space-*` / `--w-radius-*`），
   却没同步新版 `theme.css` → CSS 变量未定义、整条属性失效 →
   **官网 UI 彻底散架**（圆角变 0、间距塌陷、按钮挤扁）。
   同时还把一个文件的 `<style>` 块整个覆盖没了。

**两次的共同点：改动前没有做依赖审计，改完没有验证就宣布完成。**

## 强制执行流程

### 一、改动前必须做

1. **先读生产真实文件**，不要拿本地代码的假设去改线上。
   本地与生产长期存在漂移，`src/` 尤其严重。
2. **依赖审计**：要替换的文件，先查它依赖什么（CSS 变量、组件、import），
   确认生产是否具备。缺一样都可能让页面散架。
3. **子集校验**：覆盖前必须证明「生产文件没有本地缺少的内容」。
   标准做法：
   ```bash
   comm -23 <(grep -o -- '--w-[a-z0-9-]*:' 生产文件 | sort -u) \
            <(grep -o -- '--w-[a-z0-9-]*:' 本地文件 | sort -u)
   ```
   结果**必须为空**。不为空就不能整体覆盖，只能精准增量修改。
4. **备份**到 `/opt/hello-pix/.backup-<日期>-<时间>/`，**每一个**要动的文件都备份，
   包括看起来"顺手覆盖一下没关系"的那个。

### 二、构建必须用

```bash
node node_modules/@vue/cli-service/bin/vue-cli-service.js build
```

**禁止加 `--mode production`** —— 它会绕开主配置。`NODE_ENV=production`
由 systemd 的 `EnvironmentFile` 提供，不需要手动指定。

### 三、改动后必须验证，验证通过才能说"完成"

最低验证清单：

```bash
# 1. 产物齐全
ls dist/*.html dist/js/ dist/css/

# 2. 每个静态资源都真能取到（不能只看首页 200）
for f in dist/js/*.js dist/css/*.css; do
  printf '%-40s %s\n' "/${f#dist/}" \
    "$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000/${f#dist/})"
done

# 3. 关键样式/变量真的进了包
for k in w-space-8 w-radius-pill white-space:nowrap pointer:coarse; do
  printf '%-24s %s\n' "$k" "$(cat dist/css/*.css | grep -c -- "$k")"
done

# 4. 服务活着
systemctl is-active hello-pix
journalctl -u hello-pix -n 20 --no-pager | grep -i error
```

**任何一项不为 200 / 为 0 / 报错，就不算完，必须当场回滚。**

### 四、回滚优先于排查

一旦线上出现异常，**先回滚到已知良好状态**，再慢慢查原因。
不要把生产当作调试环境，不要"再试一次说不定就好了"。

## 禁止事项

- ❌ 拿生产当试验场，边改边看效果
- ❌ 覆盖文件前不备份
- ❌ 只改一半依赖就重建
- ❌ 构建后不验证静态资源可达性
- ❌ 改了后端代码不确认服务能否启动就重启
- ❌ 在没有回滚方案的情况下动数据库迁移
- ❌ 在未经用户确认时执行会中断服务的操作

## 与用户沟通的要求

- 说明改动前，要讲清**风险点和回滚方式**
- 宣布完成时，必须附上**实际验证结果**（状态码、检查项），不能只说"改好了"
- 如果自己造成了事故，**直接承认是哪个动作导致的**，不要模糊成"环境问题"
