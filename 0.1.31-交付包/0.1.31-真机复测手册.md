# Hello Pix 0.1.31 真机复测手册

> **本版的重点是「开满不闪退」。** 请在**报障那台机器**上走完第 1～3 步。

---

## 0. 装之前先记一笔（很重要）

先在**出问题的那台机器**上打开**旧版** Hello Pix，反复开 / 关实例十几轮，
然后主界面 → 设置 → 「客户端日志」导出（或跑 `rc030-collect.sh`）。

> 为什么要这样：旧版在这个场景下会**闪退**，而闪退往往来不及写日志。
> 先把日志捞出来，能帮我们确认"崩之前最后发生了什么"。
>
> 另外记一下：**旧版你能开到第几个才崩？**（用户报的是 18 个左右）
> 这个数字对判断很有用 —— 它是你机器上句柄上限的直接体现。

---

## 1. 【核心】能开到很多个（不再卡在 20）

**步骤**：反复点「+」，尽量多开 —— 目标是 **30 个以上**。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 能否开到 30+ | 能 | 到 20 个就被拦（说明装的是旧版） |
| 什么时候才提示 | 内存接近满时 | 一早就提示 |

> 本版已取消固定上限。只要内存够，就应该**一直能开**。

---

## 2. 【核心】内存超过 90% 时的提示

**准备**：先开一堆实例，再开几个吃内存的程序（浏览器多开标签、视频等），
把内存推到 **90% 以上**。

**步骤**：再点一次「+」。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 表现 | 弹**原生提示框**，标题「**运行内存不足**」 | 闪退 / 卡死 |
| 内容 | 说明内存已用多少 + 让用户关窗口或关其他程序 | 只说"开不了"，不说原因 |
| 应用状态 | **照常可用**，已开的窗口继续工作 | 进程消失 |
| 日志 | `resource` 一行 warn，含内存 MB 与已用百分比 | 无记录 |

> 关键：**提示的是"内存"，不是"窗口数"** —— 引导用户去关别的程序，而不只是关窗口。

---

## 3. 【核心】关掉一些后必须能继续开

**步骤**：
1. 承接上一步（已弹过内存提示）。
2. 关掉几个实例，或关掉一些别的吃内存的程序，让内存降下来。
3. 再点「+」。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 能否开出新实例 | **能** | 仍然被拒（说明水位没降或判据卡死） |

> 这条验证"水位是**动态**的，不是一次性锁死"。

## 5. 收集日志发回

在**出问题的那台机器**上跑：

```bash
# Windows 用 Git Bash / WSL
bash rc030-collect.sh
```

或手动：主界面 → 设置 → 客户端日志 → 导出。连同以下信息一起发：

1. Windows / macOS 版本（Windows 跑 `winver`）
2. **旧版能开到第几个才崩**（第 0 步记下的数字）
3. 新版开到第几个开始提示
4. 复测时**卡在第几步**、屏幕上是什么
5. 特别要「**崩/提示那一瞬间**」附近的日志时间段

真 Electron 实测的关键记录：

| 断言 | 实测值 |
|---|---|
| 每个实例消耗的句柄数 | **19.2 个**（预算按 26 算） |
| 20 个实例累计句柄 | 39 → **520** |
| 连续 30 次"拒绝"判断消耗的句柄 | **0**（87 → 87） |
| 拒绝之后能否正常建窗口 | **能** |
| 反复开关 30 次的永久泄漏 | 242 个句柄（≈8.1/次，Electron 33 原生行为） |

> 最后一条说明了为什么必须有**显式的窗口数上限**：
> 光看句柄水位会因历史泄漏而误判，而数字上限是确定的、可解释的。
