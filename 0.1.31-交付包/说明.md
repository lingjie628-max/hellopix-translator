# Hello Pix 0.1.31 交付说明

> **一句话**：把"固定最多 20 个窗口"改成**按系统内存水位动态判断** —— 内存充足就能一直开，
> 超过 90% 才提示。
>
> 顺带**推翻了 0.1.30 的归因**：那个"18 个就崩"不是句柄耗尽，是内存。

---

## 一、用户的问题

> 窗口并发上限能不能拉到 60-80？
> 会根据系统运行内存自己判断，系统运行内存超过 90% 后，再开新窗口会提示运行内存上限，无法继续打开。

这个方案比"设个固定数字"好，因为它**自适应机器大小**。于是先重新压测，确认可行。

---

## 二、压测结果 —— 推翻了 0.1.30 的归因

用真 Electron + 真 `WebContentsView` + 真独立分区，页面按 WhatsApp Web 规模造
（每个 8000 条消息 DOM + 大数组 + WebSocket + 定时器）：

| 实例数 | 句柄 | 主进程 RSS | **整机内存** |
|---|---|---|---|
| 48 个 | 1178 | 122MB | 6443MB |
| **80 个** | **1886** | **150MB** | **8163MB** |

### 结论一：**句柄根本不是瓶颈**

```
Electron 实际 ulimit -n = 1048575   (启动时把软限制抬到了硬限制)
80 个实例只用了 1886 个句柄          → 离上限差 3 个数量级
```

0.1.30 看到的"`launchd maxfiles=256`"是个**假象** —— Electron 会自己抬高。
我当时把"每实例 24 个句柄"当成主瓶颈，**判错了**。

### 结论二：**内存才是真瓶颈，且与机器大小强相关**

```
80 个实例 ≈ 8GB
  → 在 8GB 机器上是灾难（开始换页、卡死）
  → 在 32GB 机器上毫无压力
```

所以**固定一个"最多 N 个"必然是错的**：同一个数字在 8GB 上太冒险、在 32GB 上太保守。

**80 个在技术上完全可行** —— 你的需求合理，只是判据选错了。

---

## 三、改动

### 3.1 主判据：系统内存水位

```
已用 >= 90%            → 拒绝
开完这一个就 > 90%      → 也拒绝（预判，不只看当前快照）
```

**为什么要"预判"**：水位是**当前**快照。若现在 89%、直接放行，新实例一起来就
立刻越过 90% —— 那等于没保护。所以按每实例约 **120MB** 预留来推算
（实测均值约 102MB，取保守值）。

### 3.2 固定窗口数上限：默认取消

`MAX_TABS_PER_WINDOW = 0`（不限）。留着这个常量是为了"想强行限死"的场景，
设成 >0 即生效。

### 3.3 句柄判断：降级为最后一道网

`handleLimit` 由 1024 放宽到 65536。几乎不会触发，留着是因为万一某个平台上
句柄真的被别的程序耗光，这里能拦住，而不是让用户看到闪退。

### 3.4 ★ 内存口径的坑（踩过并修掉）

**这是本版最容易翻车的地方。**

macOS 的 `os.freemem()` **只返回 `Pages free`**，把可被内核立即回收的
`inactive`（文件缓存等）**全部算成"已用"**。实测本机：

```
os.freemem()      → 0.12GB   → 算出"已用 98.6%"   ← 错得离谱
vm_stat 口径      → 6.41GB   → 算出"已用 80%"     ← 可用
系统权威口径       → 可用 41%
```

**如果直接用 `os.freemem()`，这台 8GB 机器在空闲时也会被告知"内存不足"，
比不判断还糟。**

现改为按平台取"真正可用"：

| 平台 | 口径 |
|---|---|
| macOS | `vm_stat` 的 `free + inactive + speculative + purgeable` |
| Linux | `/proc/meminfo` 的 `MemAvailable`（内核算好的，最准） |
| 其他 | `os.freemem()`（接受其保守性） |

> 为什么 `inactive` 要算可用：那是内核**留着做缓存**的内存，不是被占用了。
> 本机 inactive 有约 1.5GB，不算进去就会把"可用 41%"报成"已用 98%"。
>
> 我们的口径比系统略保守（80% vs 系统说可用 41%），这正合适 ——
> 留安全边际，又不至于误拒。

### 3.5 提示文案按原因自适应

| 原因 | 对话框标题 | 引导用户去做什么 |
|---|---|---|
| 内存不足 | **运行内存不足** | 关窗口或关其他程序 |
| 窗口数达顶 | 无法再开新窗口 | 关掉几个窗口 |

### 真 Electron 验收

```
electron scripts/verify-tab-budget-electron.js
→ 12 / 12 通过
```

关键实测：

| 断言 | 实测 |
|---|---|
| 本机真实水位 | 8GB · **已用 83%** · 来源 `vm_stat` |
| ★ **未误用 `os.freemem`** | 我们 83% vs 朴素口径 **98%** |
| 内存 95% → 拒绝并点名"内存" | ✔ |

## 五、真机复测

### 1. 【核心】能开到很多个

1. 反复点「+」，尽量多开（30 个以上）。
2. 只要内存没吃满，就应该**一直能开**。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 能否开到 30+ | 能 | 到 20 个就被拦（说明是旧版） |
| 什么时候才提示 | 内存接近满时 | 一早就提示 |

### 2. 【核心】内存超 90% 时的提示

**准备**：先开一堆实例 + 再开几个别的吃内存的程序（浏览器多开标签、视频等），
把内存推到 90% 以上。

1. 再点「+」。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 表现 | 弹**原生提示框**，标题「**运行内存不足**」 | 闪退 / 卡死 |
| 内容 | 说明内存已用多少 + 让用户关窗口或关其他程序 | 只说"开不了" |
| 关掉内存后 | 又能继续开 | —— |
| 日志 | `resource` 一行 warn，含内存 MB 与百分比 | 无记录 |

### 3. 关掉一些后能继续开

关掉几个实例（或关掉别的程序）让内存降下来，再点「+」→ 应能正常开。
