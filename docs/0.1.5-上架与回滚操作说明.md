> ⚠️ **0.1.5 曾经上过一个不含后台运行的旧构建**（SHA `de11f83f…`），
> 已被本次构建**原地覆盖**（版本号没变）。如果**确定**在这之前已经有人下过
> 那份旧 0.1.5（同一版本号，客户端不会再次提示更新），需要发 **0.1.6** 才能让他们拿到

> 不要再重新构建后覆盖 —— 那样就没法证明用户装的就是验收过的那一个。

## 0.1.5 的内容

在 0.1.3 基础上修复 / 新增四项：

1. **多开分区隔离** —— 每个进程启动时独占一个槽位（`instance-slot.js`），
   分区名带 `s2-` / `s3-` 前缀，两个窗口不再共用 session、不再互相踢下线。
   槽位 1 沿用旧命名，单实例用户升级后**不丢登录态**。
2. **消息归档** —— 把每条消息的真实正文与时间上报，`messages` 表不再为空。
3. **窗口最小尺寸 900 × 560**（原 1160 × 680，小屏上占掉半屏还多）。
4. **后台运行**（新增）—— 关窗收进托盘、翻译继续跑；托盘左键唤回、右键退出；
   「系统操作」菜单或托盘菜单可关闭该行为。托盘创建失败时自动退化为「关闭即退出」，
   避免出现没有任何入口能唤回的僵尸进程。

## 上架（已执行，留档）

```sql
-- 1) 下架旧版
UPDATE client_releases SET enabled = false, updated_at = now()
 WHERE release_group = 'windows' AND version IN ('0.1.3', '0.1.4');

-- 2) 上架 0.1.5（记录已存在，改 enabled）
UPDATE client_releases SET enabled = true, updated_at = now()
 WHERE release_group = 'windows' AND version = '0.1.5';
```

**为什么必须同时下架旧版**：更新接口按「该系统的已上架记录」里挑一条返回。
如果两条同为 `arch = x64`、得分相同，选中哪条取决于排序 —— 会出现
**有的用户收到新版、有的收不到**的随机现象。

上架后自测：

```bash
# 应当返回 0.1.5
curl -s "https://lindufyht.com/apis/client/update?os=win32&arch=x64"
```

> 注意这条接口要登录才能调（返回 401 说明没带会话，不是故障）。

## 回滚

```sql
UPDATE client_releases SET enabled = false, updated_at = now() WHERE version = '0.1.5';
UPDATE client_releases SET enabled = true,  updated_at = now() WHERE version = '0.1.3';
```

回滚只是让**更新提示**回到 0.1.3，**不会**把已经装成 0.1.5 的用户变回去。
真要让用户退回，得再发一个版本号更大的包（客户端只认更大的版本号）。

下载文件不要删：`HelloPix-Setup-0.1.3.exe` 仍在服务器上，回滚时它得在。

## 关于 32 位 Windows

**不要加 ia32 构建。** 两个理由：

- **Windows 11 没有 32 位版本** —— 微软从未发布，只支持 64 位系统。
- **Electron 正在移除 32 位 Windows 支持** —— 官方 Breaking Changes 写明：
  v44.0.0 起只发布 64 位平台，v43 系列 2027 年 1 月 EOL 后 `win32-ia32` 彻底停止支持。

加了就是给未来埋一个必须回滚的坑。现在 Windows 只发 `x64`。

**顺带说明**：`HelloPix-Setup-*.exe` 用工具看会显示 **32 位（i386）**，
这是 **NSIS 安装器外壳**，不是程序。真正的程序本体
（`win-unpacked/Hello Pix.exe`）是 **x86-64**。
NSIS 的 stub 按设计就是 32 位，能在两种 Windows 上跑，再按目标机位数释放载荷。
**这不是问题，不要去"修"。**

## 更新匹配的架构规则

原实现用模糊文本打分：

```js
if ((arch === 'x64' || arch === 'ia32') && /intel|64|32/i.test(String(row.arch)))
```

`x64` 与 `ia32` 得分相同、正则同时匹配 "64" 和 "32"，
于是 **32 位客户端会被推送 64 位安装包** —— 用户下载 80MB、卸载旧版、
打开才发现打不开。而且它只是加分项、不参与筛选，架构完全不匹配的记录
只要系统对上就能被选中。

现在架构是**筛选条件**（`server/lib/release-arch.js`）：

| 发布记录的 arch 写法 | 含义 |
| --- | --- |
| `x64` / `64位` / `Intel 芯片` / `x86_64` / `amd64` | 只发给 x64 客户端 |
| `arm64` / `Apple 芯片` / `aarch64` / `M1` | 只发给 arm64 客户端 |
| `ia32` / `32位` / `x86` | 只发给 32 位客户端 |
| **留空** | 不限架构，任何客户端都能用 |
| 填了但认不出来（如笔误 `x46`） | **不匹配任何客户端**（保守：宁可这次不发更新） |

后台「客户端版本」的架构字段已从自由文本改成**下拉选择**，杜绝写法漂移。
