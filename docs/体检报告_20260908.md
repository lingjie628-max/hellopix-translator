## 一、项目定性

**Hello Pix = "聊天软件多开壳 + 翻译计费后端 + 真实协议 Telegram 客户端" 三件套。**

| 模块 | 技术栈 | 用途 |
|------|--------|------|
| `server/` | Express 5 + PostgreSQL 16 + Redis 7 | 主后端：账号/子账号/套餐/字符计费/翻译链路/审计 |
| `desktop/` | Electron 33 + WebContentsView | 多开壳：WhatsApp/Telegram/Line/IG… 网页多开 + 气泡译文注入 |
| `standalone/telegram` | Electron + GramJS | 真实 MTProto 协议电报客户端（独立应用版） |
| `standalone/telegram-win` | Electron 启动器 + tdesktop 魔改 | Windows 魔改电报气泡译文方案（stage: 待 Windows 编译） |
| `src/` | Vue 2 + Element UI | 商户/后台 Web 前端 |

**一句话：给做海外聊天群控的人卖"字符翻译套餐"，账号多开网页版聊天软件，消息实时自动翻译，按字符扣费。**

## 三、亮点（值得学的地方）

### 1. 扣费账本设计：教科书级
翻译计费不是"先扣费再翻译"，而是：

```
幂等键校验 → Redis 分布式锁(NX/PX) → 短事务[锁行+预扣+建reservation]
→ 事务外调翻译通道 → 幂等事务[成功=commit计费 / 同文=退款 / 失败=退款]
→ 超时 reservation 由 reconciliation 定时用 FOR UPDATE SKIP LOCKED 补偿退款
```

- 数据库层 `adjustChars` 带 `WHERE char_balance+$2>=0` 非负约束，负余额在 SQL 层就被堵死
- schema 里 `translation_reservations` 用 `UNIQUE(user_id, idempotency_key)` + `requestHash` 双重防重放，同键不同请求直接 409
- 缓存命中**仍然计费**（防刷）但缓存按 `main|sub+账号ID` 租户隔离，不跨账号
- 所有金额列带 CHECK 约束，`original_amount - discount_amount = paid_amount` 是库级不变量

### 2. fail-closed 原则贯彻到底
- 未迁移模块统一返回 `503 NOT_MIGRATED`，绝不用 Mock 顶替收费
- 真实翻译通道 `wired=false` 时扣费前就拒绝（`ENGINE_NOT_CONFIGURED`），不存在"演示结果收费"
- 生产启动门禁：缺 `DATABASE_URL`/`REDIS_URL`、用占位密码、远程库不开 TLS、开 demo 开关 → **全部拒绝启动**
- `register`/`forgot`/`emailCode`/支付写接口全部 stub 关闭

### 3. Electron 纵深防御很规范
- 主窗口 CSP `connect-src 'none'`，导航全禁，`setWindowOpenHandler` deny
- guest 远程页面 preload 不 `exposeInMainWorld`（无页面级 IPC 桥），翻译功能只在**受信任 tab**（域名白名单+URL 实时校验）内可用
- API 线路/下载地址统一过 `validateApiUrl`：禁私网/禁凭据/禁 dev 下非 loopback http
- SSH 隧道 spawn 用参数数组传 host/user（无 shell 拼接注入），host 有字符白名单校验
- 密码落盘用 `safeStorage` 加密 + `safe:v1:` 前缀；会话 cookie 只留内存

### 4. 认证链路完整
scrypt 密码哈希（防 GPU 爆破）、`__Host-` 前缀 cookie（防子域投毒）、HttpOnly + Secure、CSRF token 绑定会话类型、双维限流（IP+账号）、登录成败都写 `login_logs`、设备绑定/解绑/改密即撤销全部会话。

### 5. 测试质量
`desktop-security.test.js` 直接断言"guest-inject 不含 exposeInMainWorld、main.js 不含 executeJavaScript"，把安全边界固化成回归测试——这种写法非常专业。

## 四、发现的问题

> 修复状态：✅ 已修复（2026-09-08）/ 🟡 部分处理 / 🔴 待上线前处理

### 🔴 P1-1：桌面端翻译链路与正式 API 契约不匹配 —— ✅ 已修复 2026-09-08

**位置**：`desktop/main.js` translate:run handler（~1716 行）、`standalone/telegram/lib/pix-api.js`

**问题**：正式后端 `core.translate()` 强制要求 `Idempotency-Key`（header 或 form 的 `requestId`），缺失直接 400 `IDEMPOTENCY_KEY_REQUIRED`。但：

- `desktop/main.js` 的 `translate:run` 调 `api('/translate/run', { form: { text, from, to, engine } })` —— **没带幂等键，form 里也没有 requestId**
- `standalone/telegram` 的 `pix:translate` → `pix.request('/translate/run', ...)` —— **同样没带**

目前这个 bug 被 fail-closed 挡住了（通道 `wired=false` 会先返回 503 `ENGINE_NOT_CONFIGURED`），所以没爆。但一旦接上真实翻译厂商把 `wired` 置 true，**桌面端和独立电报端的翻译会立刻全部 400**——需要让调用方带上幂等键或请求侧生成 requestId（如 `desktop:{deviceId}:{counter}`）。

对比参考：`standalone/telegram-win/tdesktop-fork/hello_pix_translate_provider.cpp` 里是正确带了 `Idempotency-Key` 的，说明是桌面端漏了，不是服务端设计错。

---

### 🟡 P2-1：Windows 魔改包残留官方原版 exe —— ✅ 已处理：`.stage/` 入 .gitignore

**位置**：`standalone/telegram-win/.stage/HelloPix-Telegram/`

**问题**：`.stage` 里躺着完整官方 Telegram Desktop 程序目录（`Telegram.exe` 位置）。`使用说明.txt` 自己写了"当前安装包里仍是官方原版电报，气泡还不会自动出译文"。这是个**中间交付物**，但它：
1. 占用仓库体积（几十上百 MB 二进制）
2. 容易在发布时被误当成"成品"发出去 → 用户装了以为有译文实际没有

**建议**：加 `.gitignore` 排除 `.stage/`，发布脚本只从正式产物目录打包。

---

### 🟡 P2-2：翻译缓存"命中仍计费"且缓存时间过长 —— ✅ 已缓解：幂等键修复天然覆盖

> 补记：桌面端/独立端修复（P1-1）后，同设备同文本同参数的重复翻译会命中服务端幂等去重，
> 直接返回首次结果、不再二次扣费。多端同步重复渲染/tdesktop 撤回重发场景不再产生重复计费。
> Redis 翻译缓存 24h TTL 保留，仅用于省厂商回源成本。

**位置**：`server/services/core-service.js` translate（cache 命中路径）、`server/stores/translation-cache.js`（TTL 默认 24h）

**问题**：文档说"缓存命中仍创建 reservation 并计费"是**有意设计**（防刷）。但从产品角度，同一账号同一文本 24 小时内重复翻译每次全价计费，用户体感会很差——尤其 tdesktop 魔改版里"撤回消息重发""多端同步重复渲染"很容易触发同文再次翻译，用户会以为是 bug 导致多扣。

**建议**：给一个更短的缓存 TTL（如 10 分钟）用于防抖，或者加"24h 内同文重复翻译 X 次后免费"之类梯度；至少对 tdesktop 的重复渲染场景要保证幂等键天然去重。

## 六、结论与优先级建议

**结论：内部使用/开发阶段可以接受；收费上线前的硬性待办清单：**

1. 🔴 真实翻译通道 `wired=true` 前，**必须先修桌面端/独立端缺幂等键**的问题，否则上线即断（P1-1）
2. 🔴 支付验签、SMTP 找回、导出对象存储按 docs 计划完成后才能撤生产门禁（当前保持 fail-closed 是正确姿势）
3. 🟡 清理 `.stage/` 中间产物、`all_src.txt`；建 git 基线
4. 🟡 真实翻译厂商接入后要做"同文重复计费"的线上观察，评估缓存/幂等策略是否要调

**没有发现可利用的高危漏洞。** 当前最强的攻击面其实是：a) 翻译通道接入瞬间的幂等键断裂；b) tdesktop 魔改包分发过程中的供应链可信问题。这两个都属于"上线动作"而不是"代码缺陷"。
