# Hello Pix 电报独立版（Windows）验收步骤

这份文档存在的理由：这条链路上有**三段静默失败**——魔改电报的 Provider 按设计
"失败就不写译文、不弹错、不崩电报"；启动器只在登录那一层报错；服务端失败也只回一个
HTTP 状态码。三者叠加的结果是：**气泡不出译文，从外面看和"编译没成功"完全一样。**
所以验收不能只看"电报能不能打开"，必须逐项验到链路每一段。

---

## 一、前置条件（不满足的话后面全部白测）

| 条件 | 怎么确认 |
|------|----------|
| 后台在跑且是持久化后端 | `curl http://127.0.0.1:3000/health` → `"backend":"persistent"` |
| 至少一个翻译通道**已接通** | 后台「翻译通道」页：填好厂商凭据并设为使用中。库里可直接查：`SELECT id,wired FROM engines WHERE wired;` |
| 该通道在目标账号的套餐里 | `deepseek` 目前只挂在 `pro` 套餐；`basic`/`advanced` 套餐里一个已接通的通道都没有 |
| 账号字符余额足够 | 侧栏「用户信息」看字符数；余额不足时服务端返回 409，气泡保持原文 |
| 拿到云编译产出的魔改 `Telegram.exe` | CI 的 `Telegram-exe` artifact。**必须是配了真实 `TDESKTOP_API_ID`/`TDESKTOP_API_HASH` 的那一轮**，测试凭据编出来的包用户一登录就报内部错误 |

## 二、出包

**出包前先验补丁锚点**（不用 Windows，几十秒）：

```bash
./scripts/dryrun-tdesktop-patch.sh          # 默认 v7.2.8
./scripts/dryrun-tdesktop-patch.sh v7.2.9   # 升版本时探锚点
```

它只拉 4 个真实文件搭最小夹具，跑完注入并把 diff 打出来。7/7 命中且二次运行
全部 `skip already patched` 才算过。**升 tdesktop 版本后必须重跑**：锚点是硬编码
字符串匹配，上游挪一行缩进就可能失配，而失配的后果是 `apply.py` 静默跳过、
编出一个没有 Hello Pix 钩子的官方原版——现象和"编译失败"完全一样。

出包（推荐一条命令，自动取最近一次**成功**的产物并校验包内 exe 与下载的一致）：

```bash
./scripts/fetch-and-assemble-telegram.sh          # 取最近一次成功的运行
./scripts/fetch-and-assemble-telegram.sh <run-id> # 指定某个 run
```

手工路径（需要自己确认没拿错 exe）：

```bash
# 1. 从 CI 下载 artifact（Actions → 对应 run → Artifacts → Telegram-exe）
# 2. 组装（产物落到 ~/Desktop/HelloPix-Telegram-Windows.zip）
cd standalone/telegram-win
./assemble-from-build.sh /path/to/Telegram.exe
```

组装脚本会把 `Telegram.exe` 放到 `HelloPix-Telegram/Telegram/` 下，
并把启动器的 `main.js` / `preload.js` / `lib/` / `renderer/` 一起打进去。

**确认包里装的是魔改版而不是官方原版**（这一步别省，混错包就是白测一轮）：

```bash
shasum -a256 /path/to/Telegram.exe
unzip -p ~/Desktop/HelloPix-Telegram-Windows.zip HelloPix-Telegram/Telegram/Telegram.exe | shasum -a256
# 两个哈希必须一致
```

> 注：`assemble-windows.sh` 拉的是**官方原版**电报，用于对照测试，不含气泡译文。

## 三、自动验收（不需要 Windows，Mac 上就能跑）

这一步把"桥接文件 → 后端 `/apis/translate/run`"整段在本地跑通，把静默失败变成断言：

```bash
./scripts/dev-backend.sh                      # 起本机后台（持久化后端）
node scripts/verify-telegram-bridge-e2e.js    # 端到端验收
```

脚本会临时建一个 pro 套餐账号（并**故意**把 `active_engine_id` 设成没接通的
`youdao`，复现真实库里 `demo` 账号的状态），然后：

1. 用 client 模式登录，拿 cookie（和启动器走同一个接口、同一条设备绑定路径）
2. 拉 `/apis/translate/engines`，用**启动器真正在跑的那份** `resolveEngine()`
   （`standalone/telegram-win/lib/engines.js`，脚本直接 `require` 它，不抄一份）
3. 打三种请求：死通道必须失败、已接通通道必须真出译文、同一条消息重复请求不重复扣费
4. **换成启动器真实数据通路再走一遍**：用真的 `lib/pix-api.js` 登录、真的
   `lib/bridge.js` 写 `hello-pix-bridge.json`，然后**完全照 C++ `ReadBridge()`
   的取值方式**（所有 cookie 拼成 Cookie 头、名字含 csrf 的那个当 X-CSRF-Token）
   从文件里读出来发请求
5. 删掉临时账号及日志

2026-09-13 实测结果 **16/16 通过**，其中关键几项：

```
✅ 启动器 resolveEngine 绕开了死通道 youdao     挑中 deepseek
✅ 死通道 youdao 被服务端挡下                   HTTP 503 ENGINE_NOT_CONFIGURED
✅ 已接通通道 deepseek 真的翻出了译文            translation="早上好，会议九点开始。"
✅ 重复请求同一条消息不重复扣费                  余额 99959 -> 99959
✅ 启动器自己的 pix-api 客户端能登录             （cookie jar / CSRF 头由它维护）
✅ 桥接文件落盘正确                             hello-pix-bridge.json, apiBase 无尾斜杠
✅ 桥接文件里带上了 deviceId 与 CSRF cookie      cookies=[pix_user, pix_csrf]
✅ 照 C++ 的方式从桥接文件取值发请求，真能翻出译文
```

第二项就是"气泡静默不出译文"的实测复现；第四项说明 tdesktop 重渲染重复请求同一条
消息不会二次扣费（幂等键生效）；最后一项是**除真机之外能拿到的最强证据** ——
它证明桥接文件的文件名、字段、cookie 拼法与 C++ 侧读法完全对得上。

> 最后一项会真的调用厂商接口，产生极少量费用。

## 四、Windows 真机验收清单

解压后双击 `HelloPixTelegram.exe`，服务器地址填后台的实际地址（本机开发是
`http://127.0.0.1:3000`，注意不是文档旧版写的 8080）。

| # | 操作 | 预期 | 失败时先查 |
|---|------|------|-----------|
| 1 | 登录 Hello Pix 账号 | 进入侧栏，自动打开电报 | 账号已绑其他设备会报"账号已绑定其他设备"（后台 `/admin/users/unbind` 可解绑） |
| 2 | 打开「翻译设置」 | 通道下拉里**只有一个已接通的通道** | 下拉为空或显示提示语 → 后台没接通任何通道 |
| 3 | 点「翻译」按钮粘一段英文 | 显式显示 `[译文] …` | 这里报错说明 apiBase/cookie/余额有问题，**先修这里再看气泡** |
| 4 | 收一条英文私聊 | 同一气泡内：原文 + 下一行 `[译文] …` | 见下方排查表 |
| 5 | 群里收英文消息 | 同上（「群翻译」开着时） | 关掉「群翻译」应恢复只显示原文 |
| 6 | 关掉「接收翻译」再收消息 | 不出译文 | 改设置后桥接文件会被重写；已打开的电报需要重开才生效 |
| 7 | 自己发一条英文 | 「发送翻译」开着时也出译文 | 官方逻辑默认只翻别人发的消息，补丁放开了这条短路 |
| 8 | 打开「程序多开」再开一份 | 新窗口独立数据目录、独立桥接文件 | 两个实例的 `tdata/<id>/hello-pix-bridge.json` 应各自存在 |
| 9 | 把余额耗到不足 | 气泡保持原文，**电报不崩** | 服务端返回 409 `INSUFFICIENT_CHARS` |
| 10 | 断网后收消息 | 气泡保持原文，不崩；恢复网络后新消息正常 | 这是预期行为，Provider 不重试不报错 |

## 五、静默失败排查表

气泡不出译文时，按这个顺序排除（每一步都能把"没效果"变成"明确原因"）：

| 现象 | 原因 | 确认方式 |
|------|------|----------|
| 侧栏「翻译」按钮也报错 | 后台不可达 / cookie 过期 / 余额不足 | 报错文案会直接说明 |
| 侧栏「翻译」正常，但气泡没译文 | 桥接文件里的通道没接通 | 打开 `%APPDATA%\Hello Pix Telegram\tdata\main\hello-pix-bridge.json` 看 `engine` 字段；再到后台确认该通道 `wired=true` |
| 同上 | 桥接文件没被写到电报真正的工作目录 | 确认电报是用启动器打开的（启动器会传 `-workdir` 并先写桥接文件）；手工双击 `Telegram.exe` 不会读桥接 |
| 同上 | 电报是官方原版，没读桥接文件 | 按第二节的 SHA256 对比确认 |
| 只有部分消息有译文 | 官方翻译管线本来就过滤：纯 emoji、service 消息、过短文本 | 属预期；群/自己发的由三个开关控制 |
| 译文和原文一样 | 服务端判定"翻译后没变化"会退款且不写译文 | 属预期，不扣费 |
| 换设置后没立刻生效 | 桥接文件只在登录/保存设置/打开电报时重写 | 重开一次电报窗口 |

**关键排查入口**：`%APPDATA%\Hello Pix Telegram\tdata\main\hello-pix-bridge.json`
（多开实例把 `main` 换成对应实例 id）。

## 六、当前已知边界

- 发送翻译是"显示层"译文，不改动实际发出的消息内容。
- 群发、群组采集、提取群成员不在范围内（产品已排除）。
- 一个 Hello Pix 账号同时只能绑一台设备（client 模式登录会绑定 `deviceId`）。
- 桥接文件里的 cookie 来自登录时刻；会话过期后需要重新登录才会重写。
