# 更新签名 · 对接文本

> 照着这份搬，不用回头翻代码。每一步都给了「粘什么」「粘到哪」「怎么验」。

---

## 0. 先把概念对齐（30 秒）

| 名词 | 是什么 | 谁持有 |
|---|---|---|
| **私钥** `update-signing.key` | 签清单用的，泄露 = 攻击者能给所有用户推任意包 | 只放构建机 / 服务器环境变量 |
| **公钥** | 验签用的，写死在客户端 app.asar 里 | 任何人都能看，看到也没用 |
| **manifest** | 一份字段固定的清单 + Ed25519 签名 | `/client/update` 现签现发 |
| **sha256** | 安装包的哈希，落在 `client_releases.sha256` | 发布脚本从真实文件算出 |

签名原文（**字段顺序即契约，两端必须完全一致**）：

```
appId \n version \n url \n sha256 \n channel \n minVersion
```

## 1. 客户端侧要搬的文件

把下面 3 个文件原样放进 `desktop/src/update/`：

```
desktop/src/update/signature.js        ← 签名原文 + Ed25519 验签 + 版本比较
desktop/src/update/verify-release.js   ← 判定 hardened / legacy / rejected
desktop/src/update/trusted-keys.js     ← 内置公钥（先留占位符）
```

依赖关系：`verify-release.js` → `signature.js` + `trusted-keys.js`。
**零第三方依赖**，只用 Node 内置 `crypto`，Electron 33 直接能跑。

### 1.1 导出清单

```js
// signature.js
{
  MANIFEST_FIELDS,   // ['appId','version','url','sha256','channel','minVersion']
  manifestPayload,   // (manifest) => Buffer         签名原文
  parsePublicKey,    // (pemOrBase64) => KeyObject    强制校验必须是 ed25519
  verifySignature,   // (payload, sigB64, [keys]) => true | throw
  compareVersions    // (a, b) => 1 | 0 | -1
}

// verify-release.js
{
  extractManifest,   // (data) => manifest | null
  validateManifest,  // (manifest, opts) => release | throw
  resolveRelease     // (data, opts) => { status, remote, url, sha256, reason }
}

// trusted-keys.js
{
  PUBLIC_KEYS,       // 过滤掉占位符后的公钥数组
  configured         // boolean，构建时是否已注入公钥
}
```

### 1.2 `resolveRelease(data, options)` 就是主入口

```js
const result = resolveRelease(serverResponse, {
  appId: 'com.hellopix.desktop',  // 必须匹配 manifest.appId
  currentVersion: '1.2.1',        // 用来拒绝降级
  channel: 'stable',              // 必须匹配 manifest.channel
  publicKeys: PUBLIC_KEYS,        // 不给就只用内置的
  allowLegacy: false,             // true = 服务端没清单时降级到白名单模式
  logger: (level, channel, msg) => {}  // 可选，level 是 'warn' / 'error'
})
```

返回：

```js
{
  status: 'hardened' | 'legacy' | 'rejected',
  remote: '1.3.0',   // 远端版本。★ 三种状态都可能有值 ★
  url:    'https://...',  // rejected 时恒为空串
  sha256: 'abc123...',    // hardened 才有；legacy / rejected 是空串
  reason: ''              // 不可用时的人类可读原因
}
```

> **`remote` 在 `rejected` 时也有值，这是故意的。**
> 渲染层拿 `remote > local` 判断「有没有新版」，拿空 `url` 判断「能不能下」。
> 把 `remote` 清零会让界面显示「当前已是最新版本」—— 但用户手上确实不是，
> 等于在骗他，而且骗得没有任何痕迹。
> 正确显示是「**已检测到新版本，但暂时不可下载**」。

## 2. 客户端接入点：`app:checkUpdate`

如果你的项目还没有这个 IPC，直接抄下面这段；已经有了就对照改。

```js
const { resolveRelease } = require('../update/verify-release')
const { configured: SIGNING_CONFIGURED } = require('../update/trusted-keys')

function registerAppIpc (deps) {
  const { reg, actions, env } = deps

  // 默认严格：没公钥 = 拿不到更新，而不是「谁都能推更新」
  const allowLegacy = process.env.PIX_ALLOW_UNSIGNED_UPDATE === '1'
  const state = { warnedMissingKey: false }

  reg.handle('app:checkUpdate', async () => {
    const local = env.APP_VERSION
    try {
      const data = await actions.api('/client/update?os=' + process.platform + '&arch=' + process.arch)

      if (!SIGNING_CONFIGURED && !allowLegacy && !state.warnedMissingKey) {
        state.warnedMissingKey = true
        if (actions.log) actions.log('error', 'update', '客户端未内置更新公钥，所有更新将被拒绝（构建时忘记注入？）')
      }

      const resolved = resolveRelease(data, {
        appId: 'com.hellopix.desktop',
        currentVersion: local,
        channel: 'stable',
        allowLegacy,
        logger: actions.log || (() => {})
      })

      if (resolved.status === 'rejected') {
        // remote 传下去，别清零 —— 有新版但不可下载 ≠ 已是最新
        return { success: true, local, remote: resolved.remote || '', url: '', signed: false, msg: resolved.reason }
      }

      // 第二道防线：签名只管「内容没被改」，不管「地址该不该放」
      const url = env.isAllowedExternalUrl(resolved.url, env.DOWNLOAD_HOSTS) ? resolved.url : ''

      return {
        success: true,
        local,
        remote: resolved.remote,
        url,
        sha256: resolved.sha256 || '',
        signed: resolved.status === 'hardened'
      }
    } catch (e) {
      return { success: false, local, msg: e.message || '无法检查更新' }
    }
  })
}
```

**返回形状 `{success, local, remote, url, msg}` 保持不变** —— 渲染层一行都不用动。
新增的 `sha256` / `signed` 只是给排查用的，不读也没关系。

## 3. 服务端侧要搬的文件

```
server/lib/update-signing.js                        ← 签名实现
migrations/051_client_release_signature.js          ← 三列：sha256 / signature / min_version
```

### 3.1 导出清单

```js
{
  MANIFEST_FIELDS,
  manifestPayload,  // (manifest) => Buffer
  parsePrivateKey,  // (pemOrBase64) => KeyObject（强制 ed25519）
  signManifest,     // (release, env) => manifest | null  没私钥返回 null
  buildManifest     // (dbRow, opts) => manifest | null   带准入条件的封装
}
```

### 3.2 挂到 `/client/update`

在 `findUpdate` 的返回里**额外**加一个 `manifest` 字段，其他字段一个都别动：

```js
const { buildManifest } = require('../lib/update-signing')

// 注意用 row 而不是可能回退到通用配置的 url ——
// downloads.client_url 是没有对应哈希的兜底地址，给它签名等于给没算过
// 哈希的包背书
const manifest = buildManifest(row, {
  appId: row.app || 'com.hellopix.desktop',
  channel: 'stable',
  onError: e => console.error('[findUpdate] 更新清单签名失败：', e.message)
})

return {
  success: true,
  compatible: !archBlocked,
  reason,
  version: row.version || '',
  url,
  title: row.title || '',
  os: row.os || '',
  app: row.app || app,
  manifest          // ← 只加这一个字段
}
```

兼容性：老客户端忽略 `manifest`，继续读 `version` / `url`；
新客户端优先读 `manifest` 并验签。**两边都能用，不用协调发版。**

### 3.3 `buildManifest` 的准入条件

三个条件缺一不可，任何一条不满足就返回 `null`（= 不下发清单）：

1. 记录有 `sha256`
2. 环境变量 `UPDATE_SIGNING_KEY` 存在且是 ed25519
3. URL 是 `https://`

**返回 `null` 而不是发一份空签名**，是为了让客户端走「服务端没给清单」的分支，
而不是收到半成品后验签失败 —— 后者会触发「有人在动更新通道」的告警，
而我们自己的配置缺失不该伪装成攻击。

### 3.4 迁移

```bash
node scripts/migrate.js up
```

三列都允许 NULL，因为存量记录没签过名。**不要填假值** ——
一个伪造成「已签名」的空串会让客户端把 `signature: ''` 当成有清单，走到验签失败。

## 4. 发布工具

```
scripts/update-keygen.js    ← 生成密钥对（只跑一次）
scripts/release-client.js   ← 算哈希 + 写库
```

### 4.1 首次启用（四条命令）

```bash
# ① 生成密钥
node scripts/update-keygen.js ./keys
#    产出 keys/update-signing.key（私钥，.gitignore 已拦）
#         keys/update-signing.pub.b64（单行 base64 公钥）

# ② 填公钥
#    把 pub.b64 的内容粘进 desktop/src/update/trusted-keys.js 的 PRIMARY

# ③ 服务端配私钥
export UPDATE_SIGNING_KEY="$(cat keys/update-signing.key)"

# ④ 跟着客户端一起打包发版
```

### 4.2 每次发版

```bash
node scripts/release-client.js \
  --version 1.3.0 \
  --url https://pixfanyi.com/downloads/HelloPix-Setup-1.3.0.exe \
  --file ./desktop/release/HelloPix-Setup-1.3.0.exe \
  --min-version 1.2.0
```

| 参数 | 说明 |
|---|---|
| `--file` | 必填。从真实文件流式算 SHA256（已与 `shasum -a 256` 对过） |
| `--sha256` | 替代 `--file`，但会打警告 —— 绕过了「从真实文件算」的保证 |
| `--min-version` | **防降级下限**。签名只能证明「官方发的」，证明不了「比现在新」 |
| `--url` | 记录不存在时必填，用于新建 |
| `--dry-run` | 只看会发生什么，不写库 |
| `--os` / `--arch` | 新建记录时的默认值是 `Windows` / `x64`，**macOS 必须覆盖** |

> `--min-version` 为什么重要：攻击者手里可以攥着一份**旧但签名完全合法**的清单
> （比如 1.2.0，漏洞已在 1.2.1 修了），重放给用户就能把他拉回有洞的版本。
> 签名的所有防线都拦不住它，只有版本下限能拦。

## 5. 灰度路径（别跳）

| 阶段 | 服务端 | 客户端 | 现象 |
|---|---|---|---|
| 现在 | 老代码 | 老代码 | 白名单，能更新 |
| 上线新服务端 | 有 `manifest` | 老代码 | 正常，老客户端忽略该字段 |
| 上线新客户端 | 有 `manifest` | 有公钥 | `hardened`，验签生效 |
| 过渡期 | 没私钥 | 有公钥 | `rejected`，**不能更新**（显式，有 error 日志） |
| 全量后 | — | — | 不设 `PIX_ALLOW_UNSIGNED_UPDATE` 即为严格模式 |

过渡期允许 `PIX_ALLOW_UNSIGNED_UPDATE=1` 降级跑白名单，但**只是过渡**：
它会把 `status` 变成 `legacy` 并在日志里留 `warn`，方便你数还有多少没升级。

## 6. 换钥必须走轮换（否则旧客户端永久失去更新）

```
① node scripts/update-keygen.js ./keys-new
② trusted-keys.js：新钥 → PRIMARY，旧钥 → PREVIOUS
③ 发一版客户端，让用户升上来（这版新旧都认）
④ 服务端换新私钥开始签
⑤ 旧版本覆盖率足够低后，清空 PREVIOUS
```

跳过 ② ③ 直接换服务端私钥 = **所有旧客户端立即失去更新能力**，
而它们恰恰是最需要被更新的那批（它们没有别的路径能修好自己）。

`PUBLIC_KEYS` 是数组、`verifySignature` 是逐把尝试，就是为了支持这个过渡期。

## 7. 测试怎么搬

两个测试文件，直接放进 `test/`：

```
test/update-signature.test.js        ← 客户端侧 19 条，全是「应该被拒绝」的构造
test/update-signing-server.test.js   ← 服务端侧 11 条
```

客户端那 19 条覆盖的攻击形态：

| 用例 | 拦得住什么 |
|---|---|
| 篡改 url | 白名单域名上换恶意包 |
| 篡改 sha256 | 换包但保留原清单 |
| 换 appId | 拿同作者的别的产品的合法清单 |
| 攻击者自己重签 | 拿到别人公钥后伪造 |
| 重放旧版本 | 降级到有洞的版本 |
| 签名截断 / 空串 | 畸形输入 |
| 空公钥 | 忘记注入 |
| 公钥换成 RSA | 算法错配静默通过 |
| 字段顺序调整 | 「顺手格式化」破坏契约 |

服务端那 11 条里有一条特别关键：

```js
assert.deepEqual(MANIFEST_FIELDS, clientSignature.MANIFEST_FIELDS)
```

再一条直接拿**客户端那份 `manifestPayload`** 去验**服务端签出的东西**。
字段顺序在服务端和客户端各写了一份 —— 任何一侧改动都会让所有存量客户端
静默失效（用户只看到「检查更新失败」，没有任何线索）。这条测试就是防这个的。

测试里自己生成临时密钥对，通过 `publicKeys` 注入，所以正式公钥换了也不用改测试。

## 8. 搬之前先看这四条

1. **`signature.js` 和 `verify-release.js` 别拆开改。** 它们耦合在「原文怎么拼」上，
   拆开改几乎必然改错顺序。
2. **`MANIFEST_FIELDS` 一个字都别动。** 改了 = 所有存量客户端更新失败。
   真要加字段，必须先发一版客户端同时认新旧两种，再切。
3. **私钥绝不进仓库。** 校验一下 `.gitignore` 里有没有 `update-signing.key` 和 `*.pem`。
   私钥泄露 = 攻击者能给所有用户推任意包，而我们的签名校验会**一路放行**
   —— 它验的正是这把私钥签出来的东西。出事只能靠 `PREVIOUS` 槽位轮换止损。
4. **项目里已有的未提交改动先理一下。** 我改的时候工作区里就有别人的改动在
   `main.js` / `guest-inject.js` / `tab-context-menu.js` 里，别混在一起提交。
