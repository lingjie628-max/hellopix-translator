> 目标读者：产品负责人。

## 一、先解决一个绕不过去的取舍

在讨论架构之前，必须先把这件事说清楚 —— 它决定了整个方案的形状。

### 事实

```
翻译必须走平台（平台持有厂商 API Key、按字符计费）
        ↓
翻译必须把原文发给厂商
        ↓
原文必须经过平台
```

**平台在技术上无法"看不到"原文。** 这不是实现问题，是业务流程决定的。

### 三种选择

| | 做法 | 平台能看到 | 代价 |
|---|---|---|---|
| **A** | 平台代理翻译，但**不落库** | 经手，不留存 | 无（推荐）|
| **B** | 商户自备厂商 Key，平台不参与翻译 | **完全看不到** | 平台失去计费依据，商业模式要改成按台/按月 |
| **C** | 混合：平台通道 + 商户可填自己的 Key | 用平台通道时经手，用自己 Key 时不经手 | 实现量最大 |

### 我的建议：**A**

理由：

1. **"不上服务器"的实际诉求是"不被留存"**，而不是"不许经过" —— 客户真正担心的是数据沉淀在平台
2. 平台**经手但不留存**，与"平台存了 300 字原文 + 完整聊天记录"有本质区别
3. 选 B 会改变商业模式（现在按字符计费是核心），影响比技术方案大得多
4. A 的实现是**删代码**（删掉 snippet 写入），风险最低

**但这条必须你拍板** —— 因为如果客户的原话是"连经过都不行"，那只能选 B。

## 二、目标架构

```
┌─────────────────── 商户内网 ───────────────────┐
│                                                │
│   本地服务（工单池）                            │
│   ├─ 客户身份识别（手机号归一化 + 指纹）         │
│   ├─ 撞单检测                                   │
│   ├─ 消息存储                                   │
│   ├─ 工单 / 粉丝                                │
│   └─ 数据库（SQLite 或 PostgreSQL）             │
│                    ▲                            │
│         ┌──────────┼──────────┐                │
│      客服电脑1   客服电脑2   客服电脑3           │
│      （客户端）  （客户端）  （客户端）          │
└────────┬───────────────────────────────────────┘
         │ 只发原文用于翻译，平台不落库
         │ 只回译文与剩余字符数
         ▼
┌──────────── 平台服务器 ────────────┐
│  · 翻译代理（不存原文）             │
│  · 计费（只记字符数、通道、时间）    │
│  · 商户账号 / 套餐 / 充值           │
│  · 客户端版本 / 线路 / 公告         │
└────────────────────────────────────┘
```

### 数据边界

| 数据 | 存哪 | 平台可见 |
|---|---|---|
| **聊天内容** | 商户内网 | ❌ 经手不留存 |
| **客户身份（手机号、昵称）** | 商户内网 | ❌ |
| **工单 / 粉丝** | 商户内网 | ❌ |
| 撞单记录 | 商户内网 | ❌ |
| 翻译字符数 | 平台 | ✅ 计费必需 |
| 商户账号 / 套餐 / 充值 | 平台 | ✅ |
| 翻译通道 Key | 平台 | ✅ |

**平台侧要下架的表**：`messages` · `conversations` · `customers` · `platform_identities` ·
`customer_identities` · `customer_merchant_links` · `customer_owners` · `collision_events` ·
`identity_match_events` · `customer_merge_candidates` · `order_fans` · `order_details`

**平台侧要改的**：`translate_logs.snippet` 去掉（**不再存原文片段**）

**平台侧保留的**：商户账号、套餐、充值、翻译计费、客户端版本

## 三、本地服务的形态

三个选项：

| 方案 | 怎么用 | 优点 | 缺点 |
|---|---|---|---|
| **A. 独立可执行文件** | 商户在内网某台机器双击运行 | 无需 Docker、无需装 Node | 要按平台打包（Win/Linux）|
| **B. Docker 镜像** | `docker run` 一条命令 | 环境一致、升级方便 | 商户要会 Docker |
| **C. 客户端内置** | 客户端主进程起一个本地服务 | 零部署 | **多台电脑无法共享**，违背初衷 |

### 我的建议：**A 为主，B 作为可选项**

理由：
- 目标客户是跨境电商卖家，**不该假设他们会 Docker**
- 单文件可执行（Node SEA 或 pkg 打包）双击即用
- 同时提供 Docker 镜像，给有运维能力的商户

### 客户端如何找到本地服务

配置项，三处可设（优先级从高到低）：

1. 客户端本地配置（每个客户端单独设）
2. 商户后台的「内网服务地址」
3. 默认 `http://127.0.0.1:8899`（单机模式，本地服务与客户端同机）

**必须有"连接失败"的明确状态** —— 本地服务没起来时不能让客户端静默不工作。

## 四、撞单检测的变化

这是最需要想清楚的部分。

### 现状（服务器端）

平台知道所有商户的客户 → 能做跨商户比对。

### 本地化之后

```
商户 A 的本地服务  ←→  只有 A 的数据
商户 B 的本地服务  ←→  只有 B 的数据
        ↑
   两者互不可见，平台也不知道任何客户标识
```

**结论：跨商户撞单在技术上不再可能。**

你之前的选择是「保留架构但暂不启用」—— 但本地化之后，**架构也保不住了**：
平台根本收不到客户标识，没有比对的输入。

### 三个可选路线

| 路线 | 做法 | 隐私 | 跨商户能力 |
|---|---|---|---|
| **1. 彻底放弃** | 只做本商户内查重 | 最强 | ❌ |
| **2. 只上匿名指纹** | 客户端上报 `HMAC(平台密钥, 手机号)`，不含原文 | 中 | ✅ 能比对 |
| **3. 商户自愿加入比对联盟** | 默认关闭，商户勾选同意后上报指纹 | 中 | ✅ |

**路线 2 的细节**：平台只存指纹（不可反推），收到新指纹时回一句
「这个客户在平台别处出现过」——**不说是谁**。这样商户能知道"撞了"，
但拿不到对方的任何信息。

⚠️ **但路线 2 与"数据不上服务器"是矛盾的** —— 指纹也是数据，
虽然不可反推，但它让平台能统计"商户 A 和商户 B 有多少共同客户"。

**我的建议：先做路线 1，把路线 2 的接口预留但不实现。**
等客户明确要跨商户能力、并愿意签数据协议时再开。

## 五、改动清单

### 平台侧（服务端）

| 改动 | 工作量 | 风险 |
|---|---|---|
| 删 `translate_logs.snippet` 写入 | 小 | 低 |
| 下架客户身份相关接口（`/customer/ingest`、`/customer/reminders`）| 小 | 低 |
| 超管下架三个页面（统一客户 / 撞单规则）| 小 | 低 |
| 保留但停用相关表（不删，留回滚余地）| 小 | 低 |

### 本地服务（新项目）

| 模块 | 说明 |
|---|---|
| HTTP 服务 | 接收客户端上报 |
| 数据库 | SQLite 起步；数据量大时可选 PostgreSQL |
| 身份识别 | **直接复用现有 `server/lib/identity.js`**（归一化 + HMAC 指纹）|
| 撞单检测 | **直接复用 `customer-identity-service.js`** 的核心逻辑 |
| 客户端鉴权 | 本地服务需要自己的简单鉴权（否则内网任何人可读）|

**好消息：客户身份系统的核心逻辑可以直接搬。** 现有的
`identity.js`（手机号归一化、HMAC 指纹）与撞单判定逻辑
本来就是纯函数 + 仓储，换个数据库就能跑。

### 客户端

| 改动 | 说明 |
|---|---|
| 上报地址 | 从平台改为本地服务 |
| 连接状态 | 本地服务不可用时要有明确提示 |
| 离线容忍 | 本地服务短暂不可用时不丢数据，恢复后补传 |

## 六、分阶段实施

**不要一次做完。** 建议：

| 阶段 | 做什么 | 可验证的结果 |
|---|---|---|
| **1** | 平台侧停止存原文（删 snippet）| 翻译日志不再有原文 |
| **2** | 本地服务最小可用（收上报 + 存消息）| 客户端能把数据送到内网服务 |
| **3** | 搬身份识别与撞单检测 | 本商户内查重可用 |
| **4** | 客户端切换上报地址 + 连接状态 | 全链路走内网 |
| **5** | 平台侧下架相关接口与页面 | 平台不再接收客户数据 |

每一阶段都能独立上线、独立回滚。

## 八、一个必须提前说的风险

**本地服务的运维责任转移到了商户。**

服务器上的服务由我们运维；装到商户内网之后：
- 服务挂了、磁盘满了、机器重启了 —— **我们看不到也不知道**
- 商户的 IT 能力参差不齐

所以本地服务必须做到：

1. **零配置启动** —— 双击即用，不需要改配置文件
2. **自带健康页** —— 浏览器打开能看到状态
3. **数据自动备份** —— 至少每日一次，存到同目录的 `backup/`
4. **崩溃自动重启** —— 作为系统服务安装

**这一块的实现量可能比业务逻辑还大**，要有心理预期。
