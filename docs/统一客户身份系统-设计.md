# 统一客户身份系统 · 设计文档

> 状态：**待评审**。本文只描述设计，尚未动代码。
> 目标读者：产品负责人、客户方技术对接人。

---

## 一、这个系统要回答的四个问题

无论一个客户从哪个平台、哪个账号进来：

1. **这个人是谁？** —— 跨平台、跨账号、跨商户识别为同一个 Customer ID
2. **他以前和谁聊过？** —— 只在本商户范围内可见
3. **现在由谁负责？** —— 跟进关系（customer_owner）
4. **是否发生撞单？** —— 同一客户被多人同时跟进时实时告警

**它的定位是底层客户数据层，不是一个独立功能页。**

---

## 二、最关键的设计：身份共享，内容隔离

这是整个系统的地基，也是唯一不能妥协的地方。

```
                    Customer C_100001        ← 身份层：平台级共享
                          │                    （只有指纹，没有内容）
        ┌─────────────────┴─────────────────┐
        │                                   │
   ┌────▼─────┐                       ┌─────▼────┐
   │  商户 A   │                       │  商户 B   │   ← 内容层：硬隔离
   │ 账号A1    │                       │ 账号B1    │
   │ 账号A2    │                       │ 账号B2    │
   │  ├ 会话   │                       │  ├ 会话   │
   │  └ 消息   │                       │  └ 消息   │
   └──────────┘                       └──────────┘

   商户 A 能查到：C_100001 也在平台别处存在
   商户 A 查不到：商户 B 是谁、聊了什么、客户叫什么
```

**一句话：能知道"撞了"，不能知道"跟谁撞的"。**

### 隔离怎么保证（三层防线，缺一不可）

**防线 1：表结构上物理分离**

身份表和内容表**不在一张表里**，内容表**每一张都带 `user_id`**：

```
customers               ← 平台级，无 user_id，只有指纹
customer_merchant_links ← 客户↔商户，隔离边界
conversations           ← 带 user_id
messages                ← 带 user_id（冗余，但让隔离可被机械校验）
```

内容查询**必须**带 `user_id` 条件。给 `messages` 冗余一列 `user_id` 是刻意的：
它让"这条查询有没有做隔离"变成**可以静态检查**的事，而不是靠人记住。

**防线 2：仓储层强制 + 自动化测试**

所有内容查询走统一的仓储函数，函数签名强制要求 `userId` 参数。
配一个测试，**静态扫描所有内容查询，发现没有 `user_id` 条件就让测试失败**。

> 这一条比代码评审可靠 —— 评审会漏，测试不会。

**防线 3：接口层输出白名单**

跨商户查询的返回体**只允许**这几个字段：

```
{ 是否重复: bool, 平台首见: date, 跨商户数: int }
```

**不允许**出现：商户名、员工名、账号、昵称、消息、工单号。
出口处做字段白名单校验，多一个字段就报错。

## 三、数据模型

### 3.1 身份层（平台级，跨商户共享）

```sql
-- 平台级客户指纹。存的是 HMAC，不是原始标识。
-- 用 HMAC 而非 SHA256：防止有人拿已知 ID 自己算哈希来撞库。
CREATE TABLE platform_identities (
  fingerprint    bytea PRIMARY KEY,          -- HMAC-SHA256(平台密钥, 规范化标识)
  identity_type  text NOT NULL,              -- phone | platform_uid | email | username
  first_seen_at  timestamptz NOT NULL DEFAULT now(),
  last_seen_at   timestamptz NOT NULL DEFAULT now(),
  merchant_count int NOT NULL DEFAULT 1,     -- 被几个商户接触过
  touch_count    int NOT NULL DEFAULT 1      -- 被接触总次数
);

-- Customer ID
CREATE TABLE customers (
  id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  public_id      text NOT NULL UNIQUE,       -- 对外展示的 C_100001
  primary_fingerprint bytea REFERENCES platform_identities(fingerprint),
  created_at     timestamptz NOT NULL DEFAULT now(),
  merged_into    bigint REFERENCES customers(id)   -- 合并后指向新客户，保留溯源
);

-- 客户的多个身份（一个人可能有手机号 + 多个平台 ID）
CREATE TABLE customer_identities (
  customer_id    bigint NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  fingerprint    bytea NOT NULL REFERENCES platform_identities(fingerprint),
  confidence     text NOT NULL,              -- high | medium | low
  linked_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (fingerprint)                  -- 一个指纹只能属于一个客户
);

-- 客户 ↔ 商户。这张表就是隔离边界。
CREATE TABLE customer_merchant_links (
  customer_id    bigint NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  user_id        bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  first_seen_at  timestamptz NOT NULL DEFAULT now(),
  last_seen_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (customer_id, user_id)
);
```

### 3.2 内容层（商户隔离，每张表都带 user_id）

```sql
CREATE TABLE conversations (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id         bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- 隔离键
  customer_id     bigint REFERENCES customers(id),
  platform        text NOT NULL,             -- telegram | whatsapp | ...
  account_key     text NOT NULL,             -- 我方账号标识（对应 order_details.account）
  peer_key        text NOT NULL,             -- 对方在该平台的标识（peer id / 手机号）
  display_name    text NOT NULL DEFAULT '',
  last_message_at timestamptz,
  UNIQUE (user_id, platform, account_key, peer_key)
);

CREATE TABLE messages (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id         bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- 冗余，为了可机械校验
  conversation_id bigint NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  customer_id     bigint REFERENCES customers(id),
  direction       text NOT NULL,             -- in | out
  sender_key      text NOT NULL DEFAULT '',  -- 发送方标识（我方账号 / 对方 peer）
  body            text NOT NULL,             -- 原始内容
  body_translated text,
  lang_detected   text,
  operator_id     bigint REFERENCES sub_accounts(id),  -- 哪个员工发的（我方消息）
  source_platform text NOT NULL,             -- 来源平台（溯源，永不因合并丢失）
  source_account  text NOT NULL,             -- 来源账号
  source_conv_id  text NOT NULL DEFAULT '',  -- 平台原始会话 ID
  source_msg_id   text NOT NULL DEFAULT '',  -- 平台原始消息 ID
  sent_at         timestamptz NOT NULL,
  ingested_at     timestamptz NOT NULL DEFAULT now()
) PARTITION BY RANGE (sent_at);              -- 按时间分区，便于留存与清理
```

> **溯源字段是强制的**：规范里明确要求「不能因为合并客户就丢失原始数据来源」。
> 合并只影响 `customer_id`，`source_*` 四列**任何情况下都不改写**。

### 3.3 归属与撞单

```sql
CREATE TABLE customer_owners (
  id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id          bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  customer_id      bigint NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  employee_id      bigint REFERENCES sub_accounts(id),
  account_key      text NOT NULL DEFAULT '',
  status           text NOT NULL DEFAULT 'FOLLOWING',
                   -- UNASSIGNED | FOLLOWING | PAUSED | COMPLETED | LOST
  assigned_at      timestamptz NOT NULL DEFAULT now(),
  last_activity_at timestamptz NOT NULL DEFAULT now(),
  released_at      timestamptz
);
-- 只有 FOLLOWING 参与撞单检测；COMPLETED 之后别人再来不告警
CREATE UNIQUE INDEX customer_owners_active_uniq
  ON customer_owners (user_id, customer_id) WHERE status = 'FOLLOWING';

CREATE TABLE collision_events (
  id                    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id           bigint NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  kind                  text NOT NULL,       -- same_merchant | cross_merchant
  existing_owner_id     bigint REFERENCES customer_owners(id),
  existing_user_id      bigint NOT NULL,
  existing_employee_id  bigint REFERENCES sub_accounts(id),
  existing_account_key  text NOT NULL DEFAULT '',
  new_user_id           bigint NOT NULL,
  new_employee_id       bigint REFERENCES sub_accounts(id),
  new_account_key       text NOT NULL DEFAULT '',
  detected_at           timestamptz NOT NULL DEFAULT now(),
  resolution            text NOT NULL DEFAULT 'pending',
                        -- pending | kept_existing | transferred | both_continue | ignored
  resolved_by           bigint,
  resolved_at           timestamptz
);
```

### 3.4 疑似重复

```sql
CREATE TABLE customer_merge_candidates (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_a    bigint NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  customer_b    bigint NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  reason        text NOT NULL,               -- name_match | username_match | ...
  confidence    numeric(4,3) NOT NULL,       -- 0.000 ~ 1.000
  evidence      jsonb NOT NULL DEFAULT '{}'::jsonb,
  status        text NOT NULL DEFAULT 'pending',
                -- pending | merged | rejected
  reviewed_by   bigint,
  reviewed_at   timestamptz
);
```

## 四、身份匹配算法

### 4.1 匹配优先级（按可信度从高到低）

| 顺序 | 依据 | 可信度 | 跨平台能力 |
|---|---|---|---|
| 1 | **手机号** | 极高 | **强**（WhatsApp 必有，Telegram 可能有） |
| 2 | 平台稳定 ID | 高 | 弱（各平台 ID 不互通） |
| 3 | 邮箱 | 高 | 中 |
| 4 | 用户名 | 中 | 弱（可改） |
| 5 | 姓名 / 公司 | **低** | 无 |

### 4.2 三种结果

```
命中规则 1-3 且唯一  →  高置信度，自动关联已有 Customer ID
命中规则 4-5 或存在歧义  →  疑似重复，进 customer_merge_candidates，**不自动合并**
无命中  →  创建新 Customer ID
```

> **规范明确要求：绝不能仅因姓名相同就自动合并。**
> 同名同姓太常见，误合并会把两个真实客户的聊天记录混在一起 —— 这是不可逆的数据污染。

### 4.3 规范化规则（决定指纹怎么算）

```
手机号：去掉所有非数字字符 → 补国际区号 → E.164 归一
        8613800138000 / +86 138 0013 8000 / 013800138000
        必须归一成同一个值

用户名：转小写、去掉 @ 前缀、去掉首尾空白
平台ID：按平台规则归一（Telegram peer id 取数字部分）
```

**归一化不一致 = 同一个客户被算成两个**，这是准确率的第一道关口。

## 五、撞单检测

### 5.1 触发时机

任何账号**收到新消息 / 创建联系人 / 开始跟进**时，同步检查。

### 5.2 判定逻辑

```
1. 解析出 customer_id
2. 查 customer_owners WHERE user_id=当前商户 AND customer_id=? AND status='FOLLOWING'
3. 不存在        → 建立跟进关系，正常
4. 存在且是本人  → 更新 last_activity_at，正常
5. 存在且是他人  → 产生 collision_event
```

### 5.3 通知内容按「是否同商户」分级 —— 这是关键

| 场景 | 通知"原负责人" | 通知"新跟进人" | 通知平台管理员 |
|---|---|---|---|
| **同商户** | 「李四也开始跟进该客户」 | 「该客户已由张三负责」 | 可选 |
| **跨商户** | 「有平台其他销售也在跟进该客户」 | 「该客户正被平台其他销售跟进」 | **完整信息** |

**跨商户场景下，双方都拿不到对方的任何标识** —— 没有商户名、没有员工名、没有账号。
这在服务端强制，不是前端隐藏。

### 5.4 可配置规则（不写死）

存 `app_settings`，超管后台可改：

| 参数 | 默认 | 说明 |
|---|---|---|
| `auto_assign_on_first_follow` | true | 首次有效跟进自动归属 |
| `collision_notify_mode` | `warn` | warn（只提醒）/ block（阻止发送）/ takeover（可强制接管） |
| `owner_idle_release_days` | 30 | 超过 N 天无活动回归公共池 |
| `cross_merchant_detect` | false | **跨商户检测开关，默认关闭，需商户同意后才开** |
| `merge_auto_threshold` | 0.95 | 自动合并的置信度门槛 |
| `message_retention_days` | 180 | 消息留存天数 |

## 六、实时通知

**现状**：客户端是 **8 秒轮询** session 接口，没有长连接。

**建议**：MVP 阶段**搭车轮询**，不引入 WebSocket。理由：

| | 搭车轮询 | WebSocket |
|---|---|---|
| 撞单场景够用吗 | ✓ 延迟 ≤8 秒 | ✓ 更快 |
| 工作量 | 小 | 大（连接管理、断线重连、多实例广播）|
| 风险 | 无 | 新增故障面 |

撞单不是高频交易，"8 秒内知道"和"立刻知道"对结果没有区别。
**等真有实时性要求的功能（比如多人协同编辑）再上 WebSocket。**

## 七、客户端采集（Phase 0，工作量最大）

### 7.1 现实能力盘点

| 平台 | 能否读消息 | 依据 |
|---|---|---|
| **Telegram Web A** | ✓ | CSS 注入已有，URL 可取 peer id |
| **WhatsApp Web** | ✓ | CSS 注入已有（`.copyable-text`）|
| 其余 33 个平台 | ❌ | 仅加载网页，无注入逻辑 |

**所以"全平台"在 MVP 阶段实际是 Telegram + WhatsApp 两个平台。**

### 7.2 三个天花板（必须让客户知道）

1. **拿不到平台原始消息 ID** —— DOM 抓取没有稳定 ID，
   `source_msg_id` 多数情况为空，去重只能靠"内容+时间+发送方"的组合哈希
2. **换账号 = 换人** —— 同一人换 Telegram 号，任何系统都认不出
3. **网站改版即失效** —— DOM 选择器变了就采不到，需要持续维护

### 7.3 上报策略

- **本地先落盘，再批量上报** —— 断网不能丢数据
- 批量大小 / 间隔可配，避免高频请求拖慢客户端
- **上报失败要能重试且有上限**，避免无限堆积占满磁盘

## 八、容量与成本（必须提前算）

按**单个商户** 10 账号 × 50 活跃会话 × 40 条/天估算：

```
消息量：10 × 50 × 40 = 20,000 条/天
存储：  20,000 × 250 字节 ≈ 5 MB/天 ≈ 150 MB/月
```

**平台 100 个商户：约 15 GB/月，一年 180 GB。**

加上索引通常 ×1.5 ≈ **270 GB/年**。

> 这是聊天内容，**不能只算存储成本，还要算合规责任**：
> 需要留存策略、加密、导出与删除机制。`message_retention_days` 不是可选项。

**建议**：消息表按 `sent_at` 分区，过期分区直接 `DROP` —— 比 `DELETE` 快几个数量级，
且不会因为大事务把库拖垮。

## 九、MVP 范围

### 做什么

| # | 内容 |
|---|---|
| 1 | `platform_identities` / `customers` / `customer_identities` 三张身份表 |
| 2 | `conversations` / `messages`（含完整溯源字段） |
| 3 | `customer_owners` + 撞单检测（**同商户**）|
| 4 | 客户端上报：Telegram peer id + 消息 + 操作员工 |
| 5 | 撞单同步告警 + 搭车轮询通知 |

### 明确不做（留给后续 Phase）

- ❌ 跨商户撞单（**默认关闭**，需要商户协议确认后再开）
- ❌ 疑似重复客户 UI
- ❌ 管理员规则配置页
- ❌ 客户统一详情页
- ❌ 客户合并操作

### 验收标准

1. 同一客户在两个账号出现 → **识别为同一 Customer ID**
2. 张三跟进中、李四再联系 → **立即告警**，两人都知道
3. 张三标记 COMPLETED 后李四再联系 → **不告警**
4. 任意商户**无法**通过任何接口拿到其他商户的客户内容
5. 合并后原始 `source_*` 字段**逐字段不变**

## 十一、风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| 商户对"跨商户比对"反感 | 高 | 默认关闭 + 协议告知 + 只返回布尔 |
| 误合并污染数据 | **高** | 高置信度才自动；姓名不自动合并；合并可回滚（`merged_into`）|
| DOM 采集被改版打断 | 高 | 采集失败要**告警**，不能静默失效 |
| 消息存储成本失控 | 中 | 分区 + 留存策略 + 监控 |
| 跨商户查询被用来撞库 | 中 | HMAC + 只能查自己名下的粉 + 限流 + 审计 |
| 销售无视告警 | 中 | 先跑数据看真实反应，再决定是否升级为 block |
