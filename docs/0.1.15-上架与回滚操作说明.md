## 3. 本版内容（相对 0.1.14）

用户明确要求**两条链分开处理、都 PASS 才允许再发**。本版两条链都定位到根因并修掉。

### 3.1 链 A · 点「译」按钮静默失效（P0）

**现象**：新消息正常送达、消息下方已出现「译」按钮，点它**什么都不发生** ——
没有译文、没有提示、按钮也消失。

**根因（三条叠加）**：

1. `addClick()` 逐 chip 绑 `onclick`，并把 `host` / `root` 两个**裸 DOM 引用**闭包捕获，
   跨越 `await` 再使用。WhatsApp 是 React 托管列表，重绘会换掉这些节点；拿已 detach
   的节点解析正文 → 空串 → `paint()` 走 `clearExtras()` **顺手删掉按钮**。
   真机表现就是"点了没反应，按钮没了"。
2. chip 缺 `pointer-events: auto` / `z-index`。WhatsApp 消息层若干状态下会关掉
   pointer-events，继承下来就是"看得见、点不动"。
3. 整条链**一行 trace 都没有**，也没有失败反馈。

**修法**：

- 事件委托挂 `document` **捕获阶段**（重绘丢不掉，也不受消息区 stopPropagation 影响）；
- 点击时记 `stableMessageKey`（消息行 `data-id`），完成后**按 key 重查当前气泡**再渲染；
- chip 三态：`译` → `翻译中…` → 成功显示译文 / 失败 `翻译失败 · 点击重试`；
  **「翻译中…」只活在 Hello Pix 自己的控件上，绝不写进输入框或消息正文**；
- `translateTextDetailed()` 原样回报真实错误码；
- 结构化 trace：`MANUAL_TRANSLATE_CLICK → MANUAL_PARSED → MANUAL_REQUEST →
  MANUAL_RESPONSE → MANUAL_RENDERED`（带 `messageId` / `tabId` / `partition` / `engine` /
  `sourceTextLen`）；失败分支 `MANUAL_ROW_LOST` / `MESSAGE_TEXT_EXTRACTION_FAILED` /
  `MANUAL_RENDER_MISSED` / `MANUAL_FAILED` / `MANUAL_CLIENT_EXCEPTION`。

### 3.2 链 B · 发送翻译会丢用户内容（P0）

**现象一（草稿被吃）**：用户按发送后开始打**下一条**，第一条译文回来时把草稿整段覆盖
并发出去，用户正在打的内容凭空消失（真机已复现）。

**现象二（连发丢消息）**：连续快速发送 5 条，实际只发出 3 条，中间几条被静默丢弃。

**根因**：

1. `deliverSend()` 写回译文前**没有任何"用户已改动输入框"的检查**，无条件覆盖；
   翻译失败时的兜底 `writeComposer(box, raw)` 同样盖掉草稿。
2. `fireSend()` 用 `setTimeout(…, 400)` 开了 **400ms 的 suppression 时间窗**，窗口内
   **任何**发送事件都被当成"我们自己发的" —— 用户按的回车被静默吃掉。
3. 上一条动作的 400ms `sendActionPhase` 复位定时器会清掉下一条**正在飞**的 phase，
   下一条走到 `fireSendVerified` 时被 `STALE_ACTION` 拦下。

**修法**：

- 写回前先 `composerDraftChanged(box, raw)`；有草稿先存下、发出译文后
  `writeAndVerify()` 把草稿放回输入框；放不回去**明说**并提示（绝不静默丢内容）；
- `suppression` 改为**同步窗口**（`finally` 里立即复位）；
- phase 复位定时器校验 `sendActionId === myAction`。

### 3.3 链 B 附带 · 「发送原文」卡死循环（P0）

翻译失败提示里的「发送原文」**永远发不出去**：它走 `fireSendVerified()`，而那要求
`sendActionPhase === 'replaced'`；失败态是 `translating`，永远不满足 → `STALE_ACTION`
拦下 → 什么都不发 → 又弹回同一个失败提示。

**修法**：拆出 `fireSendUserAuthorized()` —— 用户明确授权的发送不要求走完翻译状态机，
但**保留** `sendableBody()` 校验（正文不得含占位符、必须等于预期），一点不放松。

  这两条是 0.1.14 真机复现过的数据丢失，**必须有真机证据才算闭环**。
- **Windows 免安装版不进入更新通道**（不登记 `client_releases`），只能手动下载。

## 6. 回滚

```sql
UPDATE client_releases SET enabled = false, updated_at = NOW() WHERE version = '0.1.15';
UPDATE client_releases SET enabled = true,  updated_at = NOW() WHERE version = '0.1.14';
```

回滚只是让**更新提示**回到 0.1.14，**不会**把已经装成 0.1.15 的用户变回去。
真要让用户退回，得再发一个版本号更大的包（客户端只认更大的版本号）。

> ⚠️ **本次回滚的代价极大**：0.1.14 正是「点「译」完全没反应 + 发送翻译会丢用户内容」
> 这两个 P0 的版本。回滚到 0.1.14 等于把这两条重新放回线上。
> 若回滚原因是 0.1.15 引入了新问题，应**优先热修复并升到 0.1.16**，而不是回退到 0.1.14。

**没有迁移需要回滚**（本版是纯客户端修复）。
