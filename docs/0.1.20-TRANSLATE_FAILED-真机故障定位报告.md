## 0. 结论先行（TL;DR）

1. **0.1.20 的两次「翻译失败」不是上游翻译失败，也不是 0.1.20 的代码回归。**
   两次请求**根本没有到达服务器**：服务端 nginx 访问日志、`translation_reservations`、应用日志里都**没有任何记录**。客户端在自己的传输层约 10.4s / 10.7s 后放弃，并把「连不上」统一上报成了 `TRANSLATE_FAILED`。

2. **故障早于 0.1.20。** 同一天 **13:13:47（此时跑的还是 0.1.19）** 已经出现过一次发送翻译失败，而且那一次是**真正的上游超时**（服务端 8s 超时 → HTTP 502）。因此「0.1.19 行、0.1.20 不行」的版本回归假设**不成立**。

3. **0.1.19 → 0.1.20 的客户端差异只有两处，都不在翻译/网络/发送链上**：
   - 沉降观察窗：固定 500ms → 60ms 下限 / 400ms 上限（**发生在翻译成功之后**）
   - 新增 `SEND_PERF` 埋点与四态状态条（纯观测）
   翻译请求、`api()`、错误分类、发送闸门**一行未动**。

4. **计费安全：失败已全额退款，未写 `translate_logs` / `translation_usage`，没有重复扣费、没有原文抢发。**

5. **真正需要修的是客户端传输层的健壮性**（一次坏连接会卡满 10s 才失败，且被误报成「翻译失败」），而不是回退版本。

## 2. 失败发生在发送链的哪一步

发送链：`intercept → snapshot → 【translate】 → native-input → settle → send`

**失败点：`translate` 这一步。**

代码定位（`desktop/guest-inject.js`，`deliverSend()`）：

```js
res = await translateTextDetailed(masked.masked, false, TRIGGER_SEND)
const out = String((res && res.out) || '')
if (!out) {
  const code = String((res && res.code) || 'TRANSLATE_FAILED')
  ...
  if (canSafelyRestore(box, raw)) await nativeSetComposer(box, raw, 'translate_failed_restore')
  trace('TRANSLATE_FAILED', { chain: 'send', failClosed: true, code: code })
  showSendFailureNotice(box, raw, masked, { title: '翻译失败，消息未发送', code: code })
  return false
}
```

因此：
- **翻译没拿到译文 → 直接 fail-closed，`native-input/settle/send` 一步都不会执行。**
- 用户在 trace 里看到的 `NATIVE_INPUT_BEGIN / COMPOSER_CLEARED / NATIVE_TEXT_INSERTED / LEXICAL_SETTLED`（`why: translate_failed_restore`）**不是发送**，而是失败后把**原文回填到输入框**的兜底动作（`expected.len=11` 正是原文长度）。这也解释了「原文退回输入框、没发出去」。

## 3. 具体底层错误（本次有两类，务必区分）

### 3.1 0.1.20 的两次 —— **客户端传输层失败（请求没出去）**

- 客户端：`TRANSLATE_STARTED` → **约 10.4s / 10.7s** → `TRANSLATE_FAILED`
- 服务端 nginx access log：17:18:21 之后到 17:40 之间，**没有一条 `POST /apis/translate/run`**
- 服务端 DB：**没有对应的 `translation_reservations` 行**（最后一条是 17:13:47 的 #417）

- 判定：**连接层失败 / 连接未建立或悬挂**（10s 量级超时），服务器全程没参与

> 说明：客户端 `api()` **没有任何超时**，所以一次坏连接会一直挂到操作系统的连接超时才失败 —— 这就是「等约 5–10 秒才报错」的来源。

### 3.2 0.1.19 的那一次 —— **真正的上游翻译超时**

- 客户端：13:13:47.3 → 13:13:56.8（~9.5s）

- 服务端应用日志：`[api] POST /apis/translate/run -> 502 8558ms`
- 引擎配置：`gpt / OpenAI / model=gpt-5.6-luna / call_params={}` → 走**默认上游超时 `DEFAULT_TIMEOUT_MS = 8000`**
- 判定：请求到达服务器，**上游 GPT 调用 8s 未返回被 abort** → 502；预留已 release 退款

## 7. 错误归类问题（回答「是真上游失败还是被错误归类」）

**是「其他异常被归到了 `TRANSLATE_FAILED`」。**

- 客户端的 `TRANSLATE_FAILED` 是**兜底码**：只要 `pix.translate` 抛错，或 `success:false` 且响应里没有 `code`，都会显示成它（`guest-inject.js` 的 `.catch` 与 `String(resp.code || 'TRANSLATE_FAILED')`）。
- 所以 0.1.20 那两次明明是**「连不上服务器」**，被显示成了**「翻译失败」**，把排查方向带偏。
- 另外，0.1.19 那次服务端明明回了 `{success:false, code:'TRANSLATE_FAILED'}`（502），客户端 trace 却记成了 `EMPTY_RESULT` —— 归类**前后不一致**，建议一并理顺。

不影响安全：两次都严格 fail-closed（原文完整退回、未发原文）。

## 8. 最小修复方案

### 第一步（立刻，不改代码）
用**现在这台机器上已装的 0.1.20** 再复测一次发送翻译。理由：本次两次失败落在 13:18–13:20 一个约两分钟的传输抖动窗口内，而复核时应用自身的 fetch 栈 **10/10 成功、每次 ~330ms**。若复测通过，即确认是环境抖动而非版本问题。

### 第二步（确认后做，最小改动，不新增产品功能）
1. **给 `api()` 加有界超时 + 传输错误重试 1 次**：现在是**完全无超时**，一次坏连接会卡满 10s 才失败。建议 3–5s 超时 + 原地重试一次，把「一次网络抖动」消化掉，而不是变成一个失败提示。
2. **传输失败用独立错误码**（例如 `NETWORK_UNREACHABLE`），不再冒充 `TRANSLATE_FAILED`，让用户提示与事后取证都能一眼分清「连不上」和「上游翻译坏了」。
3. **不要回退到 0.1.19**：回退不改变网络行为（0.1.19 在同一台机上同样发失败过），只会丢掉 0.1.20 的取证能力。

### 保留不动（本轮已确认全部正常生效）
Fail Closed ✅ / 原文不抢发 ✅ / 草稿保护（`canSafelyRestore` + `translate_failed_restore`）✅ / 幂等与退款 ✅ / 原生输入链 ✅ / `BODY_MISMATCH` 守闸 ✅

### 9b.3 进入 GPT 上游了吗？底层错误是什么？—— **没进上游；是「连接建立超时」**

- **没有进入 GPT 上游**（服务端零预留、零日志）。
- 受控实验（在**应用同款运行时**里，用应用同款 `fetch`）：

| 场景 | 耗时 | `err.message` | `err.cause.code` | `err.cause.message` |
|---|---|---|---|---|
| 不存在的域名 | 2086ms | `fetch failed` | `ENOTFOUND` | `getaddrinfo ENOTFOUND ...` |
| 不可路由地址（连接建立超时） | **10533ms** | `fetch failed` | **`UND_ERR_CONNECT_TIMEOUT`** | `Connect Timeout Error (attempted address: …, timeout: 10000ms)` |

- 观测值 **10433ms / 10640ms** 与 `UND_ERR_CONNECT_TIMEOUT` 的 **10533ms / 10000ms 默认值** 吻合。
- 且 DNS 失败只需 ~2s（不是 10s），连接被拒通常是毫秒级 —— 都与观测不符。

→ **判定：undici 在 10s 内未能与 `pixfanyi.com:443` 建立 TCP/TLS 连接（`UND_ERR_CONNECT_TIMEOUT`）。不是 DNS、不是 TLS 证书、不是连接拒绝、不是 Abort、不是服务端 502。**

旁证（同一窗口内**别的请求是通的**）：`17:19:40`、`17:19:48` 的 `GET /apis/client/session` 均 **200**。即：**应用能连上服务器，但个别新建连接在 10s 内建不起来** —— 间歇性、连接级，而非全断。

### 9b.4 代理问题：翻译 API **没有**走实例的 SOCKS5（已用代码与栈证实）

- 实例 SOCKS5 只写进**线路自己的 session**：`applyTabProxy` → `sessionOf(tab)` = `tab.view.webContents.session`（线路 partition）。
- 翻译走的是**主进程全局 `fetch`**：`guest-inject` → IPC `translate:run` → `requestTranslate()` → `api()` → `main.js:705 fetch(...)`。
- 该 `fetch` 是 **Node 的 undici**（不是 Chromium net）：日志栈里明确是 `at node:internal/deps/undici/undici:13502:13 at async api (.../main.js:703:15)`。
- **undici 不读 Electron 的 session/proxy 配置**，所以实例代理（乃至 `defaultSession` 代理）都不会作用到翻译接口。

→ 之前我提出「SOCKS5 可能是原因」的假设**已被排除**，特此更正。

### 9b.5 字符预留与扣费 —— **没有占用，没有扣费，没有重复扣费**

- `17:14:00–17:25:00` 的 `translation_reservations` = **0 行** → 连预留都没建，谈不上释放。
- 全客户端 `translate_logs` = 0，`translation_usage` = 0（失败单不存在）。
- 对照：0.1.19 的 #417 是 `status=released` / `committed_chars=0` / 15 字符**已退回**。

### 9b.6 缺失的证据（原始日志**无法**还原的部分）

1. **本次请求的 `requestId`** —— 客户端失败路径不记录（只在成功时记），**事后无法补回**。
2. **底层错误码** —— 应用只保留 `err.message`（`fetch failed`），`err.cause`（含 `code`/`message`/attempted address）被丢弃。已核实：全天日志中 `UND_ERR` / `ENOTFOUND` / `ECONNREFUSED` 出现次数为 **0**。
3. **网络层细节** —— 窗口期内没有抓包/`netstat` 快照，无法区分是 IPv4/v6 选路、SYN 被丢、SNAT 端口耗尽还是本机网络。
4. **`rc020-evidence`** —— 本次真机测试**没有跑** `rc020-collect.sh`，因此没有主机侧证据包可交叉验证。

### 9b.7 最小补充取证方案（只在需要"活捉一次"时做）

- **主机侧（零改代码）**：复现瞬间并行抓 `netstat -an | grep 443`、`dig A pixfanyi.com` / `dig AAAA pixfanyi.com`、`traceroute -n pixfanyi.com`，并立刻跑 `bash rc020-collect.sh <label>`。
