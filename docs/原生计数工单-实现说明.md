# Hello Pix 原生计数工单

## 需求口径

Hello Pix 内部直接实现“计数工单 / 新粉 / 重粉”功能，不嵌入、不启动外部计数器软件，也不复用已经下线的 `orders`、`order_details`、`order_fans` 空表。

计数规则：

1. **一个计数工单只属于一个应用**，例如 WhatsApp 工单与 Telegram 工单完全独立。
2. 同一工单可以绑定该应用下的多个接入账号；同一商户的同一个“应用 + 账号”同时只能属于一个进行中的同应用工单。
3. 一条 `conversation` 只贡献一个进粉事件；同一会话发多少消息都不会重复加粉。
   只有账号绑定之后、真实到达的入站消息才能触发；打开会话、出向消息、
   账号绑定前的历史消息和未来时间都不计粉。
4. 同一客户第一次进入计数系统算新粉。
5. 同一客户在同一应用内从另一条会话、另一个账号或另一个商户的计数工单再次出现，算重粉；换一个应用重新算新粉。
6. “今日”按工单自己的 IANA 时区和每日置零时间计算，不跟随后端服务器时区。
7. 计数写入失败不能阻断客户消息接入；同一会话下次上报仍可幂等补记。
8. 计数工单沿用套餐 `clients.counter` 权益；`basic` / `advanced` 默认无权限，`pro` / `solo_monthly` 可用。
9. 客户身份合并后，同一客户会在**每个应用内分别重排**进粉事件：每个应用最早一条为新粉，其余为重粉。
10. 工单产生第一条进粉记录后，业务时区和每日置零时间锁定，避免历史业务日口径漂移。
11. 消息补扫可能乱序到达；每次写入后会按真实 `event_at` 重排，
    保证最早事件始终是新粉，后续事件为重粉并指向最早事件。
12. 客户合并会递归解析最终根客户；已合并客户不能再次形成中间链。
    合并前会保存受影响粉丝、归属、撞单和身份事件快照。
13. 周期重置不删除历史账本：把当前工单出现过的客户写入同商户、同应用底库，
    工单 `cycle_no + 1`，统计从新周期重新开始。新周期内同一会话再次进线可重新
    记一次；若底库命中，则记为 `repeat_type=base`。
14. 对账分享页凭随机 token 访问，可选 scrypt 密码；只返回当前周期指标、
    接粉账号和粉丝明细，不返回商户 ID、商户名或管理配置。

## 数据模型

迁移：`migrations/054_count_tickets.js`。
完整性增强：`migrations/055_count_ticket_integrity.js`。
查重范围与底库：`migrations/056_count_ticket_dedup_scope.js`、
`migrations/057_count_ticket_groups_base.js`。
周期与分享：`migrations/060_count_ticket_share_cycles.js`。

- `count_tickets`
  - 归属商户 `user_id`
  - 名称、计数应用、状态、单日目标、总目标
  - 业务时区、每日置零时间
  - 当前结算周期 `cycle_no`、周期起点 `cycle_started_at`
- `count_ticket_accounts`
  - 工单绑定的平台账号
  - `(user_id, platform, account_key)` 的启用态唯一索引，防止一账号同时进入两个进行中工单
- `count_ticket_fans`
  - 进粉事件账本
  - 保存会话、客户、平台、接入账号、事件时间、业务日、新/重粉类型
  - `(ticket_id, conversation_id)` 唯一，保证会话去重
  - `(ticket_id, cycle_no, conversation_id)` 唯一，保证同一会话跨周期可重新计粉
  - `event_type` / `direction` 记录计粉依据；当前只允许真实入站消息

- `customer_merge_audits`
  - 保存每次客户合并的根客户、操作超管、受影响客户 ID
  - 保存合并前的计数粉丝账本、归属、撞单和身份匹配 JSON 快照

- `count_ticket_shares`
  - 一张工单一条分享记录
  - 只保存 token SHA-256、token 前缀和可选 scrypt 密码哈希
  - 支持停用、到期、访问次数和最近访问时间

所有内容层表都带 `user_id`，并用 `(ticket_id, user_id)` 复合外键绑定工单归属。

## 后端

- `server/repositories/count-ticket-repository.js`：数据访问、统计 SQL、幂等进粉账本。
- `server/services/count-ticket-service.js`：参数校验、绑定账号、新/重粉判定、商户隔离。
- `server/routes/count-tickets.js`：商户端建单、编辑、绑定账号、明细查询。
- `server/routes/admin/count-tickets.js`：超管只读查看。
- `/customer/ingest` 成功写入会话后旁路调用计数；计数异常只记录日志，不影响主链路。
- 客户端把真实消息与“仅打开会话”显式分开；主进程和服务端只让
  `eventType=message / direction=in` 且在账号绑定之后的事件入账。
- 商户接口统一校验 `clients.counter`，无权益返回 `COUNT_PLAN_REQUIRED`。

### 商户接口

```text
GET  /apis/count-tickets
GET  /apis/count-tickets/:id
GET  /apis/count-tickets/:id/fans
POST /apis/count-tickets/save
POST /apis/count-tickets/accounts/save
POST /apis/count-tickets/accounts/remove
GET  /apis/count-tickets/available-accounts
GET  /apis/count-tickets/:id/share
POST /apis/count-tickets/:id/share
POST /apis/count-tickets/:id/share/revoke
POST /apis/count-tickets/:id/reset-cycle
```

公开分享页读取接口：

```text
POST /apis/public/count-ticket-shares/view
```

token 和密码都放 POST body，不进入 URL/query 访问日志。密码错误返回
`403 COUNT_SHARE_PASSWORD_BAD`，避免通用前端拦截器把它当作用户掉线。

### 超管接口

```text
GET /apis/admin/count-tickets
GET /apis/admin/count-tickets/:id
GET /apis/admin/count-tickets/:id/fans
```

超管接口使用 `admin.data.customers` 能力，普通 operator 不可见。

## 前端

- 商户：`#/count/tickets`
- 分享：`#/share/count/:token`
- 超管：`#/admin/count-tickets`

商户页支持新建/编辑工单、绑定/停用账号、命名分组、指定工单查重、底库去重、
今日与累计新/重粉、疑似老粉、账号拆分统计、粉丝明细、周期重置和只读对账分享。
绑定账号必须已由客户端上报，页面不再允许手工编造账号。

注意：当前桌面端上报的 `accountKey` 是客户端接入账号 slug，不等同于
WhatsApp/Telegram 的真实聊天号码，因此页面统一称为“接入账号”。

## 回滚

```bash
node scripts/migrate.js down 1
```

`060` 的 down 会删除分享表并撤掉工单周期字段，但**保留**
`count_ticket_fans.cycle_no`。原因是同一会话可以跨周期重新计粉，直接恢复旧
唯一索引会与历史数据冲突；删除历史账本不可接受。回滚后的旧版新增事件仍按
`cycle_no=1` 做会话幂等保护。若需要精确恢复升级前统计口径，必须使用升级前
数据库快照。
