## 3. 本版内容（相对 0.1.10）

### 3.1 群聊「翻译通道 = 手动」失效 → 非预期扣费（P0）

**现象**：顶部已设「群组翻译 = 手动」，进群聊后消息仍自动出现译文，余额在掉。

**根因（两条叠加）**：

1. `isGroupChat()` 只认 Telegram 的 header 文案
   （`/members|subscribers|位成员|位订阅|群组/i`），**WhatsApp 群聊全被判成一对一会话**，
   于是「群聊手动模式」这条规则根本没生效。
2. 打开会话时满屏**历史消息**没有分流，自动模式下被整批翻译。

**修法**：

- 群聊判定改用**结构性证据**：WhatsApp 把会话类型编进了消息 `data-id`
  （`true_<...>@g.us_<id>` = 群、`...@c.us...` = 个人），且**只在 `#main`（会话区）里扫** ——
  左侧会话列表里混着别的群，扫它会把每个一对一会话都误判成群。
- 引入 `createHistoryGate()` **基线**：打开会话时把既有消息登记为「历史」，
  只有基线**之后**新到达的消息才允许自动翻；时间维度用 `data-pre-plain-text`
  的真实时间戳兜底。
- 所有翻译决策收敛到 `MessageParser.messageAction()` **唯一出口**：
  群聊手动模式 / 历史消息一律只给「译」按钮，**0 次 API 调用**。

**顺带修掉一个会误扣费的隐藏缺陷**：`messageTime()` 原先只用 `closest`（向上找），
而 WhatsApp 的 `data-pre-plain-text` 挂在 `[data-id]` 行的**后代**上 ——
时间戳恒为 `null`，**滚动补加载出来的历史消息一条都认不出来**，自动模式会把它们全翻了。
现在自身/后代/祖先三个方向都找。

### 3.2 消息提取把 UI 文案当正文送进翻译（P0）

**现象**：时间（`3:25 PM`）、已读图标（`wds-ic-read`）、`View group`、
链接预览卡片的标题与元数据、发信人名、`Download` 按钮都被当成待翻正文 ——
既污染译文，又按这些字符**多扣费**。

**根因**：把消息容器的 `innerText` / `textContent` 整块当作翻译输入。

**修法**：结构化解析 `MessageParser.parseForTranslation()`：

- 正文只取 `span.selectable-text`，且排除预览卡片与引用块；
- 找不到正文就返回**空串**，**绝不回退到 `innerText` / `textContent`**；
- 纯 URL 消息**不调 API**；「文字 + URL」只翻文字，URL 用 `[[n]]` 占位符掩码保护后
  原样拼回（即使模型弄丢 URL 也能还原）。

### 3.3 译中占位符 `[正在翻译中...]` 被真实发送（P0）

**现象**：真实发出去过「哈喽你好[正在翻译中...]」。

**修法**：

- 发送路径硬闸 `guardBusySend()`（capture 阶段拦 keydown / beforeinput / click）；
- 写回输入框之后、点发送之前**再复核一次**；
- 主进程 `stripBusyMarks()` **独立再拦一次**（不信任渲染进程），
  且必须在进缓存、发上游**之前**执行。

### 3.4 计费归因：`translate_logs.trigger`（migration 042）

`translate_logs` 原先只有 user / sub_account / engine / chars / 时间，**没有任何一列**
能回答「这次是手动触发还是自动触发」。用户看到余额少了，事后审计只能猜。

新增 `trigger`（`varchar(40) NOT NULL DEFAULT ''`），客户端在发起翻译时声明：

| 值 | 含义 |
| --- | --- |
| `manual_click` | 用户点了「译」按钮 / 触发发送翻译 |
| `auto_receive` | 扫描到消息后自动翻（**群聊手动模式下必须为 0 条**） |
| `manual_send` | 发送方向的手动翻译 |
| `retranslate` | 重新翻译 |
| `''` | 旧版客户端、服务端内部调用（未声明） |

值域用 CHECK 收口（客户端可控输入）；默认 `''` 而非 NOT NULL 报错 ——
存量行没有来源，回填不了也不该伪造。审计入口查询走部分索引
`translate_logs_trigger_created_idx (trigger, created_at DESC) WHERE trigger <> ''`。

### 3.5 代理实例级隔离（另一条 P0 线）

**问题一：新建应用错误继承上一次代理。**

根因不是「哪里复制了一个变量」，而是**代理被当成了「新建默认模板」的内容**：
`app-presets.json` 存的是**整份**标签页设置（含全部代理字段），
点「新增应用」拉预设 → `fillAddForm` 把预设并进表单默认值 → 新实例带着上一个实例的代理出生。

还有一条更隐蔽的泄漏：`app:rename` 的兜底值是 `tab.settings` ——
**给实例改个名字**，那条实例正在用的代理就被写进了模板。

修法：新增 `desktop/proxy-isolation.js` 作为「代理字段全集 + 直连初值」的唯一定义，
模板的**写 / 读 / 改名**三个口子全部先 `stripProxyFields()`；
渲染层 `fillAddForm` 的代理字段只认直连初值，不再读任何继承来源。
读取侧先摘再解密（`unsealSettings(stripProxyFields(...))`），
模板里的密码**连解密都不会走到**，同时**自愈**旧版本已写进磁盘的带代理模板。

**问题二：实例必须完全独立。**

审计结论是这一层**本来就设计对了**，本轮把它固化成回归测试：
`socksRelays` 按 `tab.id` 存、`proxyAuthByWebContents` 按 `webContents.id` 存，
**无** `currentProxy` / `lastProxy` / `sharedProxy` / 全局 relay / 共享 auth 缓存。

**刻意没动** `open-apps.json`（各实例自己的设置）—— 那里**必须**保留代理，
否则重启后 A 恢复不了 X。隔离的目标是「实例之间」与「模板到实例」，
不是「实例到磁盘」。

## 6. 回滚

```sql
UPDATE client_releases SET enabled = false, updated_at = NOW() WHERE version = '0.1.11';
UPDATE client_releases SET enabled = true,  updated_at = NOW() WHERE version = '0.1.10';
```

回滚只是让**更新提示**回到 0.1.10，**不会**把已经装成 0.1.11 的用户变回去。
真要让用户退回，得再发一个版本号更大的包（客户端只认更大的版本号）。

> ⚠️ **本次回滚的代价比平时大**：0.1.10 正是「群聊手动模式会扣费 + UI 文案进翻译 +
> 译中占位符会被真实发送」这三个 P0 的版本。回滚到 0.1.10 等于把这三条重新放回线上。
> 若回滚原因是 0.1.11 引入了新问题，应**优先热修复并升到 0.1.12**，而不是回退到 0.1.10。

**迁移 042 的回滚**（仅在你确定要放弃计费归因时）：

```bash
npm run db:rollback          # 042 有 down：删索引 → 删 CHECK → 删列
```

> 042 是**纯增量**（加列 + 加约束 + 加索引），对既有查询无影响；
> 且服务端代码写入 `trigger`，**先回滚迁移会导致翻译日志写入失败**。
> 顺序必须是：先回滚服务端代码，再回滚迁移。生产回滚前先备份。
