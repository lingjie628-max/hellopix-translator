# GPT 与 DeepSeek 真实性能对比报告

**轮次**：0.1.19 — WhatsApp 发送翻译性能专项优化
**日期**：2026-10-08
**范围**：只做性能测量与优化，不新增功能、不发布安装包
**结论先行**：**DeepSeek 明显更快**。端到端 P50：DeepSeek **1.34s** vs GPT **2.06s**（快 719ms / 35%）。
客户端侧已从 508ms 压到 **71ms**，占比降到 3–5%，**不再是瓶颈**；现在 95% 的时间花在厂商模型往返上。

### 关于 `trigger` 的核实结果（用户要求核实项）

`trigger: bench_live` **生产不支持**：

```javascript
// server/services/core-service.js:29
const TRIGGER_VALUES = ['manual_click', 'auto_receive', 'manual_send', 'retranslate']
// server/services/core-service.js:493-495  不在白名单 → 静默记成空串（不报错）
// migrations/042_translate_log_trigger.js:40-41  CHECK 约束兜底
```

为**不修改生产配置**，改用白名单内的 `manual_send`——即客户端真实点发送时的值，语义最贴合本次被测链路，无需任何生产改动。探针已加预检：传白名单外的值会**在发请求之前**直接中止。

### 计费口径（关键发现）

服务端按 **CJK 字符计 2、其余计 1** 收费：

```javascript
// server/services/translation-provider.js:41-47
for (const char of String(text || '')) count += /[\u4e00-\u9fff]/.test(char) ? 2 : 1
```

这导致一个**预算冲突**：40 次请求 × 约 33 计费字符 ≈ 1300 字符，会击穿 600 字符预算（原先 dry-run 的"560 字符"是按字面长度算的）。已改用**计费字符**口径计数，并把样本句缩短到 5 个汉字，使 40 次落在预算内。

| 阶段 | 含义 | 旧 P50 | 新 P50 | 变化 |
|---|---|---:|---:|---:|

## 六、加速安全性证明（不放松任何一道闸）

`verify-settle-safety.js`（真 Electron + 生产 preload）故意制造失败模式：
**13 / 13 项通过。**

| 场景 | 结果 |
|---|---|
| 正常路径（5 次） | 每次都恰好发 1 条，内容 = 译文；沉降 63–67ms |
| **迟到漂移**（插入正确，150ms 后编辑器改回原文） | 绝不泄漏原文；要么正确译文、要么一字不发 |
| **提前漂移**（插入后 40ms 就改回，早于 60ms 下限） | `LEXICAL_SETTLED` 判不等 → 重试 → **一字不发**（fail-closed） |
| 原生插入被编辑器拒绝 | 一字不发 + 留下 `BODY_MISMATCH` 取证 |
| 译文里混进占位符 | 一字不出网 |
| 翻译期间用户打了新草稿 | 不发送，且用户草稿**一字未被覆盖** |

**为什么可以缩短而不降低安全性**：缩短观察窗只影响"确认得多早"，不影响"不合格会不会被拦"——
发送前仍有一道**独立**的 `sendableBody()` 闸（`FINAL_TEXT_VALIDATED`），它在 `fireSend()` 前一行**同步**执行，
读的是**此刻的 DOM**，与触发发送之间没有任何 `await` 间隙。不一致即 fail-closed。
`BODY_MISMATCH` / `FINAL_TEXT_VALIDATED` **一行未删**。

## 八、结论：谁更快、瓶颈在哪、还能优化多少

### 谁更快

**DeepSeek 全面更快。**

| | DeepSeek | GPT | 差距 |
|---|---:|---:|---:|
| P50 | 1266ms | 1985ms | DeepSeek 快 **719ms（36%）** |
| P95 | 1538ms | 2892ms | DeepSeek 快 **1354ms（47%）** |
| 抖动（max−min） | 590ms | 2545ms | GPT 稳定性差 **4.3 倍** |

GPT 不仅更慢，**波动也大得多**——P95 是 P50 的 1.46 倍，最慢一次 3832ms。
而 DeepSeek 的 P95/P50 只有 1.21，节奏稳定。对高频客服场景，**稳定性比均值更重要**。

### 瓶颈在哪

**瓶颈已经从客户端转移到厂商模型往返。**

| 构成 | DeepSeek | GPT |
|---|---:|---:|
| 厂商模型 + 服务端 | 1266ms（**94.7%**） | 1985ms（**96.6%**） |
| 客户端（优化后） | 70ms（5.3%） | 70ms（3.4%） |

客户端内部剩余的 70ms 里，**69ms 是沉降确认窗**（下限 60ms + 轮询一拍），
其余六个阶段合计 < 2ms。

### 还能优化多少

**客户端侧：几乎没有空间了。**

- 理论极限：把下限从 60ms 压到 ~20ms，再省约 **45ms**。
- 收益：占 DeepSeek 总时长 **3.4%**、占 GPT **2.2%**。
- 代价：沉降确认余量被削薄，而"迟到漂移"正是 0.1.18 那个 P0 的成因。
- **结论：不值得。** 建议保持 60ms。真要更快，应改为**事件驱动**（监听编辑器的
  原生 `input` 事件做确认）而非继续压时间常数——但那是下一轮的事，且需要真机先验证
  WhatsApp 编辑器到底会不会派发可监听的事件。

**模型侧：这才是真正的杠杆。**

1. **换更快的模型**（GPT P50 1985ms 意味着约 2s 打底）——收益可达数百毫秒到 1 秒级。
2. **就近部署 / 更优线路**——当前到 `pixfanyi.com` 的 TLS 握手 + TTFB 约 310ms 是纯网络成本，
   占 DeepSeek 总时长的 24%。
3. **流式首字**——如果 UI 能在首个 token 到达时就展示进度，主观等待感会显著下降
   （不改变总耗时，但改变体验）。
4. **服务端内部开销未拆解**：`/translate/run` 内部有「预留事务 → 调上游 → 结算事务」
   两段 DB 往返，这部分混在 1266/1985ms 里。要精确定位需要**服务端埋点**——
   本轮明确限定"不修改生产"，故未做。这是下一个可深挖的点。

### 一句话

本轮把客户端侧从 **508ms 砍到 71ms（−86%）**，且**没有放松任何一道安全闸**（13 项安全证明 + 全量回归 0 失败）。
优化后 DeepSeek 的端到端 P50 已进入 **1.34s**，稳定达标；GPT 因模型本身约 2s 打底，P50 卡在 2.06s，
**要让它达标必须从模型/线路侧下手，继续榨客户端没有意义。**
