# Hello Pix P0/P1 安全加固方案

## 范围

- 安全优先，修复可利用漏洞、越权、余额一致性和关键稳定性问题。
- 当前生产入口仍使用内存 Mock；本轮不伪造数据库和支付实现，而是默认关闭演示能力并阻止生产启动。
- 真实数据库、支付回调验签、安装包签名与正式自动更新作为独立上线前项目。

## 实施顺序

1. 建立生产 fail-closed 门禁，演示账号、验证码回显和模拟支付仅在显式测试模式启用。
2. 收紧 Electron 导航、URL、IPC、权限和页面脚本隔离边界。
3. 避免密码、代理凭据和聊天译文明文离开主进程或长期落盘。
4. 修复 API mass assignment、多租户缓存、并发扣费、暴力破解与 RBAC。
5. 移除 Vue HTML 弹窗注入面。
6. 以攻击回归测试、安全测试、构建和 Electron 冒烟作为发布门禁。

## 关键安全不变量

- 远程页面不能获得通用主进程能力。
- 生产环境不能加载内存演示后端、默认账号或模拟支付。
- 用户输入不得覆盖资源归属和不可变标识。
- 任意并发下字符余额不得为负，失败请求不得扣费。
- API、应用页、下载和更新 URL 必须符合显式信任策略。

## 技术方案概述

本方案回答“Hello Pix 是否可以不使用 Electron”。结论是**技术上可以，但不能仅替换外壳**。当前客户端的核心竞争力由 Chromium 能力直接支撑：

- 同时承载多个 WhatsApp、Telegram、LINE、Instagram 等第三方页面。
- 每个账号使用独立持久化分区，Cookie、LocalStorage、IndexedDB 和缓存互不共享。
- 每个实例独立代理，并支持 HTTP Basic、认证 SOCKS5 和 WebRTC 泄漏防护。
- 向第三方页面注入翻译桥，读取 DOM、拦截发送、回填译文和处理语音。
- 截图/图片读取、剪贴板图片、通知、下载、后台托盘和自动更新。

当前代码规模：

| 项目 | 规模 |
|---|---:|
| `desktop/main.js` | 4562 行 |
| `desktop/guest-inject.js` | 5632 行 |
| 渲染层 JavaScript | 约 3200 行 |
| IPC handler | 56 个 |
| `WebContentsView` 引用 | 25 处 |
| `partition` 引用 | 36 处 |
| 代理模块 | 7 个 |

因此路线必须分为：

1. **短期修复**：保留 Electron，升级受支持内核，修好 macOS entitlement/签名和 Windows 签名。
2. **战略去 Electron**：先做能力验证，再迁移；推荐 Tauri v2 与 CEF 两条候选路线，不选普通 PWA。

## 技术选型

| 方案 | 浏览器内核 | 多账号隔离 | 每实例代理 | 页面注入 | 迁移成本 | 结论 |
|---|---|---|---|---|---|---|
| 升级 Electron | Chromium，与应用一起升级 | 强 | 强 | 强 | 低 | **立即修复首选** |
| Tauri v2 | Windows WebView2 / macOS WKWebView | 支持独立 profile/data store | 官方支持 webview 级代理，但平台能力有差异 | 可行，需按 WebKit/Chromium 两套适配 | 中高 | **去 Electron 的首选 POC** |
| CEF 原生壳 | Chromium | 强 | RequestContext 级控制 | 最接近现有 Electron 行为 | 高 | **兼容性优先的保底方案** |
| Qt WebEngine | Chromium | Profile 级隔离 | 需网络层定制 | 可行 | 高 | 可作为 CEF 替代，但团队门槛更高 |
| Swift/AppKit + C#/WPF 双原生 | WKWebView / WebView2 | 可实现 | macOS 每实例代理较难，需 helper | 两套实现 | 极高 | 不建议当前阶段采用 |
| PWA / 浏览器扩展 | 用户浏览器 | 受浏览器限制 | 不可控 | 权限受限 | 低 | **不满足产品要求** |

### Tauri v2

官方已支持单窗口多 webview、webview 级数据目录/profile，以及 webview 级 `proxyUrl`。这使它成为“不再打包 Electron”时最有现实可能的路线。

风险：

- Windows 使用 WebView2，macOS 使用 WKWebView，第三方站点 DOM 和媒体能力可能不一致。
- `whatsapp-direct-ptt.js` 依赖 WhatsApp 页面内部模块，WKWebView 下必须重新验证。
- macOS 代理能力带平台版本和 feature flag，认证 SOCKS5 仍需本地中继。
- WKWebView 的脚本注入、隔离世界、资源读取和权限模型与 Chromium 不同。

### CEF

CEF 能保留 Chromium 的渲染、注入、网络上下文和多 profile 语义，是从现有 Electron 迁移时功能兼容风险最低的方案。

代价：

- 主进程、窗口、IPC、更新器和打包链路都要重写。
- 需要长期维护 C++/Rust 原生壳和 Chromium 升级。
- 包体与攻防面仍然接近 Chromium 浏览器。

### 最终建议

- 如果只是解决当前闪退：**不要迁移框架，先发修复版 Electron**。
- 如果老板明确要求彻底移除 Electron：先做 2 周 Tauri POC。
- POC 任一核心能力不达标，就转 CEF，不用 Flutter/MAUI/PWA 硬扛。

## 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 是否立刻迁移 | 否 | 当前故障主要来自过期 Electron 和签名链路，迁移不能更快止血 |
| 去 Electron 首选 | Tauri v2 POC | 保留现有 Web UI，包体和维护面小于 CEF |
| POC 失败后的方案 | CEF | 最接近现有 Chromium 行为，功能回归风险最低 |
| 是否使用系统共享 Cookie | 否 | 会导致账号串号，必须一账号一 Profile |
| 是否把代理当全局设置 | 否 | 每条线路必须独立出口，禁止静默回退直连 |
| 页面注入 | 按内核分适配器 | WebKit 与 Chromium 的隔离世界和页面世界不同 |
| 更新器 | Native Core 实现 | 不沿用 Electron 自动更新链路，重新做签名校验与回滚 |

## 迁移门槛

Tauri POC 必须同时通过以下验收，否则不进入正式迁移：

1. 同一窗口内创建至少 6 个实例。
2. 两个 WhatsApp 账号同时在线，Cookie 与会话完全隔离。
3. 两个实例使用不同代理，DNS/WebRTC/IP 出口检查通过。
4. 认证 SOCKS5 可用，失败时禁止回退直连。
5. 收发文本翻译、消息回填、幂等键验证。
6. 语音导入、原生语音发送和音频权限验证。
7. 截图、图片读取、剪贴板图片验证。
8. 后台运行、托盘唤起、窗口恢复和代理分区的数据迁移验证。
9. macOS Developer ID 签名、公证；Windows Authenticode 签名。
10. 自动更新验签、失败回滚、双版本共存升级验证。

## 实现计划

1. **第 0 阶段（立即）**：保留 Electron，升级到受支持版本并修好签名/entitlement；发布可回滚的修复包。
2. **第 1 阶段（1～2 周）**：Tauri v2 最小 POC，只做多 webview、独立 profile、独立代理、一次翻译注入、一次文本发送。
3. **第 2 阶段**：补语音、图片、剪贴板、通知、下载、托盘和自动恢复。
4. **第 3 阶段**：迁移账号配置、窗口恢复、代理配置和诊断日志。
5. **第 4 阶段**：双应用 ID 并行安装，选择小范围用户灰度，服务端兼容两种客户端。
6. **第 5 阶段**：达到门槛后切正式版；Electron 版至少保留两个版本的下载与回滚通道。

## 风险与结论

最大风险不是“Tauri 能不能开窗口”，而是**第三方站点在不同 WebView 内核上的行为差异**，以及语音内部模块、代理认证和页面注入的回归。

因此：

- “不用 Electron”可以作为中期架构目标。
- 它不能替代当前闪退的紧急修复。
- 当前阶段直接全量重写，会把可快速修复的线上事故扩大成一场迁移事故。

## 2026-11-15 快速语音 PTT 实施结果

KingWorld 2.67.5-beta 已静态确认为“WhatsApp Web 内部模块直发 PTT”，不是
Cloud API，也不是本地 CSS 假气泡。本项目已按相同原理实现独立高风险入口：

```text
外部音频
→ 单声道 OGG/Opus
→ 64 段振幅 waveform + duration
→ WAWebMediaOpaqueData.createFromData
→ WAWebPrepRawMedia.prepRawMedia({ isPtt: true, precomputedFields })
→ prep.sendToChat({ chat, options })
```

关键实现：

- `desktop/src/translate/whatsapp-direct-ptt.js`：页面世界直发；
- `desktop/src/translate/voice-opus-encode.js`：主进程 WASM OGG/Opus 编码；
- `desktop/guest-inject.js`：受限 `window.postMessage` 转码桥；
- `desktop/src/ipc/translate.js`：`trustedTabSender` + 单实例并发限制。

当前官方 WhatsApp 不再暴露经典 Webpack require，而是使用 Meta
`requireLazy`。实现优先加载：

- `WAWebChatCollection`
- `WAWebMediaOpaqueData`
- `WAWebPrepRawMedia`

同时保留旧 Webpack 能力发现作为兼容路径。找不到任一模块即失败关闭，不降级
成普通文件上传，也不自动重试。

真机结果：

- 1 秒测试：原生头像、波形、`0:01`，服务端确认成功；
- 25.7535 秒测试：原生波形、`0:25`，服务端确认成功；
- 25.7535 秒本地 WASM Opus 编码约 0.2 秒；
- 解码、编码到 WhatsApp 确认总计约 2.08 秒，无法硬保证所有网络
  和所有时长都在 1 秒内完成。

头像不是逐条嵌入的图片。客户看到的是该 WhatsApp 账号的服务端资料头像；要
显示特定 Logo，必须设置对应账号的资料头像。

转码依赖：

- 使用 `opus-recorder@8.0.5`（MIT）内置的 libopus/speexDSP WASM；
- 不再随安装包分发含 `--enable-gpl --enable-nonfree` 的原生 FFmpeg；
- 同一编码器在 macOS x64/arm64 与 Windows x64 上均可运行。

风险：

- 使用 WhatsApp Web 非公开内部模块，可能违反平台条款并触发账号风控；
- WhatsApp 更新可能改变模块 API；
- 因此「快速语音」保留为独立入口，原「导入语音」虚拟麦克风入口不删除。

## 2026-11-15 18:14

# 客户侧可见的“账号头像 + 自动波形”语音气泡

## 需求澄清

目标不是在本机画一个乐观占位气泡，而是让**客户收到的消息本身**显示为：

- 该 WhatsApp 账号的头像或品牌 Logo；
- 麦克风语音标识；
- 自动生成的音频波形；
- 播放按钮、真实时长和已发送状态。

这意味着修改对象是**远端消息的渲染类型和账号资料**，不是当前 Electron 页面里的
CSS。客户手机上的 WhatsApp 不会执行我们的页面脚本，也不会接收我们本地 DOM
的样式。

## 当前项目边界

当前三个 WhatsApp 入口：

- WhatsApp 绿色版；
- WhatsApp 多功能版；
- WhatsApp 商业版；

全部加载 `https://web.whatsapp.com/`。所谓“商业版”是用手机 WhatsApp Business
App 扫码登录网页版，不等于 Meta WhatsApp Business Cloud API，也没有 WABA ID、
Business Phone Number ID 或 Graph API Token。

因此当前系统可以生成原生 PTT（波形、麦克风、时长），但：

- 不能把任意本地图片作为某一条消息的气泡头像发给客户；
- 不能在客户侧伪造一套 WhatsApp UI；
- 客户看到的头像仍由该 WhatsApp 账号在服务端的资料决定；
- 发送速度仍受网页版原生录音链路约束。

## 可行方案

### 方案 A：Meta WhatsApp Cloud API（推荐，官方）

使用 Graph API 发送 `audio.voice=true` 的 OGG/Opus 语音消息。官方语音消息会
展示业务号码对应的资料头像、麦克风图标和原生播放波形。

自动识别账号头像的落地方式：

1. 本地读取账号当前头像，仅用于界面匹配和运营识别；
2. 每个 Cloud API 业务号码在 Meta 后台配置自己的 Business Profile 图片；
3. 发语音消息时按账号映射到对应的 `phone_number_id`；
4. 客户侧显示的就是该业务号码的服务端资料头像。

限制：

- 必须已有 WABA、业务号码、永久 Token；
- 一个号码只有一个业务资料头像，不能对每条消息临时换头像；
- 现有扫码登录的个人/商业 App 账号不能直接复用；需要迁移或单独接入 API 号码；
- 25 秒小文件上传通常可以做到数秒内完成，但“严格 1 秒”仍受网络和 Meta 处理影响。

### 方案 B：Baileys/WhatsApp Web 协议直发 PTT（非官方）

可以用 `sendMessage(..., { audio, mimetype: 'audio/ogg; codecs=opus', ptt: true })`
直接上传语音，不再等待网页版实时录音。部分实现还可显式传 waveform。

限制：

- 属于非官方协议，封号和兼容性风险明显高于网页版 UI 操作；
- 不能共享当前 WebContentsView 的扫码会话，需要重新配对 Baileys 设备；
- 头像仍由账号服务端资料决定，不能任意替换成客户端图片；
- 当前项目明确避免访问内部 Store/协议，采用此方案需要单独风险授权。

### 方案 C：只改当前软件 UI（不满足客户侧要求）

可以识别账号头像并画一个漂亮的气泡，但只在操作员电脑上可见。客户收到的仍是
WhatsApp 服务端生成的消息类型，因此不满足“客户看到的也是那种样式”。

## 推荐决策

如果目标确实是客户侧头像 + 原生波形，且希望速度从 25 秒降到数秒：

1. **新增 WhatsApp Cloud API 通道**，与现有网页版多开并存；
2. 后台建立 `accounts -> WABA phone_number_id / token / profile` 映射；
3. 客户端选择外部音频后，仅做本地解码、时长与波形预处理，然后上传 API；
4. 客户侧样式完全交给 WhatsApp 官方渲染；
5. 网页版入口继续保留，但在无法快速发送时明确标记“网页版原生录音，需实时等待”。

如果客户要求“严格 1 秒内已经收到”，Cloud API 也只能作为目标，不能由客户端
单方面保证；需要实测目标服务器到 Meta 的上传和确认耗时。

## 待确认

要进入代码实现，必须先确认账号类型：

- 是否已有 WhatsApp Business Cloud API 的 WABA / 业务号码 / 永久 Token；
- 客户看到的头像是否必须与账号当前 WhatsApp 头像完全一致；
- 是否接受为快速语音单独使用 Cloud API 业务号码；
- 若不接受，是否明确接受 Baileys 非官方协议风险。

# 长语音“约 1 秒完成发送”的方案设计

## 需求拆解

必须区分两个指标：

1. **用户等待时间**：从选择音频到界面显示“已提交”，目标约 1 秒；
2. **真实送达时间**：WhatsApp 真正完成编码、上传、服务端确认并出现已发送勾。

现有安全方案把外部音频作为虚拟麦克风交给 WhatsApp Web 自己的录音 UI。
WhatsApp 录音按真实时间推进，因此 25 秒音频必须录约 25 秒。这个等待不是
本地转码慢，而是宿主录音链路的固有约束。

## 方案对比

| 优先级 | 方案 | 用户等待 | 真实发送 | 风险/前置条件 |
|---|---|---|---|---|
| 1 | 乐观 UI + 后台队列 | 约 0.1–1 秒看到“发送中/已提交” | 后台按真实时长完成，随后替换成“已发送” | 仍需等待真实时长，但不再阻塞前台；最符合现有架构 |
| 2 | Meta WhatsApp Cloud API `voice:true` | 通常约 1–数秒 | 官方 API 直接上传 OGG/Opus 语音 | 必须有 WABA、Business Phone Number ID、永久 Token；不能复用当前个人 Web 登录号 |
| 3 | Baileys `ptt:true` 直接上传 | 通常约 1–数秒 | 桌面协议直接发 PTT | 非官方协议，封号与版本兼容风险高；不能复用当前 Web 会话，需要重新配对 |
| 4 | 只改 CSS/本地假气泡 | 立即可见 | **没有真实发送** | 对方仍会看到普通文件或收不到，不能作为修复 |
| 5 | 继续前台真实录音 | 音频多长等多久 | 安全、真实 | 当前 1.3.8 实现；长音频体验差 |

## 推荐方案：乐观 UI + 后台发送队列

### 表现层

用户选择音频后：

1. 100ms 内读取文件名、时长和波形摘要；
2. 立即在原聊天插入仅本机可见的占位气泡，显示头像、波形、时长和
   “发送中”；
3. 用户可以立刻切会话或继续工作；
4. 后台发送完成后，占位气泡变为真实的 WhatsApp 消息并显示已发送勾；
5. 失败时显示“发送失败 · 重试/取消”，绝不显示假勾。

### 业务层

新增一个按聊天和账号隔离的后台任务队列：

```
queued -> preparing -> recording -> uploading -> sent
                                      \-> failed -> retry/cancel
```

任务必须固定记录 `tabId`、账号分区、聊天身份、文件哈希和目标语言。后台执行
期间即使用户切换聊天，也只能向任务创建时绑定的会话发送。队列默认并发 1，
防止多个 WhatsApp 原生录音互相抢麦克风状态。

### 数据与生命周期

任务对象至少包含：

```text
id
tabId
chatKey
fileName
fileHash
durationMs
waveformDigest
state
attempts
createdAt
lastError
```

任务只保存在本地内存和短期持久化队列中，不上传原始音频。应用退出时，
`queued/preparing` 任务可恢复；`recording/uploading` 任务必须标为中断，
由用户明确重试，避免重复发送。

## 能保证什么

- 前台 1 秒左右得到明确反馈；
- 不会长时间卡住输入区；
- 最终勾必须来自 WhatsApp 的真实发送结果；
- 支持任意 WhatsApp 允许的 PTT 时长，不受本地前台等待影响。

## 不能保证什么

乐观 UI 只能缩短“用户等待”，不能让 WhatsApp Web 的真实录音在上传前用
0 秒完成。如果验收标准是“点击后 1 秒内对方已经收到且已发送勾出现”，
必须采用方案 2 或方案 3，不能靠 UI 达成。

若选择 Cloud API，还需要提供独立的 WABA/Token/业务号码；若选择 Baileys，
需要明确接受非官方协议与封号风险，并为每个账号重新建立 Baileys 会话。

## 实施顺序

1. 增加本地任务队列和状态机；
2. 增加仅本机可见的乐观语音占位气泡；
3. 将现有虚拟麦克风导入改为后台任务执行；
4. 用真实 25.7535 秒 OGG 验证：前台反馈 < 1 秒、后台最终生成原生 PTT；
5. 验证切会话隔离、失败重试、应用退出恢复和重复发送保护。

# PostgreSQL + Redis 基础设施与 Schema 方案

## 目标与边界

- 使用 PostgreSQL 作为业务事实源，Redis 仅承载会话、限流、缓存和短期协调数据。
- 使用 CommonJS 和 `node-pg-migrate` 管理可回滚 Schema。
- 本阶段不修改 `server/index.js`、安全模块、路由或 Mock；生产入口原有门禁继续生效，
  直至 API 完成真实数据层与支付验签集成。
- 迁移只预置套餐、引擎和非敏感设置，不创建任何默认用户或管理员。

## 数据模型

- 商品配置：`packages`、`engines`、`package_engines`、`app_settings`。
- 身份体系：`users`、`sub_accounts`、`admins`；密码只允许 scrypt 哈希格式，
  用户名和邮箱使用大小写不敏感唯一索引。
- 业务记录：`orders`、`recharges`、`translate_logs`。
- 余额一致性：`translation_reservations` 以用户和幂等键唯一约束完成字符预占，
  状态约束覆盖预占、提交、释放和过期；翻译日志可关联预占记录。
- 安全追踪：`login_logs`、`audit_logs` 保存主体、IP、资源和请求信息，并对常用
  时间范围和主体查询建立组合索引。

所有余额、计数和金额都有非负约束；外键明确采用 `RESTRICT`、`CASCADE` 或
`SET NULL`；子账号相关业务记录使用 `(parent_id, id)` 复合外键防止跨租户关联。

## 运行与安全

- `server/config.js` 在生产环境强制要求带凭据的 `DATABASE_URL` 和 `REDIS_URL`，
  拒绝示例密码；非回环 PostgreSQL 禁止关闭 TLS。
- PostgreSQL 使用有上限的连接池、连接超时、空闲超时和语句超时；事务帮助器保证
  异常回滚。Redis 延迟连接并设置命令超时、有限请求重试和统一键前缀。
- Docker Compose 中 PostgreSQL 与 Redis 仅绑定本机，启用持久卷、健康检查和
  Redis AOF。systemd 在启动 API 前自动执行迁移。
- 管理员由独立脚本显式创建，用户名、昵称、角色和强密码均必须提供；脚本不覆盖
  已存在账号，密码文件优先于环境变量。

## 后续集成

1. 将会话、限流和翻译缓存从进程内存迁移到 Redis。
2. 将注册、账户、工单、充值和翻译扣费路由迁移到 PostgreSQL 事务。
3. 在支付回调中以 `idempotency_key` 和厂商交易号双重去重。
4. 完成真实支付验签及回归测试后，再评估移除生产入口门禁。

# PostgreSQL + Redis 正式核心后端实施结果

## 最终结构

- `server/index.js` 负责运行模式选择、依赖探活、迁移版本门禁、启动和优雅关闭；
  生产环境以及 `PIX_USE_PERSISTENT_BACKEND=1` 只注册正式 API，不加载 Mock。
- `server/routes/`、`server/services/`、`server/repositories/` 分别承载接口契约、
  业务事务和参数化数据访问；未迁移接口统一返回 `503 / NOT_MIGRATED`。
- PostgreSQL 保存身份、套餐、工单、充值记录、翻译日志、预留账本和审计日志；
  Redis 保存会话、主体会话索引、限流、验证码、分享授权和租户隔离翻译缓存。

## 一致性设计

- 翻译先在短事务内锁定账号、扣减余额并创建幂等 reservation，再在事务外调用
  翻译通道，最后以幂等事务提交日志或退款。
- 未接线的翻译通道在扣费前返回 `ENGINE_NOT_CONFIGURED`，不会使用演示翻译收费。
- 超时 reservation 由启动后的定时 reconciliation 使用 `FOR UPDATE SKIP LOCKED`
  领取并退款，避免多实例重复补偿。
- 主子账号字符转移固定先锁主账号、再锁子账号；余额更新带非负条件，转移记录和
  两侧余额处于同一事务。
- 翻译缓存按 `main|sub + account id` 隔离；缓存命中仍创建 reservation 并计费。

## 安全边界

- 生产环境强制 PostgreSQL/Redis 凭据、远程 TLS、HTTPS 来源和本机监听，并拒绝
  所有 demo 开关。
- Web、Client、Admin 登录同时按 IP 和账号限流；分享密码与翻译也采用双维限流。
- 登录成功和失败均写安全日志；密码使用 scrypt，正式用户密码要求 10–128 位
  且须同时包含字母和数字；分享密码只保存哈希。
- 支付、注册找回、导出、粉丝写入、短链和助手等未完成模块保持 fail-closed。
- 正式翻译层使用可注入 provider 接口，默认实现只返回未配置，不依赖 Mock。

- 三个迁移完整执行 `up → down → up`。
- `npm run test:security`：38 项，37 通过，1 项数据库测试按设计跳过。

# 官方 tdesktop 魔改：气泡内 [译文]

## 技术方案概述

气泡里直接出译文，只能改官方 Telegram Desktop（tdesktop）源码后自己编译，不能抠 HelloWorld 的 `Telegram.exe`，也不能在这台 Mac 上编出 Windows 电报。

现有 Hello Pix 启动器继续负责登录、侧栏、多开；Windows 上编出来的魔改 `Telegram.exe` 替换安装包里的官方原版。翻译仍走现有 `/apis/translate/run`，不另写一套引擎。群发、采集、提取群成员不做。

官方 tdesktop 已经有翻译管线（`TranslateProvider` + `history_view_translate_tracker`），不必重写聊天界面。魔改只做两件事：把翻译请求改打到 Hello Pix，展示改成「原文 + `[译文]`」。

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| 客户端内核 | 官方 tdesktop（对齐现包 v7.2.5 或当前稳定版） | 聊天界面就是官方电报，GPL 源码可改可编 |
| 编译环境 | Windows + Visual Studio（官方文档现为 VS 2026 / Win10 SDK） | Mac 编不出可用的 Windows `Telegram.exe` |
| 翻译通道 | 现有 Hello Pix `/apis/translate/run` | 字符余额、套餐通道、登录态已经在用 |
| 启动器 | 现有 `standalone/telegram-win` Electron | 登录、侧栏、多开、写桥接配置 |
| 不用 | HelloWorld 安装包里的 exe / 反编译 | 别人的商业客户端，接不进我们的接口 |

## 架构设计

```
Hello Pix 启动器 (登录 / 侧栏 / 多开)
        │ 写出 hello-pix-bridge.json
        │ 启动 Telegram.exe -workdir <实例目录>
        ▼
魔改 Telegram Desktop
        │ 收消息后走 TranslateProvider
        ▼
Hello Pix API  /apis/translate/run
        │
        ▼
气泡：原文
      [译文] ……
```

- 表现层：官方气泡照旧画；译文作为附加行，不是侧栏弹层。
- 业务层：Hello Pix 登录态、通道、目标语言、收/发/群开关。
- 数据层：启动器把 cookie / apiBase / prefs 写到实例目录；电报只读这份桥接文件。

## 模块划分

| 模块 | 职责 | 依赖 |
|------|------|------|
| 启动器桥接 | 登录后把 `apiBase`、cookie、`deviceId`、翻译偏好写入实例目录 | 现有 `pix-api` / `store` |
| HelloPixTranslateProvider | 在 tdesktop 里 HTTP POST 翻译，带 CSRF 与 Idempotency-Key | 桥接文件、`/apis/translate/run` |
| 气泡展示 | `translationDone` 后拼 `原文\\n[译文] 译文`，聊天默认打开翻译 | 官方 `history_item` / `translate_tracker` |
| 多开 | 每个 `-workdir` 一份 tdata + 一份桥接文件 | 现有多开逻辑 |

## 接口设计

### 启动器 → 电报：hello-pix-bridge.json

写在该实例 `-workdir` 下，电报启动和偏好变更时覆盖。

```
{
  "apiBase": "http://192.168.x.x:8080",
  "deviceId": "…",
  "cookies": { "pix_session": "…", "pix_csrf": "…" },
  "engine": "youdao",
  "lang": "zh",
  "transRecv": true,
  "transSend": true,
  "transGroup": true
}
```

### 电报 → Hello Pix：翻译

- 方法：POST
- 路径：`{apiBase}/apis/translate/run`
- 头：`Cookie`、`X-CSRF-Token`、`X-Pix-Device`、`Idempotency-Key`（每条消息唯一，例如 `tg:{peer}:{msgId}:{hash}`）
- 表单：`text`、`from=auto`、`to={lang}`、`engine={engine}`
- 成功：`{ "success": true, "translation": "…" }`
- 失败：余额不足 / 通道未配置 / 未登录时气泡不写译文，不崩电报

### 官方源码钩子（tdesktop 现网结构）

| 文件 | 改动 |
|------|------|
| `Telegram/SourceFiles/lang/translate_provider.cpp`（及 `CreateTranslateProvider`） | 增加 Hello Pix Provider，优先于官方 MTProto 翻译 |
| `Telegram/SourceFiles/history/view/history_view_translate_tracker.cpp` | 收消息后按 `transRecv` / `transGroup` 触发翻译 |
| `Telegram/SourceFiles/history/history_item.cpp`（`translationDone`） | 展示文本改成原文 + `[译文]` |
| 发送路径（`history_widget` 发送前，第二阶段） | `transSend` 为真时先译再显示/发送 |

第一阶段只做**接收气泡**。发送翻译第二阶段再做。

## 数据模型

桥接文件即配置，不新增数据库表。Telegram 账号数据仍在官方 `tdata`。Hello Pix 账号、字符余额仍在现有后台。

## 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 改谁的源码 | 官方 tdesktop，不改 HelloWorld | 有源码、能接我们的 API、能合法出包 |
| 展示形态 | 原文和 `[译文]` 同气泡，不替换原文 | 对齐用户要的 HelloWorld 用法 |
| 编译地点 | 必须 Windows + VS | 这台 Mac 编不出 Windows 电报 |
| 启动器是否保留 | 保留 | 登录/侧栏/多开已经接上，不必重做成 Qt |
| 范围 | 不做群发、采集、提取群成员 | 产品已排除 |

## 实现计划

1. 启动器在打开电报时写出 `hello-pix-bridge.json`（这台 Mac 就能做）。
2. Windows 机器按官方文档准备 `D:\TBuild`，克隆 tdesktop，跑 `win.bat`，用自己的 `api_id` / `api_hash` 配置工程。
3. 加上 Hello Pix Provider 和 `[译文]` 展示，编出 `Telegram.exe`。
4. 替换现在安装包里的官方 `Telegram/Telegram.exe`，侧栏逻辑不动。
5. 用真实收消息、群聊、余额不足、断线重连验收气泡译文。

风险：第一次编 tdesktop 通常要数小时、几十 GB 磁盘；官方构建文档会随 VS 版本变。没有 Windows 编译机就出不了带气泡译文的包。

# 云编译卡点定位：不是编译失败，是编好的成果每轮被丢掉

## 现象与真因

问题一直被当成"tdesktop 编不过 / 6 小时不够编"。查 run 34649615155 的分步计时后，
结论完全不同：

| 步骤 | 实际耗时 | 结果 |
|------|----------|------|
| prepare 三方库 | 4h08m（34/34 全部编完） | **成功** |
| 保存三方库缓存 | 12m（6.06GiB） | **成功** |
| configure CMake | 58s | **成功** |
| msbuild Release x64 | 1h32m 后被 job 上限砍掉 | 未完成 |

也就是说三方库那 4 小时**只需要付一次**。真正的问题是 `actions/cache/restore` 的
`cache-hit` 只在**主 key 精确命中**时才为 true，而工作流当时只配了 `restore-keys`
前缀匹配 —— 命中缓存却仍判定为 false，于是第二轮又把 4h08m 的 prepare 从头跑了一遍，
等轮到 msbuild 时只剩 1h32m。

另外仓库里还躺着一份 6.5GB 废缓存 `tdesktop-libs-v7.2.8-Windows`（key 前缀不匹配，
永远取不到）。两份合计 13GB 已超免费额度 10GB，随时会把好缓存挤掉。

## 本轮改动

- 三方库缓存主 key 钉到那份已编完的缓存上，精确命中后 `prepare` / `save` 整步跳过，
  整个 6 小时配额留给 msbuild（实测 build 约需 2.5h：92 分钟编完 989/1387 个
  SourceFiles 单元，剩下是其余目标加链接）。
- 删除永远取不到的废缓存，把仓库缓存占用压回 6GB。
- 缓存被逐出时仍能自动退化：精确 miss → 前缀 miss → 全量 prepare → 用同名 key 重存。

## 补丁编译风险已提前排掉

补丁文件落在 `lang/`，在编译顺序里靠后，一旦编译不过会白烧一轮 6 小时。所以改 CI 的
同时把 7 个锚点对着 v7.2.8 真实源码逐个验了一遍，用到的全是官方现成 API：

- `TranslateProvider` / `TranslateProviderResult`（`lib_translate`，含 `supportsMessageId`、
  `request(TranslateProviderRequest, LanguageId, Fn<void(TranslateProviderResult)>)`）
- `LanguageId::FromName` / `known()` / `twoLetterCode()`（`lib_spellcheck`）
- `History::translateTo(LanguageId)`、`rpl::variable<bool> _trackingLanguage = rpl::single(true)`
- `cWorkingDir()` = `DeclareSetting(QString, WorkingDir)`（`settings.h`）
- `u"..."_q` 来自 `base/basic_types.h`，经 `settings.h → base/integration.h` 传递可见
- `endsWith('/')`、`QNetworkAccessManager` 在同目录官方文件里都有先例

## 顺手修掉一个"编出来也是白编"的问题

启动器侧栏的翻译通道写死成 `youdao / google / deepl`，而这三个通道在后台
`wired=false`（凭据未配置）；真正接通的只有 `deepseek`（且只在 pro 套餐里）。
桥接文件把死通道写进 `hello-pix-bridge.json` 后，服务端一律返回
`503 ENGINE_NOT_CONFIGURED`；魔改电报的 Provider 按设计"失败就不写译文、不弹错、
不崩电报"，所以气泡永远静默不出 `[译文]` —— 从外面看和"编译没成功"一模一样。

改为：通道列表走后台 `/apis/translate/engines`（只列已接通的），默认取后台的
`activeEngine`；问不到后台就沿用本地缓存；再没有就写空串，让服务端按账号当前通道
回退（`core-service` 里 `String(data.engine || session.account.activeEngineId || ...)`
对空串是 falsy）。同时打开「翻译设置」会重新拉一次，后台刚接通的通道不用重启。

## 2026-09-14

# 拿到真凭据后，云编译又暴露的三个陷阱

凭据到位后连跑四轮，全部失败——但**没有一次是编译错误**，也没有一次是补丁的问题。
三个坑都属于"看日志只会以为机器慢 / 网络差 / 编译不过"的类型。

## 1. prepare.py 会在 CI 上永久挂起（最隐蔽）

`Telegram/build/prepare/prepare.py` 里，stage 处于 `Stale`（key 文件在但内容对不上）
时走的是**交互式分支**：

```python
elif checkResult == 'Stale' or checkResult == 'Forced':
    print('(r)ebuild, rebuild (a)ll, (s)kip, (p)rint, (q)uit?: ', end='', flush=True)
    while True:
        ch = 'r' if rebuildStale else getch()      # 阻塞等键盘
```

CI 没有 stdin，于是一挂到步骤超时，**日志里一个字都没有**（run 34791050283 挂了 37 分钟）。

之所以一直没暴露，是**我自己的优化把它藏起来了**：上一轮为了省 5 分钟加的
`if: steps.libs-cache.outputs.cache-hit != 'true'` 守卫，让 prepare 在每次缓存命中时
被整步跳过；那是第一次让它在热缓存下真正跑起来。冷启动那轮能跑完，是因为所有
stage 都是 `NotFound`，**不走提示分支**。

修法：传 `silent`（prepare.py 自己支持，`win.bat` 会透传参数），
`elif arg == 'silent': rebuildStale = True` → Stale 的 stage 直接重建，不再问人。

教训：**为省几分钟而跳过的路径，恰恰是没被验证过的路径**。

## 2. runner 的密钥脱敏器会被构建日志压垮

run 34793229857 跑了 2h15m 后整个作业消失：

```
X Stack overflow.
   at GitHub.DistributedTask.Logging.SecretMasker.MaskSecrets(System.String)
   at GitHub.Runner.Worker.ExecutionContext.Write(...)
```

runner 每写一行日志都要过一遍密钥脱敏，而 `/v:m` 编 2600 多个源文件会产出几万行、
单行动辄上千字符（cl.exe 命令行）。全喂给脱敏器 → 它一栈溢出，2h15m 的成果一起没，
而且崩在 runner 里**日志都取不回来**（重试三次下载均失败）。

修法：msbuild 输出重定向到文件，只回显有界摘要（成功 40 行 / 失败 120 行），
并把完整日志作为 artifact 传上来。

## 3. 免费额度用尽会"拒绝启动作业"，且公开仓库顺带翻倍 CPU

```
The job was not started because recent account payments have failed
or your spending limit needs to be increased.
```

四轮里最贵的两轮（5h55m + 2h15m）按 Windows 2 倍计费早已越过 GitHub Free 的
2000 分钟/月。**注意这不是"运行中被打断"，而是作业根本没分配 runner**（4 秒失败）。

按官方计费文档，改成公开仓库后：

| | 私有 | 公开 |
|---|---|---|
| 计费 | 2000 分钟/月，超额即封 | 免费且不限量 |
| `windows-2025` | 2 核 / 8 GB | **4 核 / 16 GB** |

所以之前所有实测速率（~10 个编译单元/分钟）都是**在 2 核机器上**测的，
换公开仓库后编译时间大约减半——之前按 2 核推算的"3 小时 10 分"是悲观值。

改公开前已审计：仓库只有 6 个补丁脚本文件，真实凭据在 git 全历史里 0 命中。
代价是产物 `Telegram.exe` 也会被任何人下载，交付验收完成后可改回私有。

## 工作流纳入版本控制（原来只存在于被 gitignore 的 .ci-build 里）

`.ci-build/` 是独立 git 仓库、被主仓库 `.gitignore` 排除，而主仓库补丁包的注释写着
"补丁包正文在主仓库 standalone 那份，.ci-build 是镜像"。但**工作流本身没遵守这个约定** ——
它只存在于 `.ci-build/.github/workflows/`，等于整条流水线在主仓库里没有版本控制，
重新克隆一次就没了。

现在正文落在 `standalone/telegram-win/tdesktop-fork/build-telegram.yml`，
`.ci-build` 那份仍是镜像，由 `test/ci-workflow.test.js` 断言两份逐字节一致。

同一个测试还把今天三个坑固化成断言（只打在会被执行的 YAML 值上，避免被密集的注释
误命中）：

- prepare 必须 `win.bat silent`（缺了会挂在交互提示上）
- msbuild 输出必须重定向到文件 + 失败时上传完整日志
- 构建超时 ≥ 300 分钟、作业级 ≤ 355
- 凭据门禁存在且 `exit /b 1`，artifact 只在真凭据模式上传
- 缓存守卫：prepare 用 `cache-hit != 'true'`，保存用 `cache-hit == 'false'`

**变异验证过**：分别去掉 `silent`、退回 `!= 'true'` 的保存条件、去掉日志重定向，
对应断言立刻变红；恢复后全绿。全量 158 项 157 通过 1 跳过。

## 顺带核实到源码级的几件事

- `-workdir`（`core/launcher.cpp` v7.2.8）：第 606 行声明 `KeyFormat::OneValue`，
  第 655-657 行取值并 `QDir(...).absolutePath() + '/'`，再 `cForceWorkingDir()`。
  与启动器写桥接文件的目录、以及 Provider 读 `cWorkingDir() + "hello-pix-bridge.json"`
  完全对上。**这是整条链路的单点**，之前只有 APPLY.txt 里一句"已核实"。
- 我们的 `HelloPixTranslateProvider` 与官方同目录的 `UrlTranslateProvider`
  结构逐项一致（继承方式、`supportsMessageId()` 返回 false、`request()` 签名、
  `[=]` 捕获 + `reply->deleteLater()`、`QNetworkAccessManager _network` 成员）。
  即"请求在飞时 Provider 被销毁"这一风险属于上游既有约定，不是我们引入的。
- **多开靠的就是 `-workdir`，这是 tdesktop 明确设计的路径**（`core/sandbox.cpp`）：
  局部服务器名按**工作目录**哈希，锁文件却按**exe 路径**哈希 —— 所有实例共用同一个
  exe，所以第二份必然抢不到锁；而
  ```cpp
  if (!_lockFile->tryLock() && Launcher::Instance().customWorkingDir()) {
      if constexpr (Platform::IsWindows()) {
          if (!_lockFile->removeStaleLockFile()) gManyInstance = true;
      }
  }
  ```
  只有带着 `-workdir`（`customWorkingDir()` 为真）才会被标记为多实例；
  之后 `singleInstanceChecked()` 对 `cManyInstance()` **只记一行日志、不阻止启动**。
  不带 `-workdir` 的话会走连到已有实例本地服务去"显示窗口"那条路，根本开不出新窗口。
  所以验收清单第 8 项（程序多开）不是"试出来能用"，而是设计如此。
