# PostgreSQL + Redis 基础设施与 Schema 方案

## 目标与边界

- 使用 PostgreSQL 作为业务事实源，Redis 仅承载会话、限流、缓存和短期协调数据。
- 使用 CommonJS 和 `node-pg-migrate` 管理可回滚 Schema。
- 本阶段不修改 `server/index.js`、安全模块、路由或 Mock；生产入口原有门禁继续生效，
  直至 API 完成真实数据层与支付验签集成。
- 迁移只预置套餐、引擎和非敏感设置，不创建任何默认用户或管理员。

## 数据模型

- 商品配置：`packages`、`engines`、`package_engines`、`app_settings`。
- 身份体系：`users`、`sub_accounts`、`admins`；密码只允许 scrypt 哈希格式，
  用户名和邮箱使用大小写不敏感唯一索引。
- 业务记录：`orders`、`recharges`、`translate_logs`。
- 余额一致性：`translation_reservations` 以用户和幂等键唯一约束完成字符预占，
  状态约束覆盖预占、提交、释放和过期；翻译日志可关联预占记录。
- 安全追踪：`login_logs`、`audit_logs` 保存主体、IP、资源和请求信息，并对常用
  时间范围和主体查询建立组合索引。

所有余额、计数和金额都有非负约束；外键明确采用 `RESTRICT`、`CASCADE` 或
`SET NULL`；子账号相关业务记录使用 `(parent_id, id)` 复合外键防止跨租户关联。

## 运行与安全

- `server/config.js` 在生产环境强制要求带凭据的 `DATABASE_URL` 和 `REDIS_URL`，
  拒绝示例密码；非回环 PostgreSQL 禁止关闭 TLS。
- PostgreSQL 使用有上限的连接池、连接超时、空闲超时和语句超时；事务帮助器保证
  异常回滚。Redis 延迟连接并设置命令超时、有限请求重试和统一键前缀。
- Docker Compose 中 PostgreSQL 与 Redis 仅绑定本机，启用持久卷、健康检查和
  Redis AOF。systemd 在启动 API 前自动执行迁移。
- 管理员由独立脚本显式创建，用户名、昵称、角色和强密码均必须提供；脚本不覆盖
  已存在账号，密码文件优先于环境变量。

## 后续集成

1. 将会话、限流和翻译缓存从进程内存迁移到 Redis。
2. 将注册、账户、工单、充值和翻译扣费路由迁移到 PostgreSQL 事务。
3. 在支付回调中以 `idempotency_key` 和厂商交易号双重去重。
4. 完成真实支付验签及回归测试后，再评估移除生产入口门禁。

# PostgreSQL + Redis 正式核心后端实施结果

## 最终结构

- `server/index.js` 负责运行模式选择、依赖探活、迁移版本门禁、启动和优雅关闭；
  生产环境以及 `PIX_USE_PERSISTENT_BACKEND=1` 只注册正式 API，不加载 Mock。
- `server/routes/`、`server/services/`、`server/repositories/` 分别承载接口契约、
  业务事务和参数化数据访问；未迁移接口统一返回 `503 / NOT_MIGRATED`。
- PostgreSQL 保存身份、套餐、工单、充值记录、翻译日志、预留账本和审计日志；
  Redis 保存会话、主体会话索引、限流、验证码、分享授权和租户隔离翻译缓存。

## 一致性设计

- 翻译先在短事务内锁定账号、扣减余额并创建幂等 reservation，再在事务外调用
  翻译通道，最后以幂等事务提交日志或退款。
- 未接线的翻译通道在扣费前返回 `ENGINE_NOT_CONFIGURED`，不会使用演示翻译收费。
- 超时 reservation 由启动后的定时 reconciliation 使用 `FOR UPDATE SKIP LOCKED`
  领取并退款，避免多实例重复补偿。
- 主子账号字符转移固定先锁主账号、再锁子账号；余额更新带非负条件，转移记录和
  两侧余额处于同一事务。
- 翻译缓存按 `main|sub + account id` 隔离；缓存命中仍创建 reservation 并计费。

## 安全边界

- 生产环境强制 PostgreSQL/Redis 凭据、远程 TLS、HTTPS 来源和本机监听，并拒绝
  所有 demo 开关。
- Web、Client、Admin 登录同时按 IP 和账号限流；分享密码与翻译也采用双维限流。
- 登录成功和失败均写安全日志；密码使用 scrypt，正式用户密码要求 10–128 位并
  同时包含字母和数字；分享密码只保存哈希。
- 支付、注册找回、导出、粉丝写入、短链和助手等未完成模块保持 fail-closed。
- 正式翻译层使用可注入 provider 接口，默认实现只返回未配置，不依赖 Mock。

## 已验证命令

- 三个迁移完整执行 `up → down → up`。
- `npm run test:security`：38 项，37 通过，1 项数据库测试按设计跳过。
- 配置测试环境后 `npm run test:integration`：真实 PostgreSQL + Redis 测试通过，
  覆盖跨进程会话、账号唯一性、并发预扣、失败退款、缓存计费、超时恢复和余额守恒。
- `npm run build`：通过。
- Electron 实际启动：通过，未出现 preload、CSP 或未捕获异常。

# 官方 tdesktop 魔改：气泡内 [译文]

## 技术方案概述

气泡里直接出译文，只能改官方 Telegram Desktop（tdesktop）源码后自己编译，不能抠 HelloWorld 的 `Telegram.exe`，也不能在这台 Mac 上编出 Windows 电报。

现有 Hello Pix 启动器继续负责登录、侧栏、多开；Windows 上编出来的魔改 `Telegram.exe` 替换安装包里的官方原版。翻译仍走现有 `/apis/translate/run`，不另写一套引擎。群发、采集、提取群成员不做。

官方 tdesktop 已经有翻译管线（`TranslateProvider` + `history_view_translate_tracker`），不必重写聊天界面。魔改只做两件事：把翻译请求改打到 Hello Pix，展示改成「原文 + `[译文]`」。

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| 客户端内核 | 官方 tdesktop（对齐现包 v7.2.5 或当前稳定版） | 聊天界面就是官方电报，GPL 源码可改可编 |
| 编译环境 | Windows + Visual Studio（官方文档现为 VS 2026 / Win10 SDK） | Mac 编不出可用的 Windows `Telegram.exe` |
| 翻译通道 | 现有 Hello Pix `/apis/translate/run` | 字符余额、套餐通道、登录态已经在用 |
| 启动器 | 现有 `standalone/telegram-win` Electron | 登录、侧栏、多开、写桥接配置 |
| 不用 | HelloWorld 安装包里的 exe / 反编译 | 别人的商业客户端，接不进我们的接口 |

## 架构设计

```
Hello Pix 启动器 (登录 / 侧栏 / 多开)
        │ 写出 hello-pix-bridge.json
        │ 启动 Telegram.exe -workdir <实例目录>
        ▼
魔改 Telegram Desktop
        │ 收消息后走 TranslateProvider
        ▼
Hello Pix API  /apis/translate/run
        │
        ▼
气泡：原文
      [译文] ……
```

- 表现层：官方气泡照旧画；译文作为附加行，不是侧栏弹层。
- 业务层：Hello Pix 登录态、通道、目标语言、收/发/群开关。
- 数据层：启动器把 cookie / apiBase / prefs 写到实例目录；电报只读这份桥接文件。

## 模块划分

| 模块 | 职责 | 依赖 |
|------|------|------|
| 启动器桥接 | 登录后把 `apiBase`、cookie、`deviceId`、翻译偏好写入实例目录 | 现有 `pix-api` / `store` |
| HelloPixTranslateProvider | 在 tdesktop 里 HTTP POST 翻译，带 CSRF 与 Idempotency-Key | 桥接文件、`/apis/translate/run` |
| 气泡展示 | `translationDone` 后拼 `原文\\n[译文] 译文`，聊天默认打开翻译 | 官方 `history_item` / `translate_tracker` |
| 多开 | 每个 `-workdir` 一份 tdata + 一份桥接文件 | 现有多开逻辑 |

## 接口设计

### 启动器 → 电报：hello-pix-bridge.json

写在该实例 `-workdir` 下，电报启动和偏好变更时覆盖。

```
{
  "apiBase": "http://192.168.x.x:8080",
  "deviceId": "…",
  "cookies": { "pix_session": "…", "pix_csrf": "…" },
  "engine": "youdao",
  "lang": "zh",
  "transRecv": true,
  "transSend": true,
  "transGroup": true
}
```

### 电报 → Hello Pix：翻译

- 方法：POST
- 路径：`{apiBase}/apis/translate/run`
- 头：`Cookie`、`X-CSRF-Token`、`X-Pix-Device`、`Idempotency-Key`（每条消息唯一，例如 `tg:{peer}:{msgId}:{hash}`）
- 表单：`text`、`from=auto`、`to={lang}`、`engine={engine}`
- 成功：`{ "success": true, "translation": "…" }`
- 失败：余额不足 / 通道未配置 / 未登录时气泡不写译文，不崩电报

### 官方源码钩子（tdesktop 现网结构）

| 文件 | 改动 |
|------|------|
| `Telegram/SourceFiles/lang/translate_provider.cpp`（及 `CreateTranslateProvider`） | 增加 Hello Pix Provider，优先于官方 MTProto 翻译 |
| `Telegram/SourceFiles/history/view/history_view_translate_tracker.cpp` | 收消息后按 `transRecv` / `transGroup` 触发翻译 |
| `Telegram/SourceFiles/history/history_item.cpp`（`translationDone`） | 展示文本改成原文 + `[译文]` |
| 发送路径（`history_widget` 发送前，第二阶段） | `transSend` 为真时先译再显示/发送 |

第一阶段只做**接收气泡**。发送翻译第二阶段再做。

## 数据模型

桥接文件即配置，不新增数据库表。Telegram 账号数据仍在官方 `tdata`。Hello Pix 账号、字符余额仍在现有后台。

## 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 改谁的源码 | 官方 tdesktop，不改 HelloWorld | 有源码、能接我们的 API、能合法出包 |
| 展示形态 | 原文和 `[译文]` 同气泡，不替换原文 | 对齐用户要的 HelloWorld 用法 |
| 编译地点 | 必须 Windows + VS | 这台 Mac 编不出 Windows 电报 |
| 启动器是否保留 | 保留 | 登录/侧栏/多开已经接上，不必重做成 Qt |
| 范围 | 不做群发、采集、提取群成员 | 产品已排除 |

## 实现计划

1. 启动器在打开电报时写出 `hello-pix-bridge.json`（这台 Mac 就能做）。
2. Windows 机器按官方文档准备 `D:\TBuild`，克隆 tdesktop，跑 `win.bat`，用自己的 `api_id` / `api_hash` 配置工程。
3. 加上 Hello Pix Provider 和 `[译文]` 展示，编出 `Telegram.exe`。
4. 替换现在安装包里的官方 `Telegram/Telegram.exe`，侧栏逻辑不动。
5. 用真实收消息、群聊、余额不足、断线重连验收气泡译文。

风险：第一次编 tdesktop 通常要数小时、几十 GB 磁盘；官方构建文档会随 VS 版本变。没有 Windows 编译机就出不了带气泡译文的包。

# 云编译卡点定位：不是编译失败，是编好的成果每轮被丢掉

## 现象与真因

问题一直被当成"tdesktop 编不过 / 6 小时不够编"。查 run 34649615155 的分步计时后，
结论完全不同：

| 步骤 | 实际耗时 | 结果 |
|------|----------|------|
| prepare 三方库 | 4h08m（34/34 全部编完） | **成功** |
| 保存三方库缓存 | 12m（6.06GiB） | **成功** |
| configure CMake | 58s | **成功** |
| msbuild Release x64 | 1h32m 后被 job 上限砍掉 | 未完成 |

也就是说三方库那 4 小时**只需要付一次**。真正的问题是 `actions/cache/restore` 的
`cache-hit` 只在**主 key 精确命中**时才为 true，而工作流当时只配了 `restore-keys`
前缀匹配 —— 命中缓存却仍判定为 false，于是第二轮又把 4h08m 的 prepare 从头跑了一遍，
等轮到 msbuild 时只剩 1h32m。

另外仓库里还躺着一份 6.5GB 废缓存 `tdesktop-libs-v7.2.8-Windows`（key 前缀不匹配，
永远取不到）。两份合计 13GB 已超免费额度 10GB，随时会把好缓存挤掉。

## 本轮改动

- 三方库缓存主 key 钉到那份已编完的缓存上，精确命中后 `prepare` / `save` 整步跳过，
  整个 6 小时配额留给 msbuild（实测 build 约需 2.5h：92 分钟编完 989/1387 个
  SourceFiles 单元，剩下是其余目标加链接）。
- 删除永远取不到的废缓存，把仓库缓存占用压回 6GB。
- 缓存被逐出时仍能自动退化：精确 miss → 前缀 miss → 全量 prepare → 用同名 key 重存。

## 补丁编译风险已提前排掉

补丁文件落在 `lang/`，在编译顺序里靠后，一旦编译不过会白烧一轮 6 小时。所以改 CI 的
同时把 7 个锚点对着 v7.2.8 真实源码逐个验了一遍，用到的全是官方现成 API：

- `TranslateProvider` / `TranslateProviderResult`（`lib_translate`，含 `supportsMessageId`、
  `request(TranslateProviderRequest, LanguageId, Fn<void(TranslateProviderResult)>)`）
- `LanguageId::FromName` / `known()` / `twoLetterCode()`（`lib_spellcheck`）
- `History::translateTo(LanguageId)`、`rpl::variable<bool> _trackingLanguage = rpl::single(true)`
- `cWorkingDir()` = `DeclareSetting(QString, WorkingDir)`（`settings.h`）
- `u"..."_q` 来自 `base/basic_types.h`，经 `settings.h → base/integration.h` 传递可见
- `endsWith('/')`、`QNetworkAccessManager` 在同目录官方文件里都有先例

## 顺手修掉一个"编出来也是白编"的问题

启动器侧栏的翻译通道写死成 `youdao / google / deepl`，而这三个通道在后台
`wired=false`（凭据未配置）；真正接通的只有 `deepseek`（且只在 pro 套餐里）。
桥接文件把死通道写进 `hello-pix-bridge.json` 后，服务端一律返回
`503 ENGINE_NOT_CONFIGURED`；魔改电报的 Provider 按设计"失败就不写译文、不弹错、
不崩电报"，所以气泡永远静默不出 `[译文]` —— 从外面看和"编译没成功"一模一样。

改为：通道列表走后台 `/apis/translate/engines`（只列已接通的），默认取后台的
`activeEngine`；问不到后台就沿用本地缓存；再没有就写空串，让服务端按账号当前通道
回退（`core-service` 里 `String(data.engine || session.account.activeEngineId || ...)`
对空串是 falsy）。同时打开「翻译设置」会重新拉一次，后台刚接通的通道不用重启。

## 同日补充：把"静默失败"变成断言

上面三个坑的共同点是**都不报错**：Provider 失败不写译文不弹错、启动器只在登录层报错、
服务端只回状态码。所以补了两套验证手段，都不需要 Windows：

### 1. 端到端验收脚本 `scripts/verify-telegram-bridge-e2e.js`

把 `hello_pix_translate_provider.cpp` 实际会发的那份 HTTP 请求原样打到真后端。
临时建 pro 套餐账号并**故意**把 `active_engine_id` 设成未接通的 `youdao`，
复现真实库里 `demo` 账号的状态。实测 **10/10 通过**：

```
✅ 取到通道列表           已接通=[deepseek]  账号 activeEngine=youdao
✅ resolveEngine 绕开死通道                挑中 deepseek
✅ 死通道 youdao 被挡下                    HTTP 503 ENGINE_NOT_CONFIGURED
✅ deepseek 真翻出译文                     translation="早上好，会议九点开始。"
✅ 重复请求不重复扣费                       余额 99959 -> 99959
```

第三项就是"气泡静默不出译文"的实测复现；第五项说明 tdesktop 重渲染
重复请求同一条消息不会二次扣费（幂等键生效）。

### 2. 补丁干跑 `scripts/dryrun-tdesktop-patch.sh`

补丁锚点是硬编码字符串匹配，升级 tdesktop 后一旦失配，`apply.py` 会静默跳过，
编出来是一个**没有 Hello Pix 钩子的官方原版**——现象同样是"气泡不出译文"。
本机（不需要 Windows、不需要 clone 整个 tdesktop）拉 4 个真实文件搭最小夹具，
跑完注入并 diff 出来。v7.2.8 实测 7/7 命中、二次运行全部 `skip already patched`。

顺带把 C++ 契约的最后一环也核了：`LanguageId::FromName("zh")` 经 `QLocale` 解析为
`QLocale::Chinese`，`twoLetterCode()` 得 `"zh"`，正好落在服务端
`^[a-z]{2,3}(-[a-z0-9]{2,8})?$` 的校验范围内。

### 3. 出包链路已空跑验证

用官方 7.2.5 的 exe 当替身跑了一遍 `assemble-from-build.sh`：产出 176MB zip，
结构正确，包内 `main.js` / `preload.js` / `lib/bridge.js` / `renderer/app.js`
与仓库版本 SHA256 一致（即装进去的是修好通道的版本）。
官方便携包只有 `Telegram.exe` + `modules/x64/d3d/d3dcompiler_47.dll`，
替换 exe 很干净。验收步骤见 `docs/电报独立版验收步骤.md`。
