#### 1. 管理端工单列表的分页参数和时间字段不一致

- 位置：`server/routes/admin/tickets.js:190-221,230-265`；
  `server/routes/user-tickets.js:201-225`；迁移

- 修复：将消息写入和状态变更放进同一事务，对票行 `SELECT ... FOR UPDATE`；
  或在事务中使用 version 条件更新并正确递增。创建工单与首条消息也应
  同事务，确保不会出现无正文工单。

#### 3. 图片翻译没有服务端幂等/预算闸，成本可被持续放大

- 位置：`server/routes/production.js:394-406`，
  `server/services/core-service.js:789-900`，
  `server/routes/context.js:106-127`。
- 图片不参与字符预留或结算，只按账号 20 次/分钟、IP 40 次/分钟限流。
  单账号可持续约 `20 × 60 × 24 = 28,800` 次/天；直接调用 API 可绕过
  桌面端 LRU 缓存。服务端没有 `Idempotency-Key`、请求结果缓存或并发闸，

- 线上 `pixfanyi.com` 的 Nginx `client_max_body_size` 实际为 2m，而
  API 解析器允许 16m、业务上限 12m。正常 1600px WebP 约 300–800KB，
  因此当前常用路径能通过；但 WebP 编码回退 PNG、较大截图或未来提高画质时，
  请求会在进入 Node 前被 Nginx 413，表现为“图片翻译有时可用、有时失败”。
- 成本台账记录是好事，但它只能事后记账，不能阻止账单增长。
- 修复：若产品承诺图片免费，增加日/月预算和账号并发上限；若图片属于
  套餐权益，接入图片预留/结算或明确图片计费规则；客户端和服务端都使用
  图片内容哈希 + 目标语言 + 引擎的幂等键；同时统一 Nginx 与 API 的体量契约。

#### 4. 本地翻译缓存没有租户边界，图片缓存没有引擎边界

- 位置：`desktop/src/translate/translation-cache.js:100-124`，
  `desktop/src/ipc/translate.js:192-197`，
  `desktop/src/ipc/auth.js:61-73`。
- 文本缓存键只包含引擎、语向和正文，不含当前账号；`currentUser`
  只参与幂等指纹，不参与 `cacheKey`。已用纯函数复现：账号 A 写入缓存后，
  切换账号 B，B 能命中 A 的译文。

  仍可能拿到上一个引擎的结果，且账号切换不会清理模块级缓存。

  登出时清理当前会话缓存，或把缓存生命周期绑定到登录会话。

#### 5. 代理面板的“刷新URL”“UDP协议”当前没有消费者

- 修复：实现对应行为并增加真实出口测试；若暂不支持，隐藏字段或明确标注

# 外部录音 → WhatsApp 原生语音消息

## 问题

外部录制的 `.ogg`/Opus 通过 WhatsApp 的普通文件入口发送后，会被归类为
`AUDIO`，显示耳机图标和普通进度条；原生语音消息则是 `PTT`，显示波形。
只修改 CSS 不会改变消息协议，接收方仍会看到普通音频文件。

## 修复方案

- 在 WhatsApp Web 的页面世界增加「导入语音」入口，并拦截单个音频文件的
  拖入/粘贴。
- 使用 Web Audio 解码外部音频，接入 `MediaStreamAudioDestinationNode`，
  在一次 `getUserMedia({audio:true})` 中临时作为虚拟麦克风。
- 点击 WhatsApp 自己的麦克风按钮，让 WhatsApp 自己编码 Opus、生成时长和

### 问题清单

#### 🔴 严重问题

**问题1：打开旧会话、发消息或补扫历史消息都会计成“进粉”**

- 位置：
  - `server/routes/production.js:416`
  - `desktop/guest-inject.js:2548`
  - `server/services/count-ticket-service.js:168`
- 问题：`/customer/ingest` 的所有调用都会旁路执行 `captureFan`，但客户端在
  仅切换/打开会话时也会调用 `reportClue('', 'in')`，出向消息也会上报。
  `captureFan` 不检查 `direction`、正文是否为空、事件是否早于工单/账号绑定时间。
  实测空正文、`direction=out`、2020 年的历史事件仍返回 `captured=true`，
  并被记为新粉。
- 风险：绑定账号后，客服逐个打开已有会话即可把历史联系人和自己的出向消息
  全部刷成“进粉”；新工单会回填旧历史，日/累计计数严重虚高。若计数用于
  绩效、线索结算或客户对账，这是直接错账。
- 建议：把“客户归档事件”和“进粉事件”拆开。只有满足产品定义的真实入站事件
  才能进计数账本；至少要求 `direction === 'in'`、非空真实消息、
  `eventAt >= account.updated_at`，并拒绝/夹取未来时间。打开会话只做撞单检测，
  不直接计粉。补一条“空 body / out / 旧历史均不计粉”的真实库测试。

**问题2：已合并客户再次成为合并目标会形成链，导致重粉永久算成新粉**

- 位置：
  - `server/services/customer-identity-service.js:315`
  - `server/repositories/customer-repository.js:51`
  - `server/repositories/customer-repository.js:459`
- 问题：处理合并候选时直接使用候选里的两个客户 ID，没有先把双方解析到
  最终根客户，也没有拒绝“目标客户已合并”或锁定两个根。实测先合并
  `B -> A`，再把 `D` 并入 `B` 后形成 `D -> B -> A`；D 的粉丝账本停在中间节点 B，
  后续根客户 A 再出现时查不到 B 的历史，结果 `new=2 / repeat=0`。
- 风险：一次过期的合并候选就可能让同一客户在同一应用内重复算新粉；重粉
  `repeat_of_id`、账号统计、商户统计和管理端统计全部失真，而且没有现成撤销
  操作。当前自动化测试只覆盖简单的一次合并，所以全绿。
- 建议：合并事务内先用递归 CTE 把 `fromId/intoId` 都解析到最终根，拒绝同一根
  和环，再对两个根执行 `FOR UPDATE`；冻结已处理候选涉及的客户状态，禁止对已
  合并客户继续建/处理候选；所有后代 `merged_into`、客户归属和计数账本统一指向
  根客户。补“B 已并入 A，再处理 B-D 候选”的复现测试。

#### 🟡 建议修改

**问题3：迟到事件会倒挂新/重粉时间线**

- 位置：
  - `server/services/count-ticket-service.js:194`
  - `server/repositories/count-ticket-repository.js:57`
- 问题：先到一条较晚事件会记 `new`；之后补到更早的真实历史事件时，
  `priorFanForCustomer` 只看到已存在事件，于是把更早事件记成 `repeat`。
  实测输出 `later=new earlier=repeat`。
- 风险：总数通常仍是“1 个新粉 + 其余重粉”，但新粉归属、时间线和
  `repeat_of_id` 错误；多商户、多工单补扫时审计会失真。
- 建议：插入后按 `customer/platform/event_at` 重排该客户事件，或发现更早事件时
  把更早事件提升为 `new` 并重排后续事件的 `repeat_of_id`。补乱序到达测试。

**问题4：合并会原地重写计数账本，但没有可恢复快照**

- 位置：`server/repositories/customer-repository.js:459`
- 问题：合并会重写 `customer_id`、`fan_type`、`repeat_of_id`、客户归属和撞单
  记录。注释称“合并可回滚”，但仅保留 `merged_into` 不能恢复被改写的旧账本。
- 风险：误合并或合并链错误发生后，无法证明合并前每条粉丝事件的类型和归属，
  也无法精确回滚绩效/结算统计。
- 建议：合并事件写一份不可变快照（客户、受影响粉丝账本、owners、collisions），
  或改成 append-only 客户归属历史 + 按最终根动态计算统计；至少提供可验证的
  unmerge 流程。

**问题5：删除商户会永久删除计数账本，但删除快照未包含计数数据**

- 位置：`server/lib/merchant-purge.js:53`、`server/lib/merchant-purge.js:141`
- 问题：`count_tickets`、`count_ticket_accounts`、`count_ticket_fans` 被列入
  业务表和级联删除，但 `buildSnapshot` 只保存用户、充值、字符流水、划转和旧订单。
- 风险：删除商户后只能看到“删了多少行”，看不到工单、账号绑定、粉丝明细或
  新/重粉类型，发生结算争议或审计时无据可查。
- 建议：把 `count_tickets`、账号绑定和粉丝账本纳入删除快照；粉丝量过大时至少
  保存工单、按账号/业务日聚合、事件 ID 范围和摘要哈希。

**问题6：绑定账号允许任意手填，且历史停用绑定永久锁死应用切换**

- 位置：
  - `src/components/count/CountTickets.vue:259`
  - `server/repositories/count-ticket-repository.js:124`
  - `server/repositories/count-ticket-repository.js:194`
- 问题：UI 允许 `allow-create` 手填不存在的 `accountKey`；`has_accounts`
  统计所有历史绑定（包括已停用），即使没有粉丝，只要曾经误绑过账号，工单
  就永远不能改平台。
- 风险：录入误操作会留下无效绑定并把工单锁死；账号拼接错误不会被服务端拒绝。
- 建议：绑定前校验该账号确有本商户会话；如产品坚持手填，增加显式“手工账号”
  标记和确认。平台锁应只由真实粉丝或启用中绑定触发，不把历史停用记录当永久锁。

**问题7：“跨商户算重粉”需要书面业务确认**

- 位置：`docs/原生计数工单-实现说明.md` 需求规则第 5 条
- 问题：当前明确把“另一个商户的计数工单”也纳入重粉；这与统一客户系统里
  `crossMerchant` 默认关闭的隐私策略存在张力。
- 风险：商户 B 的第一次接触会因为商户 A 的历史被标为重粉；客户合并后，
  其他商户的统计也会被追溯改写。如果用于绩效或结算，必须明确这是平台级口径。
- 建议：保留当前规则前先让业务方书面确认；若只按商户计数，给
  `priorFanForCustomer` 和合并重排增加 `user_id` 维度。对外文档也应明确说明
  重粉可能是跨商户口径，避免争议。
