# 客户端更新签名

## 这套东西解决什么问题

改之前，`app:checkUpdate` 只做一件事：把服务端给的下载地址过一遍
`DOWNLOAD_HOSTS` 域名白名单。

白名单能挡「服务端把用户引到 evil.com」，但挡不住**服务端被攻破、在白名单
域名上换一个恶意安装包**。那时 URL 完全合法，白名单一路放行。

更新通道是唯一能给所有用户推代码执行的通道，却把完整性押在了服务端的健康上。

现在加了一层与服务端无关的校验：安装包哈希由**私钥签名**，客户端**内置公钥**
验签。私钥泄露不了，服务器就被打穿也签不出一份合法清单。

## 两道防线，顺序不能反

```
服务端 /client/update
        │  返回 { version, url, manifest: { 字段..., signature } }
        ▼
① 验签  desktop/src/update/verify-release.js
        │  签名对不上 → 直接拒绝，不给下载地址
        ▼
② 白名单  DOWNLOAD_HOSTS
        │  签名对但域名不对 → 也拒绝
        ▼
   把 url 交给渲染层
```

第二道留着，是因为签名只管「内容没被改」，不管「地址该不该放」。万一发布流程
出错把外部域名的包签了进去，白名单兜底。

## 文件在哪

| 文件 | 作用 |
|---|---|
| `desktop/src/update/signature.js` | 签名原文构造、Ed25519 验签、版本比较 |
| `desktop/src/update/verify-release.js` | 把服务端响应变成 hardened / legacy / rejected |
| `desktop/src/update/trusted-keys.js` | **内置公钥**（当前是占位符，见下文） |
| `desktop/src/ipc/app.js` | `app:checkUpdate` 接上两道防线 |
| `server/lib/update-signing.js` | 服务端签名 |
| `server/services/core-service.js` | `findUpdate` 额外下发 `manifest` |
| `migrations/051_client_release_signature.js` | `client_releases` 加 sha256 / signature / min_version |
| `scripts/update-keygen.js` | 生成密钥对 |
| `scripts/release-client.js` | 发布版本：算哈希并写库 |

## 签名原文为什么不用 JSON

```
appId \n version \n url \n sha256 \n channel \n minVersion
```

`JSON.stringify` 的 key 顺序、空格、转义都会随实现变化，任何一处变化都让验签
失败，而且失败得看不出原因。定长字段顺序是唯一稳定的做法。

字段顺序同时写在服务端和客户端两处，`test/update-signing-server.test.js` 里有
一条测试直接拿两边的 `manifestPayload` 对撞 —— 改任意一侧都会红。

## 现在的状态：**更新功能是关闭的**

`trusted-keys.js` 里的公钥还是占位符 `__UPDATE_PUBLIC_KEY_PRIMARY__`。

这意味着：**签名校验拒绝一切清单**。是「更新不可用」，不是「更新不安全」。
这是有意的安全默认 —— 宁可暂时不能更新，也不能在没有公钥的情况下放行任何清单。

> 养号系统那份 `config.json` 里 `updatePublicKey` 是空串，结果所有客户端静默
> 失去更新能力，还没人发现。这次把「没配公钥」做成显式的拒绝 + 启动日志告警，
> 就是要避免同一种沉默。

## 启用步骤

### 1. 生成密钥（只做一次）

```bash
node scripts/update-keygen.js ./keys
```

产出：

- `keys/update-signing.key` —— 私钥，**不要提交**（`.gitignore` 已拦）
- `keys/update-signing.pub.b64` —— 单行 base64 公钥

### 2. 填公钥

把 `update-signing.pub.b64` 的内容填进 `desktop/src/update/trusted-keys.js`：

```js
const PRIMARY = 'MCowBQYDK2VwAyEA...'
```

### 3. 服务端配私钥

```bash
export UPDATE_SIGNING_KEY="$(cat keys/update-signing.key)"
```

没配私钥时 `buildManifest` 返回 `null`，不下发清单 —— 不会发半成品。

### 4. 发版 + 发布

```bash
# 客户端（打包后）
node scripts/release-client.js \
  --version 1.3.0 \
  --url https://pixfanyi.com/downloads/HelloPix-Setup-1.3.0.exe \
  --file ./desktop/release/HelloPix-Setup-1.3.0.exe \
  --min-version 1.2.0
```

脚本从真实文件流式算 SHA256（已和 `shasum -a 256` 对过，逐字节一致），写进
`client_releases.sha256`。

`--min-version` 是**防降级**下限：签名只能证明「这是官方发的」，证明不了
「它比现在新」。攻击者可以重放一份旧但签名合法的清单，把用户拉回有已知漏洞的版本。

先用 `--dry-run` 看一眼也支持。

## 灰度：老服务端怎么办

`resolveRelease` 有三种结果：

| 状态 | 含义 | 处置 |
|---|---|---|
| `hardened` | 有签名清单且验签通过 | 正常 |
| `legacy` | 服务端还没升级，只有 version/url | 降级到白名单模式，**日志留痕** |
| `rejected` | 有清单但验不过 | 拒绝 + `error` 日志 |

允许 `legacy` 是为了灰度：新版客户端一上线就硬性要求签名的话，服务端发布脚本
没跟上时**所有用户会同时失去更新能力**，而他们手里的版本没有修复能力。

但这只是过渡。客户端和服务端都升级到位后，加环境变量关掉：

```bash
PIX_ALLOW_UNSIGNED_UPDATE=0   # 默认就是关的，不设即可
```

## 换钥必须走轮换

换了密钥，旧客户端只认内置的旧公钥，新公钥它们不认。

所以：

1. 生成新钥
2. `trusted-keys.js` 里：新钥 → `PRIMARY`，旧钥 → `PREVIOUS`
3. 发一版客户端，让用户升上来（这版新旧都认）
4. 服务端换新私钥开始签
5. 旧版本覆盖率足够低后，清空 `PREVIOUS`

跳过 2、3 直接换服务端私钥 = 所有旧客户端立即失去更新能力，而它们恰恰是最需要
被更新的那批。

## 测试

```bash
node --test test/update-signature.test.js      # 客户端侧：19 条，全是攻击形态
node --test test/update-signing-server.test.js # 服务端侧：11 条，含两端契约对撞
node --test test/ipc-app.test.js               # IPC 层：白名单 + 严格模式默认
```

`update-signature.test.js` 里每一条都是「应该被拒绝」的构造：篡改 url、篡改
sha256、换 appId、攻击者自己签、重放旧版本、截断签名、空公钥……

## 一个待办

`release-client.js` 新建记录时默认 `release_group=desktop / os=Windows / arch=x64`。
跑 macOS 发布必须用 `--os` / `--arch` 覆盖 —— 参考 `server/lib/release-arch.js`
里那次「Apple 芯片用户拿到 x64 包」的事故。

如果嫌麻烦，更稳的做法是只让它回填哈希（`--version` + `--file`，不带 `--url`），
发布记录仍由后台页面创建，避免脚本里的默认值把平台写错。
