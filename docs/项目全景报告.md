# 一、项目是什么

## 1.1 一句话

**给跨境电商客服用的多开翻译软件** —— 一台电脑同时登录几十个聊天账号，消息自动翻译，多客服协作不撞车。

## 1.2 解决什么

跨境电商卖家在 Telegram / WhatsApp 上同时运营多个账号与海外客户沟通，面临四个问题：

| 问题 | 表现 | 本项目的解法 |
|---|---|---|
| **语言不通** | 客户说日语、西班牙语、阿拉伯语，客服看不懂 | 消息自动翻译（9 个通道）|
| **账号多开** | 一个客服要同时盯十几个账号 | 桌面客户端多开（35+ 平台）|
| **客户重复** | 同一个人在不同账号出现，被多人重复跟进 | 统一客户身份 + 撞单检测 |
| **买粉被骗** | 引流商把同一批客户卖给多家 | 跨商户撞单检测（已设计，未启用）|

## 1.3 商业模式

**按字符计费**（不是按时长）。三档套餐：

| 套餐 | 价格 | 字符额度 | 通道 | 可切换 |
|---|---|---|---|---|
| 基础版 | $40 | 150 万 | 2 个 | ✗ 固定 |
| 高级版 | $75 | 150 万 | 4 个 | ✓ |
| 专业版 | $135 | 150 万 | 9 个（全部）| ✓ |

**收款**：TRC20 USDT（跨境、无拒付、手续费低）

## 2.4 三个关键架构决策

### 决策一：官网与主应用拆成两个入口

访客只为看一页官网，不该下载整个后台。

| | 拆分前 | 拆分后 |
|---|---|---|
| 官网首屏 | 365 KB | **79 KB** |
| | | **降 78%** |

### 决策二：客户身份共享，聊天内容隔离

```
        Customer C_100001      ← 身份层：平台级（只有指纹）
              │
    ┌─────────┴─────────┐
 商户 A                商户 B     ← 内容层：硬隔离
 账号A1 / 账号A2        账号B1
  └ 会话 └ 消息          └ 会话 └ 消息
```

**隔离三层**：表结构（内容表带 `user_id`）→ 静态测试（缺 `user_id` 即失败）→ 出口白名单（跨商户只返回匿名提示）

### 决策三：翻译通道可插拔

9 个通道统一抽象成 `{ translate, configured }`。新增通道只需实现这两个方法。

# 五、卡点问题

## 5.1 🔴 卡点一：邮件服务（唯一阻断注册的）

**现状**：注册接口已完整实现，但**邮件服务未配置**，新商户一个都注册不了。

实测：

```
POST /apis/user/emailCode
→ {"code":"MAIL_NOT_CONFIGURED","msg":"邮件服务尚未配置，请联系客服"}
```

**为什么卡**：需要 SMTP 账号，且**必须完成域名 SPF/DKIM 验证**。

**不验域名的后果很隐蔽**：邮件进垃圾箱 → 用户收不到验证码 → 注册不可用，**但后台看起来一切正常**。

**操作步骤**：

```
1. 阿里云邮件推送 https://www.aliyun.com/product/directmail
   （或腾讯云 SES / Resend）
2. 添加发信域名 pixfanyi.com
3. 按提示加 3 条 DNS 记录（SPF + DKIM）
4. 等验证通过
5. 创建发信地址 → 拿到 SMTP 密码（不是登录密码）
6. 填到后台「邮件服务」→ 点「发送测试邮件」实测
```

**预计**：30 分钟操作 + DNS 传播等待

## 5.2 🟠 卡点二：客户端从未真机验证

**现状**：客户端采集代码写完了，但**没在真实 Telegram / WhatsApp 上跑过**。

**为什么危险**：

```
如果 URL 格式与代码假设不符
        ↓
采集静默失效（失败不报错，因为不能影响翻译主流程）
        ↓
用户看不出问题，但 messages 表一直是空的
```

**这是最危险的失败模式** —— 没有报错、没有异常，只是数据一直是 0。

**验证方法**：Windows 电脑装客户端 → 真实 Telegram 登录 → 点几个会话 → 服务端查：

```sql
SELECT count(*) FROM messages;                              -- 应该 > 0
SELECT * FROM identity_match_events ORDER BY id DESC LIMIT 5;
```

**预计**：20 分钟

## 5.3 🟠 卡点三：收款地址

**现状**：`payment.channels` 为空，商户看到"收款方式尚未配置"。

**解法**：后台 → 收款方式 → 填 TRC20 地址

⚠️ **地址填错 = 资金永久丢失**。系统有校验和检查，但**识别不了"另一个同样合法的地址"** —— 保存后核对前 6 位和后 6 位。

**预计**：5 分钟

## 5.4 🟡 待决策：工单池本地化

**你的诉求**：建立工单池、录入本地数据、不上服务器。

**已确认**：本地 = 商户内网；不上服务器 = 聊天内容 + 客户身份

**绕不过去的取舍**：翻译必须走平台（平台持 Key、按字符计费），而翻译必须把原文发出去 —— **平台必然经手原文**。

| | 做法 | 平台能看到 |
|---|---|---|
| **A** | 平台代理但不落库 | 经手，不留存 |
| **B** | 商户自备 Key | 完全看不到，但计费改成按台/月 |
| **C** | 混合 | 视通道而定 |

**现状确实存了原文**：`translate_logs.snippet` = `text.slice(0, 300)`

**另一个必须纠正的认知**：本地化之后**跨商户撞单在技术上不再可能** —— 平台收不到任何客户标识，没有比对输入。

详见 `docs/工单池本地化-设计方案.md`
