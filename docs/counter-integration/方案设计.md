# 工单计数融合进 Hello Pix：技术方案

## 技术方案概述

采用“原生模块 + 服务端数据中心”方案，不嵌入旧计数软件窗口，也不在 Hello Pix 内再跑一套
Baileys 连接。

```text
WhatsApp WebContentsView
  └─ 页面世界事件观察器（登录后自动安装）
       └─ preload 固定频道
            └─ Electron 主进程（可信 tab 校验 + 本地待传队列）
                 └─ HTTPS /counter/inbound（复用 Hello Pix 会话）
                      └─ PostgreSQL 进粉事实表 + 全局客户身份
                           ├─ 1 条新粉/重粉流水
                           ├─ 1 张进粉工单
                           └─ 返回实时计数

Hello Pix 原生渲染层
  ├─ 计数台
  ├─ 重粉库
  └─ 进粉工单
```

## 为什么选这个方案

| 方案 | 结论 | 原因 |
|------|------|------|
| 把旧计数软件做成 iframe/webview | 不采用 | 两套登录、两套数据、独立令牌，界面和数据仍割裂 |
| 在 Hello Pix 内再跑 Baileys | 不采用 | 每个 WhatsApp 要重复配对，代理/设备冲突，资源翻倍，风控更高 |
| 只扫描当前聊天 DOM | 只能做降级 | 用户不在该聊天时不扫描，必然漏实时进粉 |
| 原生模块 + WhatsApp 页面事件 + 服务端判重 | 采用 | 复用现有登录、会话、代理和客户身份，能实时、全局、幂等 |

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| 桌面入口 | 现有 Electron renderer 原生页面 | 主题、登录、权限和发布链完全复用 |
| 消息观察 | WhatsApp 页面世界内部模型事件 + 能力发现 | 可监听所有私聊，不依赖当前打开哪个会话 |
| 降级观察 | 现有 DOM 扫描器 | 内部模块不兼容时至少保留当前聊天可见范围内的降级能力 |
| 数据中心 | 现有 PostgreSQL | 全局判重、并发事务、审计和历史归档需要强一致 |
| 实时缓存/限流 | 现有 Redis | 心跳、热点 KPI、可选实时推送 |
| 身份识别 | 现有 `platform_identities/customers` | 已有 HMAC 指纹、客户 ID、跨商户隔离基础 |
| 认证 | 现有 Hello Pix cookie 会话 + `X-Pix-Device` | 无邀请码、无新令牌、无第二套账号 |

## 架构设计

### 1. 页面世界事件观察器

新增 `desktop/src/translate/whatsapp-counter-observer.js`，跟随页面世界宿主脚本注入。

职责：

1. 仅运行在 `web.whatsapp.com`。
2. 通过 `requireLazy`/Webpack 缓存按能力寻找聊天集合和消息集合模块。
3. 订阅新增消息事件。
4. 只提取：
   - 本机消息 ID
   - 会话 ID
   - 手机号（可得时）
   - LID（可得时）
   - 是否本人发送
   - 是否群聊/广播/状态
   - 消息类型
   - 消息时间
   - 发送者昵称
5. 不读取、不发送聊天正文。
6. 找不到稳定内部事件接口时记录明确原因，并启用 DOM 降级扫描。
7. 模块结构变化时失败关闭，不猜测消息归属。

### 2. preload 与主进程

页面世界通过固定 `postMessage` 频道把事件交给 preload；preload 再走专用 IPC。

主进程负责：

- 用 `trustedTabSender` 确认事件确实来自受管 WhatsApp 实例。
- 注入可信的 `platform`、`counterAccountId`、设备 ID 和账号备注。
- 拒绝页面自报的商户号/账号归属。
- 对未确认事件写入本机待传队列。
- 服务端返回后立刻向渲染层推送计数更新。

### 3. 计数账号

每个启用“计数器”的 WhatsApp 多开实例对应一条 `counter_accounts` 记录。

不能继续只用 Hello Pix 用户名作为 `account_key`。当前客户端 `accountSlug()` 只返回用户名，
会把同一用户下所有 WhatsApp 实例合并成一个账号。计数模块必须使用：

```text
device_id + local_tab_id
```

由主进程生成稳定实例键，并在服务端登记成独立的 `counter_accounts.id`。

### 4. 服务端数据中心

服务端是全局新粉/重粉和工单的唯一权威。

一条事件的事务顺序：

1. 校验 Hello Pix 会话、设备绑定、计数账号归属。
2. 归一化手机号和 LID，生成 HMAC 指纹。
3. 对指纹按排序后的顺序获取 PostgreSQL advisory lock，保证并发串行。
4. 查找已有 `customer_identities`。
5. 多身份命中不同客户时执行客户合并。
6. 检查当前计数账号是否已计过该客户。
   - 已计过：`duplicate`，不增加计数，不建工单。
7. 检查该客户在**当前主账号**下是否已有进粉流水。
   - 不存在：`new`。
   - 已存在：`repeat`。
8. 插入唯一 `counter_fan_events` 流水。
9. 同事务插入唯一 `counter_tickets` 工单。
10. 返回事件 ID、公开客户号、当前账号次数、工单 ID 和最新 KPI。

### 5. 原生界面

不把隐藏的 `tickets` 平台（`127.0.0.1:8080`）作为正式入口。

新增“进粉中心”原生视图，包含：

- 计数台
- 实时流水
- 重粉库
- 进粉工单
- 计数账号设置

入口可放在系统操作/个人中心旁，打开时隐藏 WebContentsView；关闭后恢复原聊天。

“添加应用”里已有的“开启计数器”开关直接接线，不另造账号管理页面。

## 模块划分

| 模块 | 职责 | 依赖 |
|------|------|------|
| `whatsapp-counter-observer` | 监听 WhatsApp 新增私聊事件，输出身份骨架 | WhatsApp 页面世界 |
| `counter-bridge` | postMessage → preload → IPC，限制 payload | preload、主进程 |
| `counter-outbox` | 本机待传事件、重试、幂等键 | 主进程文件存储 |
| `counter-account-service` | 计数实例登记、启停、归档、心跳 | PostgreSQL |
| `counter-identity-service` | 手机号/LID 合并、并发判重、客户归档 | 现有客户身份系统 |
| `counter-service` | 进粉流水、KPI、重粉库 | PostgreSQL |
| `counter-ticket-service` | 自动建单、状态机、指派、SLA | PostgreSQL |
| `counter-ui` | 计数台、重粉库、工单页 | renderer、IPC |

## 接口设计

所有接口都在现有 `/apis` 会话体系内，不使用邀请码或独立 Bearer Token。

### 1. 登记计数账号

```text
接口名称：登记/更新计数实例
请求方式：POST
请求路径：/api/counter/accounts/register
请求参数：
  - localTabId (string, 必填): 当前进程内的稳定标签 ID
  - platform (string, 必填): whatsapp-green / whatsapp-pro / whatsapp-biz
  - label (string, 必填): 用户可识别的账号备注
  - enabled (bool, 必填): 是否开启计数
响应：
  {
    "id": "counter-account-uuid",
    "deviceId": "desktop-...",
    "heartbeatSeconds": 30
  }
```

服务端从会话获取 `user_id`、主/子账号身份；客户端不得自报。

### 2. 入站事件

```text
接口名称：进粉事件接入
请求方式：POST
请求路径：/api/counter/inbound
请求头：
  - Idempotency-Key: <counterAccountId>:<sourceMessageId>
请求参数：
  - counterAccountId (string, 必填)
  - sourceMessageId (string, 必填)
  - peerKey (string, 必填)
  - phone (string, 可选): 带国家码手机号
  - platformUid (string, 可选): WhatsApp LID 或其他稳定标识
  - pushName (string, 可选)
  - messageType (string, 必填)
  - sentAt (ISO datetime, 必填)
响应：
  {
    "status": "new | repeat | duplicate | ignored",
    "eventId": 123,
    "customerId": "C_100123",
    "times": 2,
    "ticketId": 456,
    "summary": {
      "todayNew": 18,
      "todayRepeat": 3,
      "allNew": 220,
      "uniqueCustomers": 201
    }
  }
```

### 3. 计数与流水

```text
GET /api/counter/summary?from&to&accountId
GET /api/counter/events?from&to&accountId&kind&page&rows
GET /api/counter/repeats?from&to&page&rows
GET /api/counter/accounts
POST /api/counter/accounts/:id/archive
```

### 4. 进粉工单

```text
GET  /api/counter/tickets?status&priority&assignee&from&to&page&rows
GET  /api/counter/tickets/:id
POST /api/counter/tickets/:id/transition
POST /api/counter/tickets/:id/reply
POST /api/counter/tickets/:id/assign
```

工单正文、内部备注和操作者都必须落 `counter_ticket_events`，只追加不修改。

## 数据模型

### `counter_accounts`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | bigint identity | 主键 |
| `user_id` | bigint | 主账号，外键 `users.id` |
| `operator_id` | bigint nullable | 子账号，外键 `sub_accounts.id` |
| `device_id` | text | Hello Pix 设备 ID |
| `local_tab_id` | text | 桌面多开实例 ID |
| `platform` | text | WhatsApp 平台类型 |
| `label` | text | 运营备注名 |
| `enabled` | bool | 当前是否计数 |
| `last_seen_at` | timestamptz | 心跳 |
| `archived_at` | timestamptz nullable | 删除/归档时间 |

唯一：`(user_id, device_id, local_tab_id)`。

### `counter_fan_events`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | bigint identity | 流水主键 |
| `user_id` | bigint | 商户隔离键 |
| `counter_account_id` | bigint | 计数实例 |
| `customer_id` | bigint | 全局客户 |
| `kind` | text | `new` / `repeat` |
| `source_message_id` | text | WhatsApp 消息 ID |
| `phone_tail` | text | 后四位，界面识别用 |
| `push_name` | text | 昵称 |
| `message_type` | text | text/image/audio... |
| `first_msg_at` | timestamptz | 消息时间 |
| `day` | date | 客户端本地日 |
| `created_at` | timestamptz | 服务端入库时间 |

唯一：

- `(counter_account_id, customer_id)`：一个账号对同一客户只计一次。
- `(counter_account_id, source_message_id)`：同一条消息只处理一次。

索引：`(user_id, day)`、`(customer_id)`、`(counter_account_id, first_msg_at)`。

### `counter_tickets`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | bigint identity | 主键 |
| `code` | text | `IT-YYYYMMDD-0001` |
| `user_id` | bigint | 商户 |
| `counter_account_id` | bigint | 来源账号 |
| `customer_id` | bigint | 客户 |
| `fan_event_id` | bigint | 一对一关联流水 |
| `status` | text | open/in_progress/pending/resolved/closed |
| `priority` | text | normal/high/urgent/low |
| `assignee_id` | bigint nullable | 子账号 |
| `due_at` | timestamptz | 首响截止 |
| `resolve_due_at` | timestamptz | 解决截止 |
| `created_at/updated_at` | timestamptz | 时间 |

唯一：`fan_event_id`。

### `customer_identity_aliases`

为避免手机号与 LID 指向不同客户，补充别名映射：

| 字段 | 类型 | 说明 |
|------|------|------|
| `fingerprint` | bytea | HMAC 指纹 |
| `customer_id` | bigint | 当前规范客户 |
| `source` | text | phone / whatsapp_lid |

若后续发现数据库已有等价的 `customer_identities` 可表达同一语义，不新增重复表；
实现时优先扩展现有表，避免两套身份真源。

## 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 旧计数软件载体 | 不嵌入整套 | 独立数据库和令牌会让“全局”失效 |
| WhatsApp 接入 | 复用当前 WebContentsView 会话 | 不重复扫码，不新增 Baileys 风险 |
| 实时事件源 | 内部模型事件优先，DOM 降级 | 后台聊天也必须实时 |
| 全局判重 | PostgreSQL 事务 + advisory lock | 避免并发双新粉 |
| 工单真源 | 服务端事务内建单 | 客户端崩溃也不会出现“有流水无工单” |
| 本地离线 | 主进程待传队列 | 网络抖动不丢粉 |
| 删除账号 | 归档计数实例，不删历史 | 当前汇总归零，数据中心保留 |
| 客服工单与进粉工单 | 完全分表分页 | 语义、权限、状态机均不同 |
| UI 形态 | renderer 原生页 | 主题、权限和交互一致，不做 localhost iframe |

## 实施计划

### 第一阶段：可验证骨架

1. 新增数据库迁移和 `counter-*` 服务。
2. 完成手机号 + LID 身份归一化、并发判重和幂等单测。
3. 完成服务端新粉/重粉/重复联系及自动建单事务测试。

### 第二阶段：真机事件链

1. 对当前 WhatsApp Web 版本做只读能力探针，确认消息集合事件名称。
2. 实现页面世界观察器，先只记录日志，不上报计数。
3. 用两个 WhatsApp 实例做后台标签页真实入站测试。
4. 通过后再接主进程队列和服务端。

### 第三阶段：原生 UI

1. 接通“开启计数器”开关。
2. 增加“进粉中心”入口和计数台。
3. 增加重粉库和进粉工单页面。
4. 删除隐藏的 `127.0.0.1:8080` 计数工单平台入口。

### 第四阶段：发布

1. 真机验收：新粉、重粉、重复联系、LID 后补号码、并发判重、断网补传、删号清零。
2. 三平台构建与签名。
3. 服务端和客户端同时升级，保留关闭开关和回滚路径。

## 风险与待确认

1. WhatsApp Web 内部消息事件不是公开接口，必须在当前版本做真机探针；失败时只能降级为当前聊天 DOM 扫描，无法保证后台聊天实时。
2. “全局重粉”默认只在同一 Hello Pix 主账号下跨设备、跨子账号生效；
   跨独立商户共享客户线索默认关闭。若后续确实需要全平台匿名判重，必须单独做隐私授权。
3. 旧计数软件历史数据是否必须导入；若必须，需要提供旧设备 ID/账号备注与 Hello Pix 主账号的对应关系。
4. 进粉工单的负责人是否直接复用 Hello Pix 子账号。建议直接复用，不另建客服表。
