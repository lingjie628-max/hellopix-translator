## 复测 1（P0-1）重试翻译必须最终成功发送

**制造一次失败**（任选其一，挑最容易复现的）：

- 翻译通道未接通 / 余额不足（后台临时改一下即可）；
- 或在按回车的瞬间断开网络，让 `/translate/run` 失败。

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| 1 | 输入一句**中文**，按回车 | 被拦下（**对方什么都收不到**），弹出失败提示 |
| 2 | 看提示 | 提示里应有 **「错误码：XXXX」** 一行（真实原因，不是笼统的「翻译状态异常」） |
| 3 | 恢复条件（接通通道 / 联网） | — |
| 4 | 点「**重试翻译**」 | 立刻显示「正在重试…」 |
| 5 | 等结果 | **重试真正进入发送链并成功发送最终译文**；提示自动收起；**不再出现 `BODY_MISMATCH`** |

**FAIL 判据（任一即 FAIL）**：又回到「重试失败」；提示里出现 `BODY_MISMATCH`；
对方收到**中文原文**；对方收到 `[正在翻译中...]` 之类的占位符；**同一条发了两次**；重复扣费。

### 这一轮做了什么（为什么这次不再 `BODY_MISMATCH`）

真机轨迹是：`RETRY_TRANSLATE_CLICK → … → INPUT_REPLACED` 都过了，**最后**才报
`BODY_MISMATCH`。也就是**写入成功之后，正文又被改掉了** —— WhatsApp 的输入框是
React/Lexical 托管编辑器，它会用**自己的状态**在下一次调和时重画 DOM。老实现
「写一次就算数、等 50ms 只看一眼」，正好撞上这次重画，于是判失败。

本轮改了三件事：

1. **严格 canonical 化再比对**（新增 `canonicalizeSendBody()`）：
   只放行**无语义差异** —— `CRLF/LF` 统一、`NBSP`(U+00A0)/窄空格/全角空格 → 普通空格、
   必要零宽字符清理（U+200B/200C/200D/2060/FEFF/180E）、Unicode 归一化 `NFC`。
   **文字 / 数字 / URL / 标点 / 换行结构的真实变化一律照判不等**，安全校验一点没放松。
2. **发送前沉降期 + 就地自愈**：写入 → 等待 → canonical 比对 → **不一致就重写** → 再验（最多 3 轮）。
   这正是把「被页面还原的正文」救回来的动作。
3. **完整差异取证**：`BODY_MISMATCH` 时落 `SEND_BODY_MISMATCH_DETAIL` ——
   预期/实际的长度与 hash、canonical 前后文本、**首个差异位置**、
   输入框 `tag/class/contenteditable`、**写入方式**、**是否触发 input/beforeinput**。

守住的三条底线（明确禁止越线）：

- ❌ 不删 `BODY_MISMATCH` 校验；❌ 不改成「只要不为空就发」；❌ mismatch 时**不自动发原文**。
- `canonical` 后仍不一致 → **fail closed，不发送任何内容**（并显示真实错误码）。
- 有用户草稿时（正文既不是最终译文、也不是我们捕获的原文）**绝不重写**，优先保住用户正在打的内容。

## 复测 2（P0-3）短消息的「译」按钮必须始终可见、可点

**前提**：一个**群聊**（翻译模式 = 手动），群里准备**下面每种**消息各一条。

| 必测样本 | 覆盖点 |
|---|---|
| 1~3 个字的超短消息（如 `Hi` / `OK` / `好`） | 最容易和右下角挤在一起 |
| 单行短消息（如 `Good morning.`） | 单勾/双勾紧贴正文 |
| 多行长消息 | 布局不能因增高而错位 |
| incoming（对方发的） | `message-in` 侧 |
| outgoing（自己发的） | `message-out` 侧 + 自己的勾 |
| 带时间（含带单勾 / 带双勾 / 已读） | 直接验证不被 metadata 遮挡 |
| 带 emoji | 正文 span 分片 |
| 带 URL | 正文被 linkify 成 `<a>` |

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| 1 | 逐条看「译」按钮 | 每条都**完整可见**，不被时间 / 单勾 / 双勾 / 已读状态盖住 |
| 2 | 逐条点「译」 | 每条都**能点动**（不是"看得见、点不动"） |
| 3 | 点击后看状态 | 按钮在同一位置变「翻译中…」，成功后变「已翻译」，失败变「翻译失败 · 点击重试」 |
| 4 | 看顺序与正文 | 阅读顺序始终是 **正文 → 操作行（按钮）→ 译文**；按钮**不遮正文**、**不遮时间/勾** |

**FAIL 判据（任一即 FAIL）**：任一短消息的按钮被时间/勾盖住或点不动；
不同状态跳到不同位置（例如「翻译中…」跑到了别处）；译文压住正文或时间/勾。

### 这一轮做了什么（为什么这次不会被盖住）

老实现把入口**内联贴在正文尾部**，而 WhatsApp 的时间 / 单勾 / 双勾是贴在气泡
**右下角**的（绝对定位 / 右对齐）。正文一短，两者就叠在同一块区域 → 按钮被盖住。

本轮把入口搬进**正常文档流**里的独立容器 `.pix-trans-action-row`：

```css
.pix-trans-action-row { display:block; clear:both; width:100%; flex-basis:100%;
                        position:static; margin:6px 0 0; text-align:left; }
.pix-click            { display:inline-flex; position:static; pointer-events:auto !important; }
```

- 入口在**当前消息气泡内**、位于**正文下方**、**整行块单独成行** → 气泡自然增高，
  结构上不可能与右下角的 metadata 同排或重叠；
- **不用绝对定位、不用 `right/bottom`、不用叠加层级（z-index）、不用负 margin** 去抢 metadata 区域；
- **不**把按钮挪到聊天根节点、**不** append 到 `#main` / `msg-list` / conversation root；
- 仍然沿用已经通过的 **`data-id` / messageKey → 精确 message bubble** 绑定机制；
- **所有状态（译 / 翻译中… / 已翻译 / 翻译失败·重试）都在同一个 action row 里**，位置统一、绝不跳位。

## 取证（可选项，但强烈建议顺带采一次）

```bash
bash rc018-collect.sh before
# 做复测 2（先测布局，纯前端、不依赖服务端）
bash rc018-collect.sh after-B-03-short-chip
# 做复测 1（制造失败 → 重试）
bash rc018-collect.sh after-A-01-retry
```

把生成的 `rc018-evidence-<电脑名>.txt` 整个发回即可（脚本只读、不含口令）。
它会重点抽出这几行，正是判定两个 P0 的直接证据：

| 事件 | 说明 |
|---|---|
| `MANUAL_CHIP_RENDERED` | 含 `inActionRow:true` → ✅ 入口确实住进了操作行（P0-3 的直接证据） |
| `RETRY_TRANSLATE_CLICK` | 点下「重试翻译」（带新的 `sendActionId`） |
| `RETRY_TRANSLATE_RESULT` | 重试收口 + **真实错误码** |
| `INPUT_REPLACED` | 译文写入成功 |
| `INPUT_REWRITTEN` | ✅ **正文被页面还原后就地重写**（0.1.18 修 `BODY_MISMATCH` 的关键动作） |
| `FINAL_TEXT_VALIDATED` | 发送前最后一道正文校验（`ok:true` 才算过） |
| `SEND_BODY_MISMATCH_DETAIL` | ❌ 若出现：预期/实际长度·hash、首个差异位、写入方式、input 事件是否触发 |
| `PROGRAMMATIC_SEND_BEGIN` / `_DONE` | 程序化发送开始/结束（只应各出现一次） |

本地分诊：

```bash
node scripts/rc-trace-triage.js rc018-evidence-<电脑名>.txt
```
