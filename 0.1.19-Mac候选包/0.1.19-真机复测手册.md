## 复测（P0-1）发送翻译必须走原生输入、编辑器认可、稳定发送

**准备**：任意一个能正常翻译的聊天（私聊 / 群聊均可）。

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| 1 | 输入一句**中文**，按回车 | 被拦下；输入框短暂显示译文；**对方收到的是英文译文** |
| 2 | 看对方收到的内容 | 只有**一条**；内容是**译文** |
| 3 | 连发 3 条不同的中文 | 3 条都发出、都是各自译文、不串行、不丢 |
| 4 | 制造一次翻译失败（断网 / 后台停通道）后点「**重试翻译**」 | 重试**真正进入发送链并成功**发送最终译文；**不再出现 `BODY_MISMATCH`** |

**FAIL 判据（任一即 FAIL）**：

- 又出现 `BODY_MISMATCH`（无论首发送还是重试）；
- 对方收到**中文原文**；
- 对方收到 `[正在翻译中...]` 之类的占位符；
- 同一条发了两次 / 重复扣费；
- 在**等翻译期间**你打了下一条 → 这一条虽然没发，但**你的新草稿被覆盖 / 丢失**。

### 这一轮改了什么（为什么这次不会再被 Lexical 盖回去）

真机 0.1.18 日志把根因钉死在**事件可信性**上：

```
writeMethod:"execCommand:insertText"  sawBeforeInput:false  sawInput:true
expected: len=29 hash=33aaf90e  "Test translation information."
actual  : len=6  hash=3a49c2d5  "测试翻译信息"
```

`execCommand` / `textContent` 这类**页面内改 DOM** 产生的是 **untrusted** 事件。
WhatsApp / Lexical 在**捕获阶段直接过滤掉 untrusted `beforeinput`**（所以
`sawBeforeInput:false`），译文从未进入它的输入管线、也没更新 `EditorState`。
下一次调和时它按**自己的状态**重画 DOM → 正文退回原文 → `BODY_MISMATCH`。
连续重写 3 次仍然失败，正因为每次写进去的东西它都不认。

0.1.19 改成**从 Electron 主进程发 Chromium 原生编辑命令**（事件由浏览器进程发起，
`isTrusted:true`，编辑器必须处理）：

```
translation result
  → native composer focus
  → 原生 selectAll
  → 原生 delete（清空）
  → webContents.insertText(translatedText)
  → Lexical 自己完成 input/update（0ms / 100ms / 300ms / 500ms 漂移采样确认稳定）
  → 回读 DOM + canonicalizeSendBody 比对
  → 通过后才触发一次原生发送
```

对应 trace（必须按这个顺序出现）：

```
NATIVE_INPUT_BEGIN → COMPOSER_CLEARED → NATIVE_TEXT_INSERTED
  → (COMPOSER_DRIFT_SAMPLE ×4) → LEXICAL_SETTLED
  → INPUT_REPLACED → FINAL_TEXT_VALIDATED ok=true → PROGRAMMATIC_SEND_DONE
```

### 守住的三条底线（明确禁止越线）

- ❌ 不删 `BODY_MISMATCH`；❌ 不改成「只要不为空就发」；❌ mismatch 时**不自动发原文**。
- 原生写入后正文仍不一致 → **fail closed，一个字节都不发**（弹真实错误码）。
- 写入前先确认**当前框里仍是本次原文**：如果你已经打了新内容 → **立即中止**，
  这一条不发送，且**一个字节都不动**你的新草稿（宁可漏发一条，也不吃你正在打的内容）。
- 初次发送、重试、失败兜底、发送原文**共用同一条原生写入管线**，不存在第二套写法。

## 取证（强烈建议顺带采一次）

```bash
bash rc019-collect.sh before
# 做复测（正常发一条中文）
bash rc019-collect.sh after-send
# 制造失败 → 点「重试翻译」
bash rc019-collect.sh after-retry
```

把生成的 `rc019-evidence-<电脑名>.txt` 整个发回即可（脚本只读、不含口令）。
它会重点抽出下面这些行，正是判定 P0-1 的直接证据：

| 事件 | 说明 |
|---|---|
| `COMPOSER_STILL_SOURCE` | 写入前确认：框里还是本次原文（没被用户改过）→ 允许替换 |
| `NATIVE_INPUT_BEGIN` | 原生输入开始（带 expected 的 len/hash/canonicalLen） |
| `COMPOSER_CLEARED` | ✅ 原生 selectAll + delete 生效（`ok:true`） |
| `NATIVE_TEXT_INSERTED` | ✅ `insertText` 生效，回读 hash == 译文 hash |
| `COMPOSER_DRIFT_SAMPLE` | 0 / 100 / 300 / 500ms 逐点回读：**每一点都 `equal:true`** |
| `LEXICAL_SETTLED` | ✅ 沉降完成且 `stable:true` / `canonicalEqual:true`（无晚期漂移） |
| `FINAL_TEXT_VALIDATED` | 发送前最后一道正文校验（`ok:true` 才算过） |
| `SEND_BODY_MISMATCH_DETAIL` | ❌ 若出现：预期/实际 len·hash、首个差异位、`writeMethod`、input 事件 |
| `PROGRAMMATIC_SEND_BEGIN` / `_DONE` | 程序化发送开始/结束（只应各一次） |
| `COMPOSER_LEFT_AS_IS` | ℹ️ 你已改草稿 → 主动放弃覆盖（正确行为，不是 bug） |

本地分诊（会直接给出「原生输入链完整 / 断在哪」）：

```bash
node scripts/rc-trace-triage.js rc019-evidence-<电脑名>.txt
```
