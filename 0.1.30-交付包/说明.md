# Hello Pix 0.1.30 交付说明

> 修的是：**一个账号开到 18 个左右的实例，再开第 19 个整个应用直接闪退**。
> 结论先行：不是逻辑限制写错了，也不是内存不够，而是**文件句柄被开光**。

---

## 一、用户现象

> 一个账号只能开 18 个左右的应用窗口，继续开更多新窗口就会**闪退**。

关键特征：**闪退，不是报错**。没有任何提示、没有任何日志、窗口直接消失。

这三条特征本身就指向了根因 —— 见下。

---

## 二、根因（真 Electron 实测，不是推断）

### 2.1 每个实例吃掉多少句柄

跑真 Electron、真 `WebContentsView`、真独立分区，逐个计句柄：

```
基线 句柄=39
#1  → 64     (+25)
#2  → 88     (+24)
#3  → 112    (+24)
#4  → 136    (+24)
...
#20 → 520    (+24/个)
```

**线性 24 个/实例。**

### 2.2 为什么"18 个"是那个数字

句柄是**进程级硬上限**：

| 平台 | 约束 |
|---|---|
| macOS / Linux | `ulimit -n`（图形应用常见 256 ～ 10240） |
| Windows | 进程 HANDLE 配额 + Chromium 内部上限 |

```
基础开销（Electron 自身 + 界面）  ~ 150 句柄
18 个实例 × 24                    ~ 432
                                  ─────────
                                  ~ 582   ← 正好落在常见上限附近
```

再加一个，就踩线了。

### 2.3 为什么是"闪退"而不是"报错"

**这才是这个 bug 最坑的地方。**

Chromium 在**渲染进程创建路径**上碰到 `EMFILE`（too many open files）
**不是抛错，而是直接终止进程**。所以：

- 用户看不到"开不了"的提示 —— 进程已经没了
- 客户端日志里也没有异常 —— 来不及写
- 看起来像"开了 18 个之后就随机崩"

### 2.4 还有一个隐藏的加重因素

实测：每次"开→关"一轮，**永久泄漏约 8 个句柄**（Electron 33 的原生行为，
强制 GC 也回收不了 —— 释放引用 + `gc()` ×3 后句柄数纹丝不动）。

```
反复开关 30 次 → 句柄净增 242，平均 8.1/次
```

所以长期使用中，**即使当前窗口数不到 18**，剩余额度也可能被历史开关吃掉。
这解释了为什么有的用户"开到 12 个就不行了"。

---

## 三、为什么不用"把上限调大"

能想到的第一反应是 `ulimit -n 65535`。但这不解决问题：

1. 上限**终究存在**，只是把 18 推后到 100；
2. 各平台改法完全不同（Windows 根本没有 POSIX ulimit）；
3. 打包后的应用拿到的软限制**比开发时更低**，改了也不一定生效；
4. 用户会继续开到新的上限，然后**还是闪退**。

**真正的修法是：在触顶之前拒绝，并明确告诉用户为什么。**

崩溃时用户什么都看不到；主动拒绝时用户知道"该关几个了"。

## 四、代码改动

### 4.1 新增 `desktop/tab-budget.js`

| 判据 | 规则 | 为什么 |
|---|---|---|
| 窗口数上限 | `MAX_TABS_PER_WINDOW = 20` | 跨平台一致、用户能理解、远低于任何平台的句柄上限 |
| 句柄水位 | 剩余 < `每实例预算(26)` + `安全余量(96)` → 拒绝 | 创建有**瞬时峰值**，余量打光会崩在"半途"，那时再想优雅收尾已晚 |
| 测不出来 | **一律放行** | 宁可让用户试，也不要无故拦住 |

实测每实例 19.2 ～ 24 个句柄，预算按 **26** 算 —— 宁早拒，不晚崩。

### 4.2 `openPlatform()` 前置检查

```js
const budget = tabBudget.canOpenAnotherTab({
  tabCount: tabs.length,
  maxTabs: MAX_TABS_PER_WINDOW,
  used: tabBudget.openHandleCount(),
  limit: tabBudget.handleLimit()
})
if (!budget.ok) { showResourceNotice(budget.reason); return { success: false, ... } }
```

**在创建任何 Chromium 对象之前**完成判断。

拒绝时弹**原生对话框**而不是渲染层弹窗 —— 因为主界面是 `WebContentsView`
**盖**在渲染层上方的原生视图，渲染层弹的东西会被完全挡住；而这个提示出现的
场景恰恰是"窗口已经很多"，那时用户眼前全是实例页面。

### 4.3 `destroyTab()` 收尾加固

| 改动 | 为什么 |
|---|---|
| 接住 `releaseSocksRelay()` 的 promise | 它是 async（要等监听端口真正释放）。原先漂浮在事件循环上，端口与句柄晚一步才还 |
| 销毁前 `removeAllListeners()` | 销毁后仍挂着的监听器会一直持有 webContents 引用，让原生对象多活很久 |
| 断开 `tab.view` 引用 | 让 JS 侧对象图尽早可回收 |

### 4.4 顺带修掉一个**会让安装包启动即崩**的坑

新增的 `tab-budget.js` **必须**登记进 `package.json` 的 `build.files`，
否则打包后 `require` 失败 → 窗口都建不出来。

**这是回归测试先发现的**（既有的"打包白名单"用例直接报红）。
已加入白名单 + 补了一条专门的测试锁死它：

```
✖ tab-budget.js 在打包白名单里（漏了会让安装包启动即崩）
  → 修复后 ✔
```

## 六、真机复测步骤

### 1. 【核心】开到上限提示，而不是闪退

1. 开一个 WhatsApp 实例，反复点「+」开新实例，开到 20 个。
2. 再点一次「+」。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 表现 | 弹**原生提示框**「无法再开新窗口」 | 应用闪退 |
| 提示内容 | 说明"最多 20 个"并让用户"关掉几个" | 什么都没说 |
| 应用状态 | **照常可用**，已开的 20 个窗口正常工作 | 进程没了 |
| 日志 | `resource` 一行 warn 记录原因 | 无记录 |

### 2. 【核心】关掉几个之后能继续开

关掉 3 个实例，再点「+」→ 应能正常开出第 21 个（因为当前只有 18 个）。

### 3. 【回归】反复开关不再加速触顶

连续"开一个 → 关一个" 10 轮，再开到 19 个，应仍能正常开
（收尾加固让句柄回收更及时）。
