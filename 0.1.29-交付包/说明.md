# Hello Pix 0.1.29 交付说明

> 本次修的是**两个看起来不相关、实际同根**的真机 P0。
> 根因一句话：**一次坏节点的「节点检测」会把整个应用弄瘸，之后所有新开的实例都起不来。**

---

## 一、用户报的两个现象

| # | 现象 | 谁来报的 |
|---|---|---|
| 1 | 点「节点检测」→ **永远停在"正在检测节点…"**，连错误都不给 | Windows，多个用户 |
| 2 | 打开新的 WhatsApp 实例 → 页面顶部红色横幅 **「翻译组件未启动」** | Windows |

## 二、根因（真机 + 真 Electron 复现）

这两个现象是**一条故障链**的两端。

```
上游 SOCKS5 节点 TCP 连得上，但握手阶段不回任何数据
        │
        ▼
Chromium 卡在 SOCKS5 握手内部
（did-finish-load / did-fail-load / render-process-gone **一个都不触发**）
        │
        ▼
15 秒超时后清理，直接 destroy() 掉还卡在握手的窗口
        │
        ▼
★ 把 Electron 的渲染进程基础设施弄坏 ★
（日志：bootstrap_look_up … MachPortRendezvousServer: Permission denied
        No rendezvous client, terminating process）
        │
        ├──► 现象 1：此后**任何**检测都创建不出可用窗口 → 永远"正在检测"
        │
        └──► 现象 2：此后**任何**新实例的 preload 都跑不起来
                     → 8 秒内等不到 guest 第一次通信
                     → 渲染层与本页都判定「翻译组件未启动」
```

### 复现证据（真 Electron，修复前）

```
--- 老实现：直接创建探测窗口并等超时 ---
  探测超时
--- 之后：新建一个【带 preload 的 WebContentsView】（模拟新开 WhatsApp 实例）---
（什么事件都没有 —— 卡死了，连 loadURL 都不返回）
```

**一次坏节点的检测，之后新开的 WhatsApp 实例全部起不来。** 这就是现象 2。

### 修复后同一实验

```
--- 新实现：先预检（不创建任何窗口）---
  第1次预检: false | 节点无响应（1 秒内没有回话） | 1207ms
  第2次预检: false | 节点无响应（1 秒内没有回话） | 1206ms
  第3次预检: false | 节点无响应（1 秒内没有回话） | 1204ms
--- 之后：新建一个【带 preload 的 WebContentsView】---
  did-finish-load ✔   ★ 新实例正常启动
```

## 三、代码改动

### 1. `desktop/socks-relay.js`

**新增 `precheckSocks5(options)` —— 在用 Chromium 之前，用纯 Node 把节点验掉。**

完整走一遍真 SOCKS5 协议：
1. TCP 连接
2. 问候（同时提供「无认证」与「用户名/密码」）
3. 若要认证 → 走 RFC1929 用户名/密码子协商
4. **真的发起一次 CONNECT**（`api.ipify.org:443`）并等 reply

> 为什么要真的 CONNECT：有的节点问候/认证都正常，但 CONNECT 之后**不回 reply**
> （假死、被限流、隧道没通）。这种节点放进 Chromium 就会卡住渲染进程 —— 正是要根除的现场。

失败一律返回**明确错误码 + 中文原因**：

| code | 含义 |
|---|---|
| `TIMEOUT` | 节点无响应（8 秒内没有回话） |
| `ECONNREFUSED` | 节点拒绝连接（端口没人监听） |
| `AUTH_REJECTED` / `AUTH_REQUIRED` | 认证方式不接受 / 没填账密 |
| `AUTH_FAILED` | 账号或密码不对 |
| `NOT_SOCKS5` | 这个端口不是 SOCKS5 代理 |
| `CONNECT_REFUSED` | 节点拒绝/无法完成 CONNECT |
| `BAD_TARGET` | 代理地址无效 |

**新增 `HANDSHAKE_TIMEOUT_MS`（8 秒）** —— 任何握手步骤都不许"永远 pending"。

### 2. 修掉一个**隐藏更深的 bug：带认证的好节点被误判成坏节点**

预检第一版用 `socket.once('data', …)` 处理认证应答，外层再挂一个常驻
`socket.on('data')`。**Node 会把同一份数据分发给所有监听器** —— 于是认证应答
（首字节 `0x01`）也被外层当成"首个数据包"解析，`buf[0] !== 0x05` → 误判 `NOT_SOCKS5`。

**结果：所有 `socks5_auth`（要账密）的节点，无论好坏，一律报"这个端口不是 SOCKS5 代理"。**
这与用户报的「socks5 带认证 · 检测不出来」完全对得上。

已改为**单一 `data` 处理器 + 显式阶段状态机**（`greeting → auth → connect → done`）。
新增回归用例：`好节点（要认证、账密正确）→ 判可用`。

### 3. 修掉一个"只有错误路径才炸"的 TDZ

`finish()` 里 `clearTimeout(timer)`，但 `timer` 声明在"地址非法"提前 return 之后。
地址非法时会抛 `ReferenceError: Cannot access 'timer' before initialization`。
已把 `let timer = null` 提到 `finish` 之前。

### 4. `desktop/main.js`

- `detectProxyNode`：SOCKS5 先跑 `precheckSocks5`，**不可用就直接返回，根本不碰 Chromium**。
- `probeTextWithProxy`：窗口清理改温柔 —— 先 `wc.stop()` + 摘监听器，再延迟 destroy。

## 五、真机复测步骤（Windows 重点）

1. **准备一个坏节点**：填入一个 `socks5://` 且带账密的地址（端口连得上但不通）。
2. 点「节点检测」。
   - ✅ 期望：**8 秒内**返回失败，并给出中文原因（如"节点无响应"）。
   - ❌ 不允许：一直转圈、没有任何提示。
3. **紧接着**开一个新的 WhatsApp 实例。
   - ✅ 期望：页面正常加载，**没有**「翻译组件未启动」横幅。
   - 到聊天页发一条中文，确认翻译照常。
4. **换一个正常的 SOCKS5 带认证节点**，再点检测。
   - ✅ 期望：能检测成功（这是本次一并修掉的"误判"问题）。

```bash
bash rc029-collect.sh
```
