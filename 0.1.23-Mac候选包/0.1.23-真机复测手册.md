# 0.1.23 Mac arm64 候选 — 真机复测手册（两项修复）

> 本轮修**两个**真机缺陷，都在 `desktop/guest-inject.js`：
>
> | # | 现象 | 根因 |
> |---|---|---|
> | **A** | 翻译失败时气泡上写死「翻译失败 · 点击重试」，明明是连不上服务器 | chip 文案**不带错误码** |
> | **B** | **私聊也必须一条条手动点「译」**，自动翻译整个失效 | `isGroupChat()` 把**私聊判成了群** |
>
> ### 缺陷 B 的取证（真机日志，2026-10-10）
>
> ```
> trigger=manual_click : 21 次
> trigger=manual_send  :  6 次
> trigger=auto_receive :  1 次   ← 自动翻译全天只成功触发过 1 次
> ```
>
> 根因：老 `isGroupChat()` 第一条判据是 `document.querySelector('.ChatInfo, header')`
> —— 查的是**整个文档**，而 document order 上排在 `#main` **之前**的就是
> **左侧会话列表**的 header。中文界面的会话列表 header 里带着
> 「全部 / 未读 / 收藏 / **群组**」筛选标签 → 正则命中 `群组`
> → **每一个会话（含私聊）都被判成群** → 私聊自动翻译全部失效。
>
> 开关语义（`renderer/index.html`）：**「群聊自动翻译」只对群消息生效**；
> 私聊**始终自动翻译**。本轮的判据严格实现这条语义。
>
> ### 期望行为（本轮要验证的目标）
>
> | 会话类型 | 自动翻译 |
> |---|---|
> | **私聊** | **始终自动**（与「群聊自动翻译」开关**无关**） |
> | **群聊** | 跟随「群聊自动翻译」开关：开=自动；关=只给「译」按钮（半自动） |
>
> 本机是 Apple 芯片 → 用 **arm64** 包。
> **本轮不上架、不建 RELEASE、不发布正式版本、不动套餐/代理/群组/子账号/Windows。**

## 一、本轮改了什么

### 修复 A — 失败 chip 按错误类别说话

`desktop/guest-inject.js`

1. 新增错误码 → 文案映射（认不出的码一律退回默认）：

   | 错误码 | chip 显示 |
   |---|---|
   | `NETWORK_UNREACHABLE` | **连不上服务器 · 点击重试** |
   | `NETWORK_TIMEOUT` | **服务器超时 · 点击重试** |
   | `SERVER_BAD_RESPONSE` | **服务器异常 · 点击重试** |
   | `INSUFFICIENT_CHARS` | **余额不足 · 点击重试** |
   | `ENGINE_NOT_ALLOWED` / `ENGINE_NOT_CONFIGURED` | **通道不可用 · 点击重试** |
   | `ENGINE_RETIRED` | **通道已下架 · 点击重试** |
   | `NO_BRIDGE` | **翻译桥未就绪 · 点击重试** |
   | `MANUAL_ROW_LOST` | **消息已滚动 · 点击重试** |
   | `MANUAL_RENDER_MISSED` | **译文未能显示 · 点击重试** |
   | 其余（含 `TRANSLATE_FAILED`） | 翻译失败 · 点击重试 |

2. 真实错误码钉在 chip 上（`data-pix-fail-code`），便于取证与"重试前先看清上次为什么失败"。
3. 8 处失败路径全部带上真实 code；IPC `.catch` 不再把网络类错误码降级成 `TRANSLATE_FAILED`。

### 修复 B — 私聊必须自动翻译（判据重写）

1. **新增 `chatKind()`**，返回 `{ group, evidence }`，判据**一律只看 `#main`**，按证据强度排序：

   | 优先级 | 判据 | 结论 |
   |---|---|---|
   | 1 | `#main` 内消息行 `data-id` 含 `@g.us` | **群** |
   | 2 | `#main` 内消息行 `data-id` 含 `@c.us` 且无 `@g.us` | **私聊** |
   | 3 | `#main` 内头部文案含 `members` / `位成员` / `群组` | 群 |
   | 4 | `#main` 内 `aria-label` / `data-testid` 含 `group` | 群 |
   | — | 拿不到 `#main` | **按私聊**（自动翻译优先） |

2. **两种错的代价不对等**，所以证据冲突时**一律偏向群**：
   群误判成私聊 → 打开群聊自动翻满屏历史 → **扣费 P0**；
   私聊误判成群 → 用户以为"自动翻译坏了"。因此只要出现 `@g.us` 就判群。
3. **新增 `CHAT_KIND` 取证日志**：会话类型结论或判据一变就打一行，
   含 `group` / `evidence`（判据来源）/ `sawGUs` / `sawCUs` / `headerText` / `groupMarker` / `groupMode`。
   —— 本次真机排查只能靠猜，就是因为此前**没有任何**会话类型日志。
4. `groupModeLabel()`：把「群聊自动翻译」开关的读取收进一个小函数，
   使 CHAT_KIND 取证可以放在归档之前，同时不破坏"翻译开关不得出现在归档之前"的硬规则。

### 一个字都没动的（本轮硬约束）

- **传输层**（undici `Agent`、4s/8s 连接预算、错误分类、一次安全重试）；
- WhatsApp **原生输入**写入链路、**`BODY_MISMATCH`** 判定、fail-closed、草稿保护；
- **60ms 自适应沉降**；翻译正文提取与渲染（除 chip 文案）；
- **群聊历史隔离闸门**、幂等键构成、代理、字符计费规则、套餐/群组/子账号。

## 三、验收 A — ★重点一★ 私聊必须自动翻译

### A1. 私聊收到外语消息 → 必须**自动**出译文（不点任何东西）

**做法**：打开一个**一对一会话**，让对方发来一条英文/日文消息。

| 项 | 通过标准 |
|---|---|
| 译文 | **不用点任何东西**，气泡下方自动出现中文译文 |
| 「译」按钮 | **不应出现**手动 chip（出现即说明被判成群） |
| 日志 | `[PIX_TRACE] CHAT_KIND {"group":false,"evidence":"dataid:c.us",…}` |
| 日志 | 该条翻译的 `trigger=auto_receive`（不是 `manual_click`） |

### A2. 「群聊自动翻译」开关**关闭**时，私聊仍必须自动

**做法**：顶部翻译栏把「群聊自动翻译」**关掉**，再让对方给私聊发一条外语消息。

| 项 | 通过标准 |
|---|---|
| 私聊 | **仍然自动出译文**（这个开关只该管群聊） |
| 日志 | `CHAT_KIND` 里 `"groupMode":"manual"`，但私聊照样 `trigger=auto_receive` |

### A3. 群聊跟随开关（确认没被顺手改坏）

| 步骤 | 通过标准 |
|---|---|
| 「群聊自动翻译」**关** → 群里来新消息 | **不自动翻**，只给「译」按钮 |
| 「群聊自动翻译」**开** → 群里来**新**消息 | **自动翻** |
| 「群聊自动翻译」**开** → **打开**群聊 | **历史消息不自动翻**（只给按钮），否则会满屏扣费 |
| 任一情况 | 日志 `CHAT_KIND {"group":true,"evidence":"dataid:g.us",…}` |

## 四、验收 B — ★重点二★ 失败 chip 必须说真话

### B1. 网络类失败 → chip 显示「连不上服务器 · 点击重试」

**做法**：找一条收到的外语消息，**点击前**制造断网（关 Wi-Fi，或把系统代理指到死端口），再点「译」。

| 项 | 通过标准 |
|---|---|
| chip 文案 | 「**连不上服务器 · 点击重试**」——**不是**「翻译失败 · 点击重试」 |
| 顶部提示 | 「连不上服务器，请检查网络后重试」 |
| chip 属性 | `data-pix-fail-code="NETWORK_UNREACHABLE"` |
| 可重试 | 恢复网络后再点 → 真的重新请求并成功出译文 |
| 日志 | `TRANSLATE_FAILED {…,"code":"NETWORK_UNREACHABLE"}` |

### B2. 服务端翻译失败 → chip 仍显示默认文案（不该被误伤）

| 项 | 通过标准 |
|---|---|
| 错误码 | `TRANSLATE_FAILED` |
| chip 文案 | 「**翻译失败 · 点击重试**」（这一句在这里才是对的） |
| 区别 | B1 与 B2 的 chip 文案**必须不同** |

## 五、验收 C — 上一轮的传输层成果没被弄坏

### C1. 偶发连接抖动 → 自动恢复

临时制造"连不上"（拔网线 3~5 秒后立刻恢复）再按**发送**。
**通过标准**：等待明显短于 ~10s；第一次没连上会自动重连**一次**并成功发出译文；
日志里能看到 `[translate] 连接失败，复用同一幂等号重试一次`。

### C2. 持续断网 → 快速失败、文案正确、绝不发原文

| 项 | 通过标准 |
|---|---|
| 等待时间 | 约 4~8s 内给出结果，不再干等 10s |
| 顶部提示 | 「连不上服务器，请检查网络后重试」 |
| 失败面板 | 标题「网络异常，消息未发送」，错误码 `NETWORK_UNREACHABLE` |
| 对方 | **一个字节都没收到**（原文不回退发送） |
| 输入框 | 原文原样在，草稿没丢 |

### C3. 幂等与重复扣费（关键安全项）

同一条消息**只有一次成功计费**；自动重连重试**复用同一个 `requestId`**（日志里两次 `requestId=` 完全相同）；
「号已终结」那类业务重试**仍然会换号**（尾号 `:0` → `:1`）。

1. 同一窗口连发 **3 条不同长度**中文（约 5 / 20 / 60 字）。
2. 开 **3 个实例窗口**，同时各发一条。
3. 实例通道分别设 **GPT** 与 **DeepSeek** 各跑一轮。

**通过标准**：条数正确、顺序正确、内容一一对应；不串消息、不丢、不重复；
「已发送」及时收口；等待时间与 0.1.20 一致（正常约 2~3s 级），**没有变慢**。

## 七、安全底线（任一违反即 **FAIL**，请立刻停止并回传日志）

- ❌ **打开群聊**就把满屏历史消息自动翻掉（非预期扣费，最高优先级）；
- ❌ 对方收到**中文原文**（原文抢发）；
- ❌ 对方收到 `[正在翻译中...]` 之类**占位符**；
- ❌ 同一条**发两次** / **重复扣费**（含自动重试造成的重复）；
- ❌ 出现 `BODY_MISMATCH`；
- ❌ 等翻译期间你打了下一条 → 这条没发，但**你的新草稿被覆盖/丢失**；
- ❌ 翻译失败时**静默降级发原文**；
- ❌ **私聊不自动翻**（修复 B 的目标）；
- ❌ **网络类失败仍显示「翻译失败」**（修复 A 的目标）。

对应「正确行为」（不算 bug）：`COMPOSER_LEFT_AS_IS` = 你已改草稿 → 主动放弃覆盖、一个字节都不动。
