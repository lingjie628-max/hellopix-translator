## 0. 这一版修了什么

### 0.1 一句话

0.1.14 有**两条互相独立的链**是坏的，用户把两条都报上来了：

| 链 | 触发动作 | 症状 |
| --- | --- | --- |
| **A · 接收手动翻译** | 点消息下面那个「译」 | **点了完全没反应**：没有译文、没有提示，按钮随后消失 |
| **B · 发送翻译** | 开启发送翻译后按回车 | 会**丢用户内容**：正在打的下一条被覆盖、连发丢消息；失败后点「发送原文」发不出去 |

这一版两条都定位到根因并修掉，并且**各自补上了 trace 与可见状态**（失败不再静默）。

### 0.2 链 A：为什么"点了没反应"

三个根因叠在一起：

- **A1（主因）**：`addClick()` 给每个「译」按钮单独绑 `onclick`，并把消息气泡的
  **裸 DOM 引用**闭包捕获，跨越 `await` 之后还在用。WhatsApp 是 React 托管列表，
  重绘会把节点换掉；拿已 detach 的节点去解析正文 → 正文为空 → 渲染走 `clearExtras()`
  → **顺手把按钮删了**。所以真机看到的是"点一下，按钮没了，什么也没发生"。
- **A2**：按钮缺少 `pointer-events: auto` / `z-index`，WhatsApp 消息层在若干状态下
  会关掉 `pointer-events`，继承下来就是"看得见、点不动"。
- **A3**：整条链**一行 trace 都没有**，也没有失败反馈 —— 事后无法回答"断在哪一步"。

**修法**：事件委托到 `document` 捕获阶段（重绘丢不掉）；点击时记下消息行的
`data-id`，翻译完成后再**按 key 重新查当前气泡**；按钮三态
`译 → 翻译中… → 翻译失败·点击重试`；补 `MANUAL_*` 结构化 trace；
`translateTextDetailed()` 原样回报真实错误码（余额不足 / 断线 / 通道不在套餐 / 空结果）。

> 「翻译中…」只出现在 **Hello Pix 自己的按钮**上，**绝不写进输入框或消息正文**。

### 0.3 链 B：会丢用户内容的三个缺陷

| # | 现象 | 根因 |
| --- | --- | --- |
| B1 | 用户在等翻译时打**下一条**，翻译回来后草稿**整段消失**（真机已复现） | `deliverSend()` 写回译文前**没有任何"用户已改动输入框"的检查**，无条件覆盖 |
| B2 | 连续快速发 5 条，**只发出 3 条**，中间几条静默丢弃 | `fireSend()` 用 `setTimeout(…, 400)` 开了 **400ms 的 suppression 时间窗**，窗口内**任何**发送事件都被当成"我们自己发的" —— 用户按的回车被吞掉 |
| B3 | 同上（更隐蔽的一条） | 上一条动作的 400ms `sendActionPhase` 复位定时器会清掉下一条**正在飞**的 phase，下一条被 `STALE_ACTION` 拦下 |
| B4 | 翻译失败后点「发送原文」**永远发不出去**，又弹回同一个提示 | 它走 `fireSendVerified()`，而那要求 `phase === 'replaced'`；失败态是 `translating`，永远不满足 |

**修法**：写回前先 `composerDraftChanged()`，有草稿先存下、发完译文再把草稿放回输入框
（放不回去**明说**并提示）；`suppression` 改成**同步窗口**（`finally` 里立即复位）；
phase 复位定时器校验 `sendActionId === myAction`；「发送原文」改走
`fireSendUserAuthorized()`（不要求走完翻译状态机，但**保留** `sendableBody()` 校验）。

### 0.4 为什么不能原地重打 0.1.14

客户端更新判定是 `cmpVer(remote, local) > 0` —— **严格大于**。0.1.14 已上架并可被下载，
沿用同一版本号的话，**已经装到 0.1.14 的用户永远收不到修复**。
（另外 electron-builder 构建不可复现，同版本重打会出现"同版本不同内容"。）

## 2. 验收账号与基准

### 2.1 用哪个账号

- **主账号**（有余额、有多个引擎权限）。
- **对方**用一个**独立的第二账号**（另一台设备 / 另一个浏览器），
  这样"对方收到什么"才是**外部视角**，不会被本机界面误导。
- 子账号可选：若要额外验「子账号余额不足 → 提示 + 不发送」。

### 2.2 macOS 侧取证脚本（每做完一步跑一次）

```bash
cd <本验收包目录>
bash rc015-collect.sh before
# ...做一步验收操作...
bash rc015-collect.sh after-A01-manual-click
bash rc015-collect.sh after-B01-send-translate
```

产出 `rc015-evidence-<电脑名>.txt`（**追加**，不覆盖）。
把这个文件整个回传，我用 `node scripts/rc-trace-triage.js <文件>` 做分诊，
并对账 `translate_logs` 的 `trigger` / `engine`。

### 2.3 客户端日志里的判读重点

| 看到这行 | 含义 |
| --- | --- |
| `[preload] … 翻译桥已就绪` | ✅ 预加载脚本真的跑起来了（**没有这行 = 立刻停止验收并回传**） |
| `[preload] … 翻译桥未启动` | ❌ 桥没起来，装载级问题复现 |
| `MANUAL_TRANSLATE_CLICK` | 链 A：点击**到**了我们的处理器（没这行 = 点击没到，A2 类问题） |
| `MANUAL_PARSED` | 链 A：正文**提取成功**（`MESSAGE_TEXT_EXTRACTION_FAILED` = 提不出正文） |
| `MANUAL_REQUEST` | 链 A：**真的发了** `/translate/run` |
| `MANUAL_RESPONSE` | 链 A：**服务端回了**（带真实 code） |
| `MANUAL_RENDERED` | 链 A：译文**渲染回原消息**（`MANUAL_RENDER_MISSED` / `MANUAL_ROW_LOST` = 定位丢了） |
| `SEND_CAPTURED` → `NATIVE_SEND_BLOCKED` | 链 B：**拦住了**原生发送 |
| `TRANSLATE_SUCCEEDED` → `INPUT_REPLACED` | 链 B：翻译成功且**回读校验通过** |
| `PROGRAMMATIC_SEND_BEGIN` / `_DONE` | 链 B：**才**发起真实发送 |
| `DRAFT_PRESERVED` / `DRAFT_RESTORED` | 链 B：检测到你打了新内容并**帮你把草稿放回去了** |
| `TRANSLATE_FAILED` / `SEND_BLOCKED_*` | 链 B：fail-closed，**一个字节都没发** |

### 2.4 服务端对账（我来跑）

把 `rc015-evidence-*.txt` 发我，我会查：

```sql
-- 链 A：每次点「译」都应恰好 1 条 manual_click
SELECT trigger, engine, count(*), sum(chars)
FROM translate_logs
WHERE created_at > now() - interval '1 hour'
GROUP BY trigger, engine ORDER BY trigger;

-- 群聊手动模式下，auto_receive 必须是 0 条（不误扣费）
SELECT count(*) FROM translate_logs
WHERE trigger = 'auto_receive' AND created_at > now() - interval '1 hour';
```

## 3. 验收项

> 标记 **★** 的是这一版的核心，必须逐条走；未标记的是回归抽验。

### 3.0 前置：先确认装的是 0.1.15

macOS：`Hello Pix` → 关于 / 或
```bash
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' "/Applications/Hello Pix.app/Contents/Info.plist"
```
必须是 `0.1.15`。**不是 0.1.15 就地停止** —— 装了旧版验不出这一版的行为。

### 3.1 安装、启动、登录

- macOS 首次打开会看到「Apple 无法验证开发者」（**ad-hoc 签名、未公证**，与历史版本一致）：
  「系统设置 → 隐私与安全性 → 仍要打开」。详见包内 `macOS未公证安装引导-客服手册`。
- 进入主界面，打开 WhatsApp 实例，确认 WhatsApp 正常加载。

### 3.2 ★核心★ 链 A：点「译」按钮（这一版的主修复）

前置：账号能把「接收翻译」设为**手动**（或直接用群聊，群聊默认手动）。

1. 让对方给你发一条**英文**消息（例如 `Let's meet at 3pm tomorrow`）。
2. 消息下方应出现一个「**译**」按钮 —— **先确认它存在**。
3. 点它一次。
4. **期望**：
   - 按钮**立刻**变成「**翻译中…**」；
   - 随后译文出现在**这一条消息**下面（中文）；
   - 按钮仍**在**（不消失）；
   - 输入框**全程为空**（不许出现任何文字）。
5. 回传 `after-A01-manual-click`。

**判失败**：
- 点了没反应、按钮消失 → 看 trace 有没有 `MANUAL_TRANSLATE_CLICK`：
  - **没有** → 点击没到处理器（A2 类：pointer-events / 委托没挂上）；
  - **有**，但随后 `MESSAGE_TEXT_EXTRACTION_FAILED` → 正文提取失败；
  - **有** `MANUAL_REQUEST` 但没有 `MANUAL_RESPONSE` → 网络 / 服务端；
  - **有** `MANUAL_RESPONSE` 但没有 `MANUAL_RENDERED` → 渲染定位丢了（A1 类）。

### 3.3 ★核心★ 链 A：消息列表重绘后仍然可点

1. 点「译」得到译文后，**往上滚一段让消息列表重绘**（或切换会话再切回来）。
2. 再点另一条消息的「译」。
3. **期望**：仍然正常出译文（证明"按 `data-id` 重新定位"生效，不再持有失效节点）。

### 3.4 ★核心★ 链 A：失败要**看得见**，不许静默

用子账号把余额清零（或断开网络），再点一次「译」。

**期望**：
- 按钮变成「**翻译失败 · 点击重试**」；
- 出现可操作提示（带真实原因：余额不足 / 断线 / 通道不在套餐）；
- **输入框和消息正文里都不出现任何文字**；
- 恢复余额/网络后**再点一次能成功**。

### 3.5 ★核心★ 链 B：中文 → 英语，对方只收到 1 条英文

1. 在该 WhatsApp 实例上开启「发送翻译」，方向 中文 → 英语。
2. 输入 `你好，今天下午三点开会`，按回车。
3. **期望**：
   - 翻译期间**输入框里始终是中文原文**，**绝不出现 `[正在翻译中...]` 或任何占位符**；
   - 翻译完成后对方**只收到 1 条英文**；
   - **没有**"中文原文先发出去、英文又来一条"；
   - 成功后输入框清空。
4. 回传 `after-B01-send-translate`。

**判失败**：对方收到带 `[正在翻译中...]` 的消息 = 占位符出网（本版必须为 0）；trace 里应有
`SEND_CAPTURED → NATIVE_SEND_BLOCKED → … → INPUT_REPLACED → PROGRAMMATIC_SEND_DONE`。

### 3.6 ★核心★ 链 B：翻译期间打的下一条**不能被吃掉**（B1）

1. 输入第一条中文，按回车（开始翻译）。
2. **在译文回来之前**，立刻开始打**下一条**（例如 `第二条消息的草稿`）。
3. 等第一条发出去。
4. **期望**：
   - 对方只收到**第一条的译文**；
   - 输入框里**仍然是你刚打的下一条**，一个字都没丢；
   - 日志出现 `DRAFT_PRESERVED` 与 `DRAFT_RESTORED`。

**这一条是 0.1.14 真机复现过的数据丢失，必须重点看。**

### 3.7 ★核心★ 链 B：连续快速发 5 条，**5 条都要发出**（B2 + B3）

1. 连续输入并回车 **5 条**不同内容（每条之间停约 0.2 秒，不用等译文）。
2. **期望**：对方**收到 5 条**译文，顺序一致，每条**恰好一次**，**都不带占位符**。

**0.1.14 实测只发出 3 条**（中间几条被吞）。若这里仍是 3 条，请立刻回传 trace。

### 3.8 ★核心★ 链 B：API 失败 → 对方**什么都收不到** + 可操作提示

断开网络（或让服务端超时）后发一条中文。

**期望**：
- 对方**什么都收不到**（**绝不**降级成"发中文原文"）；
- 出现提示，含「**重试翻译**」与「**发送原文**」两个按钮；
- 日志出现 `TRANSLATE_FAILED`。

### 3.9 ★核心★ 链 B：点「发送原文」**必须真的发出去**（B4）

接上一条，点提示里的「**发送原文**」。

**期望**：
- **这一条中文原文真的发给对方了**；
- 提示消失；
- 不再原地弹回同一个提示（0.1.14 在这里是**死循环**）；
- 发出内容里**不含任何占位符**。

### 3.10 ★核心★ 链 B：点「发送原文」后再发新消息仍然正常

接 3.9，紧接着正常发一条中文。

**期望**：正常翻译并发出（证明「发送原文」没有把状态机卡死）。

## 5. 验收通过标准

以下**全部**满足才算两条链 PASS：

**链 A（点「译」）**
1. 点「译」在**新收 / 历史 / 群聊 / 私聊 / 长文 / 文字+URL** 上都能出译文；
2. 消息列表**重绘后**再点仍然可用；
3. 失败时**按钮态 + 提示**都可见，且**不静默**；
4. 同一条**连点 3 次只发 1 次请求**（不重复扣费）；
5. 输入框与消息正文**全程不出现任何文字**。

**链 B（发送翻译）**
