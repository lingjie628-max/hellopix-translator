## 0. 为什么有这一版

### 0.1 断点在哪一层（这版修的就是这里）

「我手动把群组翻译切成**自动**，群里新消息却一直不出译文」不是一个故障，
而是**四层各自独立的问题叠在一起**。逐层取证结果：

| # | 层 | 0.1.11 的结论 | 证据 / 根因 |
| --- | --- | --- | --- |
| 1 | 用户切 auto → 写入实例 | ❌ **断在这里** | 新建实例的 `groupMode` 被硬编码成 `'manual'`，且实例级**无条件覆盖**账号级（`hasTab ? s.groupMode==='auto' : g.transGroup`）→ 账号级「群聊自动翻译」**永远走不到**。界面显示「自动」也不会翻 |
| 2 | 设置持久化 | ❌ **断在这里（辅因）** | `saveOpenApps()` 整段覆盖 `tabs`：同一账号开两个副本时，后写的那个用自己内存里的旧 `tabs` 把另一个副本刚改的设置盖回去；`paintTransBar()` 的 `transBarSilent` 闸门没有 `try/finally`，中间一抛异常就**永远停在 true**，之后翻译栏改的任何东西都被静默丢弃 |
| 3 | `messageAction` | ❌ **断在这里（主因）** | `chatIdentity()` 扫的是**整个 document**，WhatsApp 左侧会话列表的行也带 `data-id` 且排在 `#main` 之前 → 群聊里身份取成「左侧列表里某个私聊」→ 列表每来一条消息就重排 → `historyGate` 每轮重置 → `ready` 恒为 false → 每条消息都被判成「历史」→ 一律只给「译」小按钮 |
| 4 | `auto_receive` 触发 | ❌ 从未发生 | 生产 `translate_logs` 28 行里 `trigger` **全为空串**（0.1.11 根本不发 `trigger`）；`sub_account_id=6`（`ahao`）**零条** |
| 5 | `/translate/run` 到达服务端 | ❌ **从未到达** | 生产 `translation_reservations` 里 `sub_account_id=6` = **0 行**。该行是在「余额校验之后、厂商调用之前」创建的 —— 只要请求进得来，就必然留下行 |
| 6 | 子账号 engine entitlement | ✅ 正常 | `basic` 套餐含 `gpt`+`deepseek`，两个都 `enabled=t wired=t retired=f`。且 `canSwitch=false` 只会**静默回落**到权益内第一个可用通道，不会报错 |
| 7 | 子账号 `char_balance` | ✅ 正常 | `ahao` 余额 **10000** |
| 8 | `translate_logs` | ❌ 无记录 | 上游就没发出请求（第 4/5 层的必然结果） |

**排除权限与余额的硬证据**：同一个商户（`jiufa`，ID 37，`basic` 套餐）下的
**另一个子账号 `mahou`（ID 5）翻译完全正常** —— 23 条 `committed` 预留 +
23 条 `translate_logs`（最近一次 2026-10-06 23:56）。同套餐、同服务端、
同客户端版本，所以第 6/7 层无罪。

#### 0.1.1 你这台机器上的直接证据（第 1/2 层的实锤）

`rc012-collect.sh before` 跑在**你的 Mac** 上，抓到的是磁盘上的真实值
（不是你看到的那块界面）：

```
已安装版本: /Applications/Hello Pix.app → 0.1.11

账号 ahao: nextTab=3 activeId=whatsapp-green-2 实例数=2
  - id=whatsapp-green-1  platform=whatsapp-green  groupMode='manual'  engine='gpt'
  - id=whatsapp-green-2  platform=whatsapp-green  groupMode='manual'  engine='gpt'

分区: pix-ahao-whatsapp-green-1 / pix-ahao-whatsapp-green-2  （两个实例各一套，隔离正常）
```

**你 `ahao` 名下的两个实例，`groupMode` 在磁盘上都是 `'manual'`** ——
而你记得界面上切成了「自动」。这就是第 1/2 层的实锤：

- 界面显示的「自动」与磁盘上的 `manual` **不一致**；
- 0.1.11 的 `paintTransBar()` 就是从 `trans.groupMode` 回填下拉的，
  所以那一下「自动」**要么没写进去，要么被另一个副本的保存盖回 `manual`**；
- 而 `tabPrefs()` 的 `hasTab ? s.groupMode==='auto' : g.transGroup` 只认
  磁盘上这个值 → 送给 `guest-inject` 的 `transGroup` 恒为 `false`
  → `messageAction()` 一律给 `chip` → **自动翻译从来没被触发过**。

这正好解释了两个"对不上"的现象：**界面上看着是自动，服务端日志里一条都没有**
（`translation_reservations` 里 `sub_account_id=6` = 0 行）。

> 这一段也是本版 §3.2 的验收方法为什么必须查 `open-apps.json` 而不能只看界面 ——
> 「界面显示自动」在 0.1.11 上**不构成任何证据**。


> 顺带验证了「界面在骗人」：`mahou` 库里存的是 `active_engine_id=gpt`，
> 而 23 条日志**全部是 `deepseek`** —— 这正是 `allow_engine_switch=false`
> 造成的「显示 GPT / 实扣 DeepSeek」，和截图里下拉锁死是同一个根因。

### 0.2 本版修的四处

1. **群组翻译三态**：新增 `'inherit'`（跟随账号级），**新建实例默认取它**。
   存量实例（字段缺失）**一律仍按 `'manual'`** —— 账号级 `trans_group` 的库默认是
   `true`，把「没有显式选择」解释成「跟随账号」等于给所有存量实例**打开自动扣费**。
2. **实例级设置不再丢失**：`saveOpenApps()` 改为按 tab **合并**（内存里的写入/更新；
   本副本恢复过、现已关闭的删除；磁盘上本副本没见过的**原样保留**），
   `nextTab`/`usedCount` 取单调最大值；`paintTransBar()` 改 `try/finally`。
3. **通道切换全套餐放开**：`migration 043` 把 `basic.allow_engine_switch` 置 `true`
   （**已上生产并核对通过**）。判定看的是**商户套餐**，主账号与子账号**逐项相同**。
4. **幂等键换代**：`requestId` 改为「账号 + 内容指纹 + 尝试代数」。
   旧实现是内容的纯函数 —— 厂商失败一次、预留退款之后，同一条文本
   **永远只能拿到 `409 REQUEST_FINALIZED`**。现在只在服务端明确回
   「这个号已终结」时换号重发**一次**；「服务端已成功但响应读丢」这种
   最危险的情况仍走原号，**不会重复扣费**。

### 2.3 服务端对账（我来跑）

```
=== 主账号 jiufa (main:37, Hello Pix 基础版) ===
  canSwitch        = true
  可选(allowed)    = deepseek, gpt
  显式选 gpt       -> gpt
  显式选 deepseek  -> deepseek
  余额             = 1387678

=== 子账号 ahao (sub:6, Hello Pix 基础版) ===

  可选(allowed)    = deepseek, gpt

  显式选 deepseek  -> deepseek
  余额             = 10000
```

结论：**主账号与子账号能力逐项相同**，不存在「主账号能选、子账号只能固定一个」。
通道下拉在 0.1.11 上也应该已经解锁了（服务端每次请求都现读这个字段，
不需要重启客户端、不需要重新登录）。

验收结束后我会用下面这几条对账（**只读**）：

```sql
-- ① 这个子账号有没有真的产生过翻译
SELECT count(*), sum(chars), min(created_at), max(created_at)
  FROM translate_logs WHERE sub_account_id = 6;

-- ② 每一次用的通道与来源（这是本版验收的核心断言）
SELECT id, engine_id, trigger, chars, created_at
  FROM translate_logs WHERE sub_account_id = 6 ORDER BY id DESC LIMIT 20;

-- ③ 余额必须与 ① 的 sum(chars) 对得上
SELECT char_balance, translate_count FROM sub_accounts WHERE id = 6;

-- ④ 预留状态（refunded 说明有失败后被退款，正是新幂等键要处理的场景）
SELECT id, engine_id, status, reserved_chars, created_at
  FROM translation_reservations WHERE sub_account_id = 6 ORDER BY id DESC LIMIT 20;
```

### 3.2 ★核心★ 手动切「群组翻译 = 自动」→ 群消息自动翻译

这一条是**本版第一优先**，直接对应 §0.1 的第 1/2/3 层。

1. 打开一个 **WhatsApp 群聊**实例，展开翻译栏
2. 把 **「群组翻译」** 设成 **「自动」**
3. 观察 `open-apps.json`（§2.2）：
   - [ ] `settings.groupMode` 是 `"auto"`（**不是 `"manual"`**）
   - [ ] 立刻压测一次：**完全退出软件再打开**，它**仍然是 `"auto"`**
     （0.1.11 常在这里被另一个副本的保存盖回 `manual`）
4. 停在群里**不要点任何按钮**，让群里别人发一条**新消息**
   （或你从手机发一条进群）
   - [ ] 新消息**自动**出现译文
   - [ ] **历史消息没有被补翻**（余额不因历史消息变化）
5. 余额变化

**截图**：① 翻译栏显示「自动」② `open-apps.json` 里 `groupMode: "auto"`
③ 新消息自动出现译文（含余额）

**记录**：切成自动前后余额、群里新消息条数、哪几条自动翻了

> 我会核对 `translate_logs.trigger = 'auto_receive'` 的条数 —— 这是本版
> **唯一能证明"自动翻译真的发生了"** 的服务端证据（0.1.11 的 `trigger` 全是空串）。

### 3.3 ★核心★ 通道下拉必须能自由选 GPT / DeepSeek

1. 在**子账号**里打开翻译栏的**通道**下拉
   - [ ] 下拉**不是灰的**（可以点开）
   - [ ] 里面**只有** `gpt` 和 `deepseek`
   - [ ] 选 `gpt` → 保存 → **不报错**
   - [ ] 选 `deepseek` → 保存 → **不报错**
2. **退出子账号，用主账号 `jiufa` 登录**，看同一个下拉
   - [ ] 主账号能选项**和子账号完全一样**（都是 gpt / deepseek）

### 3.4 ★核心★ 选 GPT 翻一条 → 切 DeepSeek 翻下一条

1. 通道选 **`gpt`**，在群里等/发一条**新的**外文消息
   - [ ] 自动出译文
   - [ ] 记录余额变化
2. **切换到 `deepseek`**（不要关软件）
3. 群里再来一条**新的**外文消息
   - [ ] 自动出译文
   - [ ] 记录余额变化
4. 两条都要能翻出来

**截图**：① 通道=GPT 那条的译文 ② 通道切到 DeepSeek 后那条的译文 ③ 余额两次变化

**记录**：两次的原文 / 译文 / 通道 / 扣的字符数

> `ENGINE_SWITCH_REQUIRES_NEW_REQUEST`，而旧客户端**不会换幂等号**，
> 于是换了通道也永远翻不出来（§0.2 第 4 条）。这一条就是它的验收。

## 7. Windows 侧怎么验（可选）

同一个 §3 清单，把命令换掉即可：

```powershell
Get-FileHash .\HelloPix-Setup-0.1.12.exe -Algorithm SHA256
```

本地配置目录在 `%APPDATA%\Hello Pix\`，`open-apps.json` 的判读方式与 §2.2 相同。

> ⚠️ 安装包**没有代码签名证书**，Windows Defender 大概率拦（PUA 提示）。
> 这是「未签名 + 无信誉」，不是检出病毒。放行方式仍是**只给这一个文件加白名单**，
> **不要**关「实时保护」。
