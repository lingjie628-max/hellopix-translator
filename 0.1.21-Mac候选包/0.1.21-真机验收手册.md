# 0.1.21 Mac arm64 候选 — 「网络传输层最小修复」真机验收手册

> 本轮**只做一件事**：把 0.1.20 那次真机 `TRANSLATE_FAILED` 的**真正底层原因**修掉 ——
> 那次请求**根本没发到服务端**，客户端白等了约 **10.4 秒**，根因是 Node/undici 的
> **默认连接超时 10s**（`UND_ERR_CONNECT_TIMEOUT`）。
>
> | 版本 | 发送写入 | 传输层 | 真机结果 |
> |---|---|---|---|
> | 0.1.19 | Chromium 原生输入 | 无连接预算（默认 10s） | 发送成功 ✅（但偶发 10s 白等） |
> | 0.1.20 | 同上 + 60ms 沉降 | 同上 | 发送成功 ✅，但 1 次网络抖动 → `TRANSLATE_FAILED`（**误报**） |
> | **0.1.21（本轮）** | **一个字都没动** | **连接预算 4s（首次 8s）+ 整体兜底 30s + 错误分类 + 一次安全重试** | 待测 |
>
> 本机是 Apple 芯片 → 用 **arm64** 包。
> **本轮不上架、不建 RELEASE、不发布正式版本、不动套餐/代理/群组/子账号/Windows。**

## 一、本轮改了什么 / 没改什么

### 改的（只在传输层，两处文件）

1. **连接与请求分开限时**（`desktop/main.js` · `api()`）
   - **连接预算**：只回答"现在连不连得上"。失败即在预算内判定不可达，不再等 undici 的 10s。
     - 正常（已预热）**4s**；冷启动首次 **8s**（首轮要现做 DNS + TLS，与旧版 `PING_TIMEOUT_FIRST` 同口径）。
   - **整体兜底**：整个请求的天花板 **30s**，只防"连上了却永远不回"。
     **绝不**用它去卡正常翻译（正常 2.4~3.4s、上游最坏 8s）。
2. **错误分类 + 一次安全重试**（`desktop/main.js` · `requestTranslate()` / `translate:run`）
   - `NETWORK_UNREACHABLE`：明确的 DNS / 连接建立 / 传输失败（**没拿到 HTTP 响应**）。
   - `NETWORK_TIMEOUT`：已连上但整体请求超时（没拿到响应）。
   - `SERVER_BAD_RESPONSE`：拿到响应但不是合法 JSON。
   - `TRANSLATE_FAILED`：**只有**"拿到服务端响应且翻译处理失败"才算（例如上游 8s 超时 → 502）。
   - 其余 HTTP / 鉴权 / 余额 / 幂等错误码**原样透传**，不再一律显示成"翻译失败"。
   - **安全重试规则**：仅在"连接建立失败、请求没发出去"时**自动重发 1 次**，
     **复用同一个 `requestId`**（= 服务端幂等键）→ 不新建计费动作、不重复扣费。
     502 / 余额不足 / 鉴权失败 / 连接已建立后才断（`ECONNRESET` 等）**一律不重试**。
   - 重试仍失败即 **fail-closed**：不发送原文、不重复扣费。

### 一个字都没动的（本轮硬约束）

- WhatsApp **原生输入**写入链路（`native-composer.js`：`selectAll+delete` → `insertText`）；
- **`BODY_MISMATCH`** 判定、fail-closed、草稿保护（`canSafelyRestore` / `COMPOSER_STILL_SOURCE`）；
- **60ms 自适应沉降**；
- 翻译正文**提取与渲染**；
- **GPT / DeepSeek 通道配置**、**代理配置**、**字符计费规则**；
- 幂等键构成（`requestId`）与"号已终结才换号"的业务重试。

## 四、验收 B — ★本轮重点★ 网络异常不再"白等 10 秒 + 误报翻译失败"

### B1. 偶发连接抖动 → 自动恢复（最理想）

用系统代理/防火墙**临时**制造一次"连不上"（或直接拔网线 3~5 秒后立刻恢复）再按发送。

**通过标准**：整体等待明显短于以前的 ~10s；若第一次没连上，客户端会自动重连**一次**并成功发出译文；
日志里能看到 `[translate] 连接失败，复用同一幂等号重试一次`。

### B2. 持续断网 → 快速失败、文案正确、绝不发原文

**彻底断网**后按发送。

| 项 | 通过标准 |
|---|---|
| 等待时间 | **明显快于 10s**（约 4~8s 内给出结果，不再是干等 10s） |
| 提示文案 | 顶部提示为「**连不上服务器，请检查网络后重试**」 |
| 失败面板 | 标题为「**网络异常，消息未发送**」，且**错误码为 `NETWORK_UNREACHABLE`**（不是 `TRANSLATE_FAILED`） |
| 对方 | **一个字节都没收到**（原文不回退发送） |
| 输入框 | 原文原样在，未被覆盖；你没有丢掉正在打的草稿 |

### B3. 服务端 502（上游超时）→ 仍是"翻译失败"，但不再有歧义

保持联网、正常发送；若服务端上游真的超时（GPT 通道最坏 8s）。

| 项 | 通过标准 |
|---|---|
| 错误码 | **`TRANSLATE_FAILED`**（这才是"翻译服务处理失败"） |
| 提示文案 | 「翻译服务暂不可用，请稍后重试」 |
| 对方 | **一个字节都没收到** |
| 自动重试 | **不发生**（502 不参与网络自动重试，避免重复计费） |

### B4. 幂等与重复扣费（关键安全项）

失败后点「**重试翻译**」，或网络恢复后再发一次同一条。

**通过标准**：
- 同一条消息**只有一次成功计费**（服务端不应出现两条预留的重复扣费）；
- 自动重连重试**复用同一个 `requestId`**（日志里两次 `requestId=` 完全相同）；
- 「号已终结」那类业务重试**仍然会换号**（`requestId` 尾号从 `:0` → `:1`）。

预期新增 trace / 日志：

```
[translate] source_text=… · from=… to=… engine=… dir=out trigger=manual_send
[api] NETWORK_UNREACHABLE {"path":"/translate/run","method":"POST","requestId":"desktop:…:0",
        "phase":"connect","gotResponse":false,"elapsedMs":4005,
        "errName":"TypeError","causeCode":"UND_ERR_CONNECT_TIMEOUT",
        "causeMessage":"Connect Timeout Error (… timeout: 10000ms)"}
[translate] 连接失败，复用同一幂等号重试一次 · requestId=desktop:…:0 · cause=UND_ERR_CONNECT_TIMEOUT
```

## 五、验收 C — 连续发送与多窗口（防回归）

1. 同一窗口连发 **3 条不同长度**中文（约 5 / 20 / 60 字）。
2. 开 **3 个实例窗口**，同时各发一条。

**通过标准**：条数正确、顺序正确、内容一一对应；**不串消息、不丢、不重复**；提示「已发送」及时收口、不残留。

## 六、安全底线（任一违反即 **FAIL**，请立刻停止并回传日志）

- ❌ 对方收到**中文原文**（原文抢发）；
- ❌ 对方收到 `[正在翻译中...]` 之类**占位符**；
- ❌ 同一条**发两次** / **重复扣费**（含自动重试造成的重复）；
- ❌ 出现 `BODY_MISMATCH`（首发送或重试）；
- ❌ 等翻译期间你打了下一条 → 这条没发，但**你的新草稿被覆盖/丢失**；
- ❌ 翻译失败时**静默降级发原文**；
- ❌ 网络异常仍然显示成「翻译服务暂不可用」（分类没生效）。

对应「正确行为」（不算 bug）：`COMPOSER_LEFT_AS_IS` = 你已改草稿 → 主动放弃覆盖、一个字节都不动。
