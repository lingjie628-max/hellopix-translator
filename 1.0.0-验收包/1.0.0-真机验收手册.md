> 本次验收对象：**1.0.0（首个正式版）+ 多语种翻译修复**
> 构建时间：2026-10-20 21:30
> 构建机：macOS / arm64
> 验收重点：**多语种翻译**、**标签栏侧面布局**、**两套右键菜单**、**渲染层拆分后的回归**

## 0. 这一版改了什么（先说清楚要验什么）

这一版有两部分：**渲染层/界面结构改动**，以及**一次性修掉的多语种翻译缺陷**。
计费、多开、登录流程没有动。

### 0.1 四个改动

| 改动 | 风险在哪 |
|---|---|
| **① 标签栏支持顶部/侧面切换** | 侧面布局下原生视图要右移 200px。**错一点，实例页面就把标签栏整个盖住** |
| **② 右键菜单分选中/未选中两套** | 新增「刷新全部同平台」「关闭全部同平台」「挂起」。**批量关闭必须二次确认，且只能关可见标签** |
| **③ 渲染层拆成 13 个文件** | `app.js` 1665 → 1070 行。**拆错的表现是"某个功能静默消失"——不报错、控制台干净** |
| **④ 多语种翻译修复** | 改的是客页注入层的语言判定。**错一点，要么该翻的不翻，要么把母语消息拿去烧额度** |

### 0.2 为什么 ④ 是这次最该盯的

现场反馈：**英语翻译一直正常，换成其他语言就完全没反应**。

查下来是三处独立的缺陷，全在客户端客页注入层（服务端与翻译通道没问题）：

1. **发送方向**：本地用 `detectLang()` 猜语种，认不出的**一律返回 `'en'`**。
   `sendTo` 默认就是 `'en'` → 德语/俄语/阿拉伯语/印地语/印尼语等
   被判成"本来就是英语" → **直接放行，一次翻译都不调**。
2. **接收方向**：同一个猜词器把日语判成中文 → `sameLang=true` → 直接 hide。
3. **最隐蔽的一处**：`hasChinese()` 只看 `[\u4e00-\u9fff]`（CJK 统一汉字），
   而**日语/韩语的汉字全在这个区间** → 日语消息 `hasChinese=true`，
   `includeZh` 默认关闭 → **直接 hide，连「译」按钮都不给**。

修法：把"猜语言"换成按**书写系统**判断的 `isDefinitelyLang()`——
只回答"能否 100% 确定"，拿不准就交给上游 `source='auto'`
（所有通道都支持，DeepL 代码里明确写了"auto 时不传 source_lang"）。

> **要特别验的一点**：纯 ASCII 但非英语的文本（例如
> `Guten Tag, Besprechung um 15 Uhr`，不带变音符）以前会被当成英语放行。
> 现在拉丁字母区一律送翻，所以**纯英文消息也会调用一次翻译接口**——
> 这是有意的取舍，后果是字幕区会短暂出现"翻译中"，译文等于原文。
> 若这一条在真机上体验很差，告诉我，可以改成"仅当文本极短时跳过"。

### 0.3 为什么 ③ 最需要真机验

拆分过程中踩过一个真实的坑：新文件切片时带进了别的模块的变量，
**重复声明 → 整个文件静默不执行 → 那部分功能凭空消失**，日志里什么都没有。

自动化测试已经用 vm 按真实顺序跑了一遍全部脚本（1650 项，0 失败），
但**测试环境没有真的浏览器**。真机跑一遍，才能确认浏览器里的表现和 vm 里一致。

所以本手册第 3 节的验收项是**按"模块有没有真的加载"来设计的**：
每个拆出去的模块，都有一个能在界面上看得见的信号。

### 3.1 ★核心★ 标签栏布局切换（顶部 ↔ 侧面）

这是本版第一个新功能，也是**最容易出现"视图盖住界面"**的地方。

**步骤**

1. 启动，登录，进入主界面（此时应在**顶部布局**：标签横向一行）
2. 打开 **3 个以上**不同平台的应用窗口（例如 2 个 WhatsApp + 1 个 Telegram）
3. 点击顶栏右侧的 **「顶部」按钮**（会变成「侧面」）
4. 观察布局变化
5. **切换后不要刷新**，直接点第二个标签，看能不能切过去
6. 再点一次按钮切回「顶部」
7. 完全退出 App，重新启动

**✅ 通过标准**

| # | 检查点 | 期望 |
|---|---|---|
| 1 | 切到侧面后 | 标签栏变成**左侧竖栏**，宽度约 200px |
| 2 | **实例页面不能被标签栏盖住** | 右侧聊天区完整可见，左边栏不被页面压住 |
| 3 | **顶部不能空出一条横带** | 侧栏模式下，顶栏不该还留着原来标签栏的 80px 高度 |
| 4 | 标签名完整显示 | 侧栏里能看清完整账号名，**不能被截成两三个字** |
| 5 | 未读数、头像、关闭按钮 | 都在，位置正常 |
| 6 | 侧栏出现很多标签时 | 能**纵向滚动**，滚轮往下能看后面的 |
| 7 | 切换后点标签 | 能正常切换，页面正确显示 |
| 8 | 重启后 | **仍然是上次选的布局**（持久化生效） |

**❌ 典型失败现象**

- 侧面模式下右边一片黑 / 页面被截掉左边一块 → **视图宽度算错了**
- 侧面模式下顶部空出白色横带 → **chromeOffset 没扣掉标签栏高度**
- 账号名变成「阿强…」「小李…」→ **CSS max-width 没解除**

### 3.2 ★核心★ 右键菜单（选中 vs 未选中）

**步骤 A：未选中的标签**

1. 在**非当前**的标签上点右键

**✅ 期望**：菜单标题显示该账号名，包含
「打开 / 重新加载 / 挂起 / 刷新全部同平台 / 关闭 / 关闭全部同平台 / 开发者工具」等

**步骤 B：选中的标签**

1. 在**当前正在用的**标签上点右键

**✅ 期望**：多出「刷新」「开发者工具」等只对当前页有意义的项；
**不应出现**"打开"（已经打开了）

**步骤 C：★关键★ 批量关闭必须二次确认**

1. 右键任意 WhatsApp 标签 → 点 **「关闭全部同平台」**
2. **不要马上点确认**，先看对话框写的是什么

**✅ 期望**

- 弹出确认框，写明**要关几个**
- 默认焦点在 **「取消」**（直接按回车 = 不关）
- 按 **ESC** → 关闭对话框且**什么都没关**

**❌ 这里出问题最严重**：如果 ESC 或回车就把窗口关了，
说明确认框的默认值反了 —— 那是"误关所有号"级别的事故。

**步骤 D：只关可见的**

1. 先「挂起」一个 WhatsApp 标签
2. 右键另一个 WhatsApp → 关闭全部同平台 → 确认

**✅ 期望**：挂起的那个**不受影响**，仍然在挂起列表里

### 3.5 ★核心★ 多语种翻译（本次重点修复，必验）

> 现场问题：**英语正常，其他语言完全没反应**。
> 这一节每一条都要做，做不了的说一声，别跳。

| 4 | `Hola, llego a las 3` | 对方收到**英文** | ❌ 西文原文直接发出去 |
| 5 | `Olá, chego às 15h` | 对方收到**英文** | ❌ 葡文原文直接发出去 |

| # | 操作 | ✅ 期望 |
|---|---|---|
| 1 | 接收语言设成中文，收发 `你好` | **不翻译、不扣费** |

#### E. 已知的取舍（看到别当成 bug）

**纯英文消息现在也会调用一次翻译接口。** 表现为发送时字幕区短暂出现
"翻译中"，最后译文等于原文。

原因：以前靠"纯 ASCII = 英语"来跳过，但纯 ASCII 的德语（`Guten Tag...`）、
意大利语、荷兰语都不带变音符，这条捷径正是"非英语语言被当成英语放行"的根源之一。
重复发送同一段会命中本地缓存，不会重复扣费。

> 如果这个"翻译中"闪烁让你觉得难受，告诉我，可以改成更细的判据。

### 6.1 关于 `NETWORK_UNREACHABLE`

**先把这条看完，否则你会以为是翻译坏了。**

出现下面这个提示时，**翻译请求根本没发出去**，跟多语种修复无关：

> 网络异常，消息未发送 · 错误码：NETWORK_UNREACHABLE

原文已退回输入框，对方没收到任何内容。这是**正确行为**（fail-closed），不是 bug。

日志里对应的是：

```
NETWORK_UNREACHABLE {"path":"/translate/run","phase":"connect",
  "causeCode":"UND_ERR_CONNECT_TIMEOUT",
  "causeMessage":"Connect Timeout Error (attempted address: pixfanyi.com:443)"}
```

`phase: connect` = 连 TCP 都没建起来。

#### 三条最常见的环境原因

**① App 从 DMG 挂载卷里直接运行**

```bash
# 检查是不是这样跑的
ps aux | grep "Hello Pix.app/Contents/MacOS/Hello Pix" | grep -v grep
```

如果路径是 `/Volumes/Hello Pix 1.0.0/...`，**必须**先拖进 `/Applications` 再运行。
从只读挂载卷运行的 App 在权限、网络策略、状态文件上都可能异常。

**② 防火墙没放行**

```bash
# 看状态
/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate
# 放行（需要密码）
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add "/Applications/Hello Pix.app"
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --unblockapp "/Applications/Hello Pix.app"
```

**③ DNS 用 8.8.8.8 在国内不稳**

```bash
scutil --dns | grep nameserver
```

国内建议换成 `223.5.5.5`（阿里）或 `119.29.29.29`（腾讯）。

#### 本轮代码侧的改动

| 项 | 改动前 | 改动后 | 为什么 |
|---|---|---|---|
| 热路径连接超时 | 4000ms | **8000ms** | 真机取证：连接超时稳定落在 4520~4700ms，而同一时刻另起进程只要 280~390ms → 链路间歇丢 SYN。8s 能等到 TCP 重传 |
| 连续失败退避 | 无（每 8s 硬撞） | 0 → 2s → 6s → 15s → 30s | 断网时不再刷爆日志；成功一次立刻归零 |
| 连接失败后连接池 | 复用 | **两个 Agent 全部重建** | 池里的半死 socket 会导致"必须重启 App 才好" |
| 手动重试 | 受退避约束 | **绕过退避** | 你点了重试就该真的去试，不能被"网络恢复中"挡回去 |

验证：

```bash
cd desktop && npm run verify:api-net   # 应为 11/11 通过
```

新错误码 `NETWORK_BACKOFF` 会显示成 **「网络恢复中 · 点击重试」**，
与「翻译服务坏了」明确区分。
