# 0.1.25 Mac arm64 候选 — 真机复测手册（群聊「自动」就是自动：不再留「译」按钮、不再翻一半）

> 本轮修的是用户 2026-10-11 报的**观感缺陷**，不是崩溃：
> 「群组翻译，开启自动翻译后，不应该出现这个翻译按钮，而是自动完成聊天内容的翻译；
>   而且开启了群聊自动翻译后，一部分翻译，还有一部分没有翻译。」
>
> | # | 现象（0.1.24 真机） | 根因 |
> |---|---|---|
> | **A** | 群聊开着「自动」，气泡下**还挂着「译」按钮**（截图里手红框标出的那个） | 扫描只在「新到的消息」上自动翻，**打开会话时已经在页面上的那批**被判成"历史"、只挂按钮 |
> | **B** | 一个群里**一部分翻了、一部分没翻** | 同 A。真机日志同一分钟：`MANUAL_CHIP_RENDERED × 43` 对 `auto_receive × 26`——用户眼前那批永远要手点 |
>
> ### 缺陷 A/B 的取证（0.1.24 真机日志，`hello-pix-2026-10-11.log`）
>
> | 观察项 | 实测 | 说明 |
> |---|---|---|
> | `CHAT_KIND` | `{"group":true,"evidence":"header-marker"}` | **群聊判对了**（0.1.24 的判据修复生效） |
> | `MANUAL_CHIP_RENDERED` | **95 次** | 打开群聊时页面上那批消息全部被挂上「译」 |
> | `trigger=auto_receive` | **26 次** | 只有会话进行中**新到**的消息才自动翻 |
> | 同一 `rowId` 的 `TRANSLATION_RENDER_VERIFIED` | 一秒最多 **33 次**、单条累计 **45 次** | `paint` 写 DOM 触发 `MutationObserver` 自激循环（白烧 CPU） |
>
> **结论**：0.1.24 的 `MessageParser.messageAction` 里有一条
> `if (s.group && s.historic) return 'chip'` —— 它把「群聊=自动」降级成
> **半自动**：只有新到的自动翻，打开会话时那批只给按钮。用户看到的就是 A/B。
>
> ### 期望行为（本轮目标，用户 2026-10-11 裁定）
>
> | 会话类型 / 模式 | 自动翻译 |
> |---|---|
> | **私聊** | **始终自动**（与「群聊自动翻译」开关**无关**） |
> | **群聊 = 自动** | 会话里出现的**全部**消息自动翻（**含打开会话时已经在页面上的那批**）→ **不再出现任何「译」按钮** |
> | **群聊 = 手动** | **一条都不自动翻**，只给「译」按钮（**唯一剩下的计费闸门，必须守住**） |
>
> ### 为什么"把历史也自动翻"不会变成"重复扣费"
>
> 删掉历史闸门的前提是**同一条消息翻多少次都只计一次费**，三层保证：
>
> 1. 客户端 `transRequestId` 对同一段正文 + 同一通道是**恒定**的
>    （`desktop:${deviceId}:${fingerprint}:${generation}`，`generation` 默认复用）；
> 2. 服务端 `core.translate` 按 `idempotency_key` 查 `translation_reservations`，
>    命中已有预留**直接返回、不再扣字符**；
> 3. 客户端 `transCache` + 服务端 `translationCache` 挡住重复网络/接口调用。
>
> **成本上限 = "从没翻过的正文"，不是"翻了多少次"。** 这三条已被单测锁死
> （`test/group-billing-guard.test.js` 的「★计费上限★」用例）。
>
> 本机是 Apple 芯片 → 用 **arm64** 包。
> **本轮不上架、不建 RELEASE、不发布正式版本、不动套餐/代理/群组/子账号/Windows。**

## 一、本轮改了什么

### 修复 A/B — 删除「群聊=自动 但历史只给按钮」那条闸门（`desktop/guest-inject.js`）

`MessageParser.messageAction` 现在的判定（**唯一**决策点，已被真 DOM 用例锁死）：

```text
receiveEnabled=false / 无正文 / 纯表情 / 中文且未开"含中文也译" / 同语种  → hide
群聊 且 「群聊自动翻译」= 手动                                          → chip（只给按钮）
其余（群聊自动 / 私聊）                                                 → auto（自动翻）
```

配套删除：`createHistoryGate()` / `isHistoric()` / 状态里的 `historic` 字段
（留着一段不再影响决策的"计费闸门"比没有更危险）。

### 修复 C — 自动翻译改「有界并发、新的先翻」（`enqueueAuto` / `autoPump`）

旧实现是扫描循环里**一条一条 `await`**：打开会话要翻几十条时，串行一条约 1s，
用户得盯着"翻一半"看半分钟——这正是"一部分翻、一部分没翻"的观感来源。
现在用 `AUTO_POOL_SIZE = 3` 的有界并发派发，且**倒序入队 = 最新的先翻**
（打开会话时人在底部，眼前那几条先出结果）。

> 并发上限**不能去掉**：翻译请求和**发送**链走同一套连接池，占满会拖慢发送
> （0.1.19 性能专项结论）；账号级限流是 120 次/分钟，也不允许一次性全推上去。
> 失败消息有 `AUTO_FAIL_COOLDOWN_MS = 60000` 冷却，防止每 220ms 一轮的扫描变成重试风暴。

### 修复 D — 自动接手时收掉手动留下的「译」（`removeStaleChip`）

先设「手动」→ 满屏「译」，再切「自动」→ 译文开始自动出现但**按钮还赖着**。
现在 `scan()` 的 `auto` 分支会清理残留的 idle 态 chip 与空操作行；
**busy 态刻意不动**（那是一次正在进行的手动翻译，收掉等于把用户点出来的操作掐死）。

### 修复 E — 掐断 `paint` 的自激循环（防 CPU 空转）

`paint()` 现在「内容没变就不写 DOM」。理由：`textContent = ...` 会产生一次
childList 变更，而扫描正挂在 `MutationObserver` 上——
`paint → 变更 → schedule → scan → paint → …` 会变成一台自激机器
（0.1.24 真机单条消息的渲染 trace 一秒 33 次）。本轮把「自动」扩到整个会话后，
这个循环会被放大到每一条消息，所以必须掐断。

### 新增取证 — `AUTO_DISPATCH`

每一轮扫描只要**派发过自动翻译或清过残留 chip**，就打一行
`[PIX_TRACE] AUTO_DISPATCH {...}`：

| 字段 | 含义 |
|---|---|
| `group` / `groupMode` | 会话类型 + 「群聊自动翻译」当前档位（`auto` / `manual`） |
| `candidates` | 本轮扫到、且决策为 `auto` 的消息条数 |
| `dispatched` | 真正入队的条数（已排队/冷却中的不重复入队） |
| `queued` / `running` | 队列长度 / 正在飞的数量（应 ≤ 3） |
| `chipRemoved` | 本轮被收掉的残留「译」个数（切到自动后应 > 0，之后回落到 0） |

> `CHAT_KIND` 的字段（含 `groupMode` 进指纹）沿用 0.1.24，不改。

### 一个字都没动的（本轮硬约束）

- **会话类型判据 `chatKind()`**（0.1.24 的修复原样保留：只读会话头部，消息区不参与）；
- **传输层**（undici `Agent`、连接预算、错误分类 `NETWORK_UNREACHABLE` 等、一次安全重试）；
- WhatsApp **原生输入**写入链路、`BODY_MISMATCH`、fail-closed、草稿保护；
- **60ms 自适应沉降**；翻译正文提取与渲染；失败 chip 文案映射；
- **幂等键构成**、代理、字符计费规则、套餐/群组/子账号。

## 三、验收 A — ★本轮唯一目标★ 群聊「自动」打开即全自动、**零「译」按钮**

### A1. 群聊设「自动」→ 打开群聊 → 页面上那批消息**自动全部翻**

**做法**：把「群组翻译」设成**自动**，打开一个**有历史消息的群**，**什么都不点**，等 3~5 秒。

| 项 | 通过标准 |
|---|---|
| 译文 | 打开会话时**已经在页面上的每条可翻消息**，都自动出现中文译文 |
| 「译」按钮 | **一个都不应出现**（截图里红框那个就是缺陷本身） |
| 日志 | `AUTO_DISPATCH` 的 `groupMode:"auto"`、`candidates`≈页面上消息数、`dispatched>0` |
| 日志 | 这些消息的 `trigger=auto_receive`（**不是** `manual_click`） |

### A2. ★原始复现★ 同群同屏**不再"翻一半"**

**做法**：A1 之后，让对方**连续发 5~10 条**外语消息；同时上下滚动几次让历史补加载。

| 项 | 通过标准 |
|---|---|
| 「译」按钮 | **始终为 0**（滚动补加载出来的更早消息也应自动翻） |
| 翻一半 | **不存在**：不再出现"上面几条有译文、下面几条没译文"的长期状态 |
| 日志 | 不再出现 `MANUAL_CHIP_RENDERED`（除非你手动把开关切回「手动」） |
| 日志 | `AUTO_DISPATCH` 的 `queued`/`running` 里 `running` **≤ 3**（有界并发） |

> 这一条就是**本轮的原始复现**。A1+A2 过了，用户报的问题就真的修好了。

### A3. 「自动 → 手动」切回，残留的「译」被收掉（本轮修复 D）

**做法**：先「自动」（满屏译文）→ 切「**手动**」→ 再将「手动」切回「**自动**」。

| 项 | 通过标准 |
|---|---|
| 切到手动 | 新消息只给「译」按钮，**不自动翻**（`groupMode:"manual"`） |
| 切回自动 | 残余的 idle 态「译」**被收掉**（`AUTO_DISPATCH` 的 `chipRemoved>0`，之后回落到 0） |
| busy 态 | 若你正点着某条的「译」，那条**不应**被收掉（翻译照常完成） |

### A4. 群聊「手动」的计费护栏（**最高优先级**，绝不能被顺手改坏）

**做法**：把「群组翻译」设成**手动**，打开群聊、滚动、等新消息。

| 项 | 通过标准 |
|---|---|
| 自动翻译 | **一条都不许自动翻**（`trigger=auto_receive` 在群里为 0） |
| 「译」按钮 | 每条可翻消息都有「译」 |
| 点其中一条 | 只有这一条翻（请求数 +1），且非预期扣费为 0 |

## 四、验收 B — 私聊仍然自动（确认 0.1.24 的修复没被碰坏）

**做法**：打开一个**一对一会话**，让对方发来一条英文/日文消息；再把「群聊自动翻译」**关掉**，再发一条。

| 项 | 通过标准 |
|---|---|
| 译文 | **不用点任何东西**自动出现（开关开着/关着都应自动） |
| 「译」按钮 | **不应出现** |
| 日志 | `CHAT_KIND {"group":false,…}`；`trigger=auto_receive` |

> 若私聊又只剩「译」按钮，说明 `chatKind()` 被判坏了 → 立刻停止并回传日志（见第七节）。

## 五、验收 C — 上一轮的传输层 / 发送正确性没被弄坏

### C1. 偶发连接抖动 → 自动恢复

临时制造"连不上"（拔网线 3~5 秒后立刻恢复）再按**发送**。
**通过标准**：等待明显短于 ~10s；第一次没连上会自动重连**一次**并成功发出译文；
日志里能看到 `[translate] 连接失败，复用同一幂等号重试一次`。

### C2. 持续断网 → 快速失败、文案正确、绝不发原文

| 项 | 通过标准 |
|---|---|
| 等待时间 | 约 4~8s 内给出结果，不再干等 10s |
| 顶部提示 | 「连不上服务器，请检查网络后重试」 |
| 失败面板 | 标题「网络异常，消息未发送」，错误码 `NETWORK_UNREACHABLE` |
| 「译」chip 文案 | 「**连不上服务器 · 点击重试**」（不是笼统的"翻译失败"） |
| 对方 | **一个字节都没收到**（原文不回退发送） |
| 输入框 | 原文原样在，草稿没丢 |

### C3. 幂等与重复扣费（关键安全项）

同一条消息**只有一次成功计费**；自动重连重试**复用同一个 `requestId`**
（日志里两次 `requestId=` 完全相同）；「号已终结」那类业务重试**仍然会换号**（尾号 `:0` → `:1`）。
**本轮特别看**：A1 把整屏历史自动翻了一遍后，`character_balance` 的下降量
应与"这些正文**此前从未翻译过**"相符，**不因重扫而二次下降**。

## 七、安全底线（任一违反即 **FAIL**，请立刻停止并回传日志）

- ❌ **群聊=手动** 时出现自动翻译（`trigger=auto_receive`）——非预期扣费，最高优先级；
- ❌ **打开群聊**（开关=自动）之外的**任何**情况下自动翻掉历史；
- ❌ **重复扣费**（含重扫、自动重试、快速连点造成的重复）；
- ❌ 对方收到**中文原文**（原文抢发）；
- ❌ 对方收到 `[正在翻译中...]` 之类**占位符**；
- ❌ 出现 `BODY_MISMATCH`；
- ❌ 等翻译期间你打了下一条 → 这条没发，但**你的新草稿被覆盖/丢失**；
- ❌ 翻译失败时**静默降级发原文**；
- ❌ **私聊不自动翻**（0.1.24 已修的，不许回退）。

对应「正确行为」（不算 bug）：
- `COMPOSER_LEFT_AS_IS` = 你已改草稿 → 主动放弃覆盖、一个字节都不动；
- 群聊=自动时**打开**会话自动翻满屏——**这是本轮的目标行为，不是 bug**。
