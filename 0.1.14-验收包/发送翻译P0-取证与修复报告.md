# 发送翻译 P0 · 取证与修复报告

> 对象：Hello Pix **0.1.12**（已上架版本）
> 现象：开启「发送翻译」后，在 WhatsApp 输入中文按回车，**中文原文直接发给对方**，没有翻译成英语。
> 结论：**不是翻译失败，是拦截根本没启动。** 整份 `guest-inject.js`（preload 脚本）在装载阶段就抛错停摆，`keydown` / `click` / 扫描监听器一个都没挂上。
> 处置：0.1.12 已下架（可回滚记录留档），0.1.14 已上架并完成执行级 + 分层验证。

---

## 1. 十个必答问题

### 1. Enter 事件有没有被 Hello Pix 捕获？

**没有。** 捕获阶段的 `keydown` 监听器**从未注册成功**，因为它所在的整份 `guest-inject.js`
在装载时就崩了，脚本执行到第 63 行直接中止，后面的 `document.addEventListener('keydown', …)`
一行都没执行。

校验输出：`✖ 装载后 Enter 被拦截（监听器真的挂上） → 未拦截 = 原文会直通 WhatsApp`。

### 2. 点击发送按钮有没有被捕获？

**同样没有**，且原因**完全相同** —— `click` 监听器和 `keydown` 写在同一个脚本、同一个装载流程里，
一崩全崩。不存在"Enter 拦了、按钮没拦"这种半可用状态。

这也是为什么本次修复**不允许只修一种发送方式**：三个入口（`keydown` / `beforeinput` /
发送按钮 `click`）现在都走**同一个** `safeIntercept`，测试逐条覆盖。

### 3. 当前 WhatsApp 输入框 selector 是否仍然正确？

**正确，且不是本次的原因。** 这是本次取证里最重要的一条排除项：

- selector 相关逻辑（`composerEl()` / `eventInComposer()`）**在第 63 行之后**，
  装载在第 63 行就中止了，所以**根本没执行到** selector 那一步。
- 真 DOM 里实测：把输入框填上中文后按回车，**从未调用过翻译接口**（`实际 0 次`）。
  如果 selector 失效，表现会是"找不到输入框"，而这里连"找"这个动作都没发生。
- 反证：**同一份 selector 代码在 0.1.14 上 20/20 通过**，能正确找到输入框、正确拦截。
  也就是说 selector 逻辑本身没问题，问题在它**上游**。

结论：这次**不要动 selector**。改 selector 只会把"没执行到"误判成"写错了"，越改越偏。

### 4. 是否识别到 send translation enabled=true？

**无法识别 —— 因为脚本没跑到那一步。** `prefs` 的读取与 `transSend` 的判定都在
第 63 行之后。所以它既不是 `true` 也不是 `false`，而是**这段判断压根不存在**。

真机侧"看起来像开着"（设置界面显示已开启、服务端也存着 `transSend=1`），
但那只是**配置层**开着，**执行层**从来没上线。这正是这个 P0 最迷惑人的地方：
配置是好的，代码是死的。

### 5. 当前实例的 send input/output language 是否正确读取？

同样**没读到**（原因同第 4 条）。补充一点：本次修复在发送路径上做了语言判定
（`detectLang(...) !== prefs.sendTo` 才翻），并覆盖了"输入=自动识别 / 输出=英语"的组合，
所以 0.1.14 上这条是有测试保护的。

### 6. 是否调用 /translate/run？

**完全没有调用。** 校验里两项直接给出 0：

```
✖ 成功路径：调 1 次翻译接口  → 实际 0 次
✖ 成功路径：trigger=manual_send  → 无调用
```

这是判定"断在客户端还是服务端"的分水岭：**请求从未离开客户端**。
服务端、翻译通道（GPT）、余额、套餐权限**全部无关**。

### 7. 如果没调用，断在哪一层？

**断在客户端最外层、最早的一层：preload 脚本的装载阶段（top-level execution）。**

精确位置：

```js
// desktop/guest-inject.js（0.1.12 产物实测行号）

// 第 63 行 —— 调用点
const historyGate = MessageParser.createHistoryGate()

// 第 248 行 —— 定义点（在调用点之后！）
var MessageParser = (function () {
```

`var` 声明会**提升**，但值是 `undefined`。第 63 行执行时实际是
`undefined.createHistoryGate()`，抛：

```
TypeError: Cannot read properties of undefined (reading 'createHistoryGate')
```

**为什么这个错一抛就全盘皆输**：Electron 的 preload 脚本在**顶层**抛出未捕获异常时，
脚本**立即终止**，其后所有语句都不执行。于是：

| 本该注册的东西 | 实际状态 | 后果 |
| --- | --- | --- |
| `document.addEventListener('keydown')` | 未注册 | Enter 不被拦 → 原文直发 |
| `document.addEventListener('click')` | 未注册 | 发送按钮不被拦 → 原文直发 |
| `MutationObserver` 扫描循环 | 未启动 | 群聊自动翻译（`auto_receive`）一条都不触发 |
| 翻译失败提示 | 不存在 | 失败时界面毫无反应 |

而错误只写进 `webContents` 控制台 —— 客户端**一条日志都没有**，用户界面**毫无提示**。
所以现场表现为"翻译开着、什么都没发生、中文就发出去了"，看起来像"翻译坏了"，
实际是**代码从来没有运行过**。

> **6 个协议步骤的实际断点**：
> `keydown/click` → ❌**断在这里**（监听器不存在）
> → send translation interceptor ❌不存在
> → preventDefault / stopPropagation ❌未执行
> → sourceText ❌未提取
> → translate request ❌未发起
> → server response ❌无
> → write translated text ❌无
> → native send ✅**由 WhatsApp 自己完成**（因为没人拦）

### 8. 如果调用了，是否 WhatsApp 原生发送先于异步翻译完成？

**"调用了但被抢跑"这条假设不成立 —— 因为压根没调用。**

但取证过程中确实**发现了这一族的另一个真实缺陷**（并且已被本次修复消灭），
它原本会在 D1 修好之后立刻变成新的 P0：

**D4 — `async` 函数的抛错比原生发送晚一个微任务。**

0.1.12 的 `runIntercept` 是 `async function`。第一版修复给它套了 `try/catch`，
看起来万无一失。但测试立刻打脸：**原文照样发了出去**。原因是：

- `async function` 内部抛出的异常，**不会**同步抛给调用者，而是变成一个
  **rejected promise**；
- 于是 `.catch()` 里的 `preventDefault()` 要到**微任务队列**里才执行；
- 而 WhatsApp 的原生发送挂在**冒泡阶段**，**早在那之前就已经执行完毕**。

也就是说："我以为我在拦，其实原文已经出网了" —— 这跟 D1 是**同一类失败**
（不是翻错，是没拦），而且更阴险：代码路径看起来是对的。

**修法（已落地）**：把"决定拦不拦 + `preventDefault`"拆成一个**同步**函数
`decideIntercept()`，事件回调里同步跑完；异步的翻译投递**另起一段**，
由 `safeIntercept()` 用 `.catch()` 兜底。规矩只有一条：

> 抛错 = 翻译失败 = 拦下发送 + 弹可操作提示。**绝不静默放行。**

现在源码守卫测试会**禁止** `decideIntercept` 变成 `async`，
并在 `npm run verify:client` 里用故障注入验证"抛错时 Enter 仍被拦截、对方什么都收不到"。

### 9. translate_logs 是否出现 manual_send？

**0.1.12 上永远不会出现** —— 请求都没发出去，服务端表里自然没有记录。

即便请求发得出去，0.1.12 也不会打这个标签：它调用的是

```js
translateText(masked.masked, false)   // 只传两个参数，trigger 恒为空串
```

所以 `translate_logs.trigger` 里**永远不会有 `manual_send`**，事后审计无法区分
"用户点了发送"和"扫描时自动翻"。这虽然没直接导致原文外发，但**让这次事故在事后
几乎无法追查** —— 属于必须一起修的问题。

**D3 修复**：新增 `TRIGGER_SEND = 'manual_send'` 并在发送路径传入；
服务端 CHECK 约束（`migrations/042_translate_log_trigger.js`）已包含该值。

### 10. 是否因为新子账号设置没有正确加载而跳过发送翻译？

**不是。** 这一条被明确排除，理由有三：

1. **请求压根没发出去**（第 6 条：0 次调用）。设置加载与否不会让**监听器**消失 ——
   它只影响"拦截后翻不翻"，不影响"拦不拦"。
2. **主账号、子账号、任何账号都同样失效**：装载崩溃发生在**读取账号设置之前**，
   与账号无关。
3. **执行级校验在无账号环境下同样复现**：脚本在没有任何账号上下文时照样抛
   `TypeError`，说明与设置无关。

不过你要求检查的这条确实**排除了一个真实存在的相邻风险**：见 §2 第 6 条。

### 关于"guard 误伤整条发送路径"—— 你的直觉是对的

排查发现，在 D1（拦截器根本没挂上）之外，**占位符硬闸的时序**确实存在一条
会把发送路径整体掐死的隐患：

```js
// 老实现：只在 prefs.transSend 打开时检查占位符，且 isBusy 时什么都不做
if (isBusyText(trimmed) || sendBusy) {
  preventDefault(); return true      // ← 拦下之后直接 return
}
```

`sendBusy` 期间拦下后**什么也不做**，依赖 `deliverSend` 自己的 `finally` 去清 `sendBusy`。
一旦投递流程被打断（异常 / 写回失败 / 翻译接口 hang 住），
`sendBusy` 会**永久停在 true** → 之后**每一次** Enter 都被拦下且什么都不发 →
用户表现就是"发送翻译整个失灵，消息发不出去"。

**修法**：`safeIntercept` 的兜底路径里**无条件**把 `sendBusy = false`、
`pendingSend = null` 复位，并把原文退回输入框 + 弹提示。
也就是说：**拦截可以失败，但绝不能卡死。**

另外一条相关的：`paintTransBar` 原先没有 `try/finally`，异常会让翻译工具条
永久停在中间态；`saveOpenApps` 原先整段覆盖，会让多开的另一个副本刚改的设置
被旧内存态写回去。两者都在 0.1.12 的修复里处理掉了。

## 3. 失败策略（你要求必须改的部分）

### 3.1 铁律

当「发送翻译」已开启时，**翻译 API 超时 / 失败 / 余额不足 / 通道不可用**：
**禁止自动发送中文原文。**

### 3.2 老实现错在哪

```js
const out = await translateText(masked.masked, false)   // 失败时 out = ''
const finalText = out
  ? (out === masked.masked ? raw : MessageParser.restoreUrls(out, masked.urls))
  : raw                                                 // ← 拿不到译文就用原文兜底
writeComposer(box, finalText)
scrubBusy(box, finalText)
await wait(50)
fireSend(box)                                           // ← 然后照常发送
```

`out` 为空串（超时 / 断网 / 余额不足 / 通道不在套餐里）→ `finalText = raw` →
**中文原文被发出去**，而且这一下是**用户没有同意**的发送动作。
用户以为在用"发送翻译"，对方收到的却是一段自己看不懂的中文。

> 注意这是 **D1 之外的第二个独立 P0**：即使 D1 修好了，这条兜底也照样会让原文外发。
> 两者必须一起修，只修一个都不能开放给客户。

### 3.3 新行为

改为 `deliverSend()`：**翻译成功才发送**。

- 翻译没成功 → **一个字节都不发**；
- 原文**退回输入框**（用户的内容不丢）；
- 清掉 `[正在翻译中...]` 占位符（绝不允许占位符变成一条真实消息）；
- 弹出**可操作**提示：

```
翻译失败，消息尚未发送
原文已退回输入框，对方没有收到任何内容。
[ 重试翻译 ]  [ 发送原文 ]
```

- 「**重试翻译**」：以**当前输入框内容**为准重翻一次，成功才发；
- 「**发送原文**」：**必须用户再次明确点击**才发未翻译的原文 —— 不做静默降级；
- 提示整体带 `data-pix-ui` 标记：采集 / 解析 / 发送拦截全部绕开它，
  避免"点重试被当成点了发送"。

### 3.4 第三道闸：崩溃兜底

即使翻译流程抛出**预期外**的异常，也按"翻译失败"处理：拦下发送 + 弹提示（见 §1 第 8 条）。
**任何异常都不构成"放行原文"的理由。**

### 4.1 附带发现：历史账单里「时间戳被当成正文计费」

在对生产 `translate_logs` 做只读巡检时，`snippet` 里出现了这种形态：

```
Sweet dreams18:53
Hello.14:26
Night6:52 PM
```

`18:53` / `14:26` / `6:52 PM` 是 WhatsApp 的气泡时间戳。老实现把气泡 `innerText`
整个当正文送去翻译，于是**时间戳跟着正文一起被计费** —— 上例用户只输入了
12 个字符，却被扣了 17 个。

**这条是历史问题，不是 0.1.14 的回归。** 直接跑解析器验证（真 DOM，含 24 小时制）：

```
✓ 24h 时间 + 正文     容器原文 = "Sweet dreams18:53wds-ic-read"  sourceText = "Sweet dreams"
✓ 正文本身含时间样数字  容器原文 = "Meeting at 3:00 is fine18:53…"  sourceText = "Meeting at 3:00 is fine"
```

0.1.14 的 `MessageParser` 按 DOM 结构（而非正则黑名单）剥离噪音，24 小时制同样
剥干净，并且**不会误删正文里本来就有的 `3:00`**。

## 5. 为什么必须换版本号（0.1.12 → 0.1.14）

1. **客户端的更新判定是 `cmpVer(remote, local) > 0`（严格大于）。**
   已经装成 0.1.12 的用户，只有拿到**版本号更大**的包才会被提示升级。
   沿用 0.1.12 原地重打，这批用户**永远收不到修复**。
2. **构建不可复现。** 同一个版本号重打会产生"同版本不同内容"，
   而这次恰恰最需要"同一个文件 = 验收过的那个文件"。
3. 0.1.13 在修复窗口内已经上架过（可下载），因此 0.1.13 → **0.1.14** 同理。

> 回滚只让**更新提示与下载页**回到可用版本，**不会**把已经装成 0.1.12 的用户变回去。
> 已装 0.1.12 的用户必须靠 0.1.14 才能修好 —— 所以这一版的**上架动作本身就是修复**。

## 6. 这次为什么以前没发现（流程层面的改进）

之前的"产物核对"是**在 `app.asar` 字节里搜关键字**。0.1.12 那次全部关键字都在，
于是判定通过。但那次的问题恰恰是**装载期错误** —— 关键字在不在，
跟代码**能不能跑起来**毫无关系。字符串搜索**永远**发现不了这类缺陷。

现在上架闸门改成**执行级**：`scripts/verify-preload-load.js`
（`npm run verify:client`）从 `app.asar` 里取出真实的 preload，
塞进真 DOM **完整执行一遍**，验证拦截器真的挂上、失败真的不发、抛错真的拦得住。

- 对**已上架的 0.1.12**：报 **16 项阻断**，退出码 1；
- 对**待发的 0.1.14**（三份 asar）：**20/20 通过**。

结论：**这个闸门能拦住 0.1.12 这类事故。** 它现在是发版流程的一步。
