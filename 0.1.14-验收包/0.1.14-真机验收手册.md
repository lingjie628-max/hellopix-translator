# PIXS Client 0.1.14 · 真机验收手册（发送翻译 P0）

> **这一版是紧急修复版。** 上一版 0.1.12/0.1.13 存在"开启发送翻译后会把中文原文直接发给对方"
> 的 P0（成因与取证见同目录 `发送翻译P0-取证与修复报告.md`）。
> **在 §3 全部通过之前，不要对外宣称 WhatsApp 发送翻译可用。**

---

## 0. 这一版修了什么（为什么值得你花时间验）

### 0.1 一句话

`guest-inject.js` 是**预加载脚本**。0.1.12 里它在**装载第 63 行**就抛错
（在 `var MessageParser` 定义之前调用了它），脚本立即终止：

- `keydown` / `click` 监听器**一个都没挂上** → Enter 和发送按钮**都不被拦** → 中文原文直通 WhatsApp
- 扫描循环**没启动** → 群聊自动翻译一条都不触发
- 界面**毫无提示**，客户端日志**一条都没有**

在它之上还有第二个独立 P0：翻译失败时**静默降级成"发原文"**。

### 0.2 本版七个修复

| 编号 | 问题 | 严重度 |
| --- | --- | --- |
| A | 装载即崩，整个翻译链路从未启动（拦截器不存在） | P0 阻断 |
| B | 翻译失败 / 超时 / 余额不足 → 静默把中文原文发出 | P0 |
| C | 发送路径不打 `trigger`，`translate_logs` 无法归因 | P1 |
| D | **拦截流程中途抛错 → 原文照样出网**（`async` 抛错晚一个微任务，来不及拦） | P0 |
| E | **桥装载失败仍然完全静默** —— 没有日志、没有提示、侧边栏看不出来 | P0 观测面 |
| F | 发送翻译开启后，翻译进行中的 `sendBusy` 可能永久卡住 → 之后**每次**发送都被拦下且什么都不发 | P1 |
| G | 多开时实例设置互相覆盖；翻译工具条异常后停在中间态 | P1 |

其中 **D / E** 是在做本版验收时新发现的 —— 也就是说：**如果只修 A/B/C，客户的原文仍然可能被发出去。**

### 0.3 为什么不能原地重打 0.1.12 / 0.1.13

客户端更新判定是 `cmpVer(remote, local) > 0`（**严格大于**）。已经装成 0.1.12 / 0.1.13 的用户，
只有拿到**版本号更大**的包才会被提示升级。所以必须 **0.1.14**。

## 2. 验收账号与基准

### 2.1 用哪个账号

用一个**字符余额充足**的子账号（不要用余额为 0 的号做成功路径，那验的是失败路径）。
记录账号名，方便后面用 SQL 对账 `translate_logs`。

### 2.2 macOS 侧取证脚本（每做完一步跑一次）

```bash
cd 0.1.14-验收包
bash rc014-collect.sh before                 # 开始前：只记基线，不贴内容
# ...做一步验收操作...
bash rc014-collect.sh after-01-cn2en         # 每步之后跑一次，标签自己起
bash rc014-collect.sh after-05-slow-api
```

产出：`./rc014-evidence-<电脑名>.txt`，多次调用是**追加**不是覆盖。
脚本**只读**，不会改任何东西，也**不打印口令**（`proxyPass` 一律替换成 `[redacted]`）。

**把这个文件整个发我**，我用它和服务端 `translate_logs` 做分层对账。

### 2.3 客户端日志里的判读重点

日志在 `~/Library/Application Support/Hello Pix/logs/hello-pix-YYYY-MM-DD.log`。

| 关键字 | 含义 |
| --- | --- |
| `trigger=manual_send` | ✅ 发送翻译的请求**真的发出去**了（0.1.12 上这一行永远不会出现） |
| `source_text=` | 实际送给上游的原文。**这里必须是用户输入本身**，不能混进 UI 文案 / 时间戳 / 已读 |
| `engine=gpt` / `deepseek` | 实际用的通道，必须与界面显示一致 |
| `[preload] … 翻译桥已就绪` | ✅ 预加载脚本**装起来了**（0.1.12 上不会有这一行） |
| `[preload] … 翻译桥**未启动**` | ❌ **看到这一行立刻停止验收并回传** —— 说明又出现了同类问题 |
| `[preload] … 装载失败` | ❌ 同上，附带了具体原因 |
| `[guest] …` | guest 页面里的报错（含拦截器内部异常） |

### 2.4 服务端对账（我来跑）

验收做完后，我需要这些（你只要回传 §2.2 的文件）：

- `translate_logs` 中该账号该时段的 `trigger` / `engine` / `from` / `to` / `source_text` / 字符数
- 每条发送是否**恰好一次**计费
- 是否有 `trigger=manual_send` 的记录

对账脚本：`deploy/reconcile-send-translate.sql`（**只读**）。

```bash
psql -d hello_pix \
  -v username='你的账号' \
  -v since="'2026-10-07 18:00:00-04'" \
  -f deploy/reconcile-send-translate.sql
```

各节读法：

| 节 | 看什么 | 通过条件 |
|---|---|---|
| 1 | 明细 | `trigger` 是 `manual_send`（发送）或 `auto_receive`（群聊接收） |
| 2 | 按 trigger 汇总 | `manual_send` 条数 == 你实际发送的消息数 |
| 3 | 重复计费 | **0 行** |
| 4 | 字符扣减 | `判定` 列全是 ✅ 相符 |
| **4b** | **历史多扣** | 只该出现**旧版**（≤0.1.11）产生的行；见下 |
| 5 | 群聊自动 | 「群组翻译=手动」的实例上必须 0 条 |

**§4b 是这次新增的**，用来把「旧版把时间戳一起计费」的历史多扣逐条算清楚：

- 账单里出现过 `Sweet dreams18:53` —— 用户只输了 12 个字符，却被扣了 17 个
  （尾部 `18:53` 是 WhatsApp 的气泡时间，0.1.14 之前它跟着正文一起被翻译并计费）。
- 脚本会用 `应退字符` 给出每条的**多扣字符数**，并区分两类：
  - `时钟污染（可自动核定）` → `应退字符` 可直接用于退款；
  - `含 UI 文案（需人工核定）` → 服务端还原不出纯正文，`应退字符` 为 NULL，
    **不是 0**，需要人工核定后再补。
- 还有一列 `版本判定`：以 `trigger` 为准（0.1.14 起才写 `trigger`）。
  - `旧版（预期）` → 旧版本产生的，出现是**符合预期**的；
  - `❌ 本版回归` → 0.1.14 已写了 `trigger` 却仍然污染 = 修复回归，
    **必须把输出发我，不要直接退款了事**。
- ⚠️ **已知误报**：正文本身就以时间结尾的正常消息（例如
  `let us meet at 18:53`）也会被算成时钟污染，每行只差几字符。
  如果样例里大量出现这种句尾时间，先人工核对再退款。

## 3. 验收项

> **判定口径统一为：对方（或另一个自己的号）到底收到了什么、收到了几条。**
> 界面上写着"已翻译"不算通过 —— 这次的事故恰恰就是"界面一切正常，原文已经发出去"。

### 3.0 前置：先确认装的是 0.1.14

```bash
bash rc014-collect.sh before
```

确认输出里 **`已安装版本 = 0.1.14`**，并且日志里能看到 `[preload] 实例 … 翻译桥已就绪`。

⚠️ **如果日志里出现"翻译桥未启动"或"装载失败" —— 停下，不要再往下验，直接回传文件。**

### 3.1 安装、启动、登录

- [ ] 安装包能装、能启动、能登录
- [ ] 打开 WhatsApp 实例，能正常加载
- [ ] 日志里出现 `[preload] 实例 whatsapp-pro-1 翻译桥已就绪`

### 3.2 ★核心★ 中文 → 英语：对方只收到 1 条英文

设置：发送翻译**开**，输入语言 = **自动识别**，输出语言 = **英语**，通道 = **GPT**。

1. 在 WhatsApp 输入中文：`今天下午三点开会`
2. **按 Enter 发送**

- [ ] 对方**只收到一条**英文（例如 `Let's meet at 3 PM today`）
- [ ] 对方**没有收到任何中文**
- [ ] 自己没有看到"发了两条"
- [ ] `rc014-collect.sh after-cn2en` 后，日志里有 `trigger=manual_send`

### 3.3 ★核心★ 英语 → 中文：对方只收到 1 条中文

设置：输出语言改成 **中文**。

1. 输入英文：`Let's meet at 3 PM today`
2. 按 Enter

- [ ] 对方**只收到一条**中文
- [ ] 没有多出英文原文那一条

### 3.4 ★核心★ 连续发送 5 条：每条只发一次译文

连发 5 条不同内容的中文，不要等上一条翻完。

- [ ] 对方收到 **5 条**，每条都是英文
- [ ] **没有**任何一条是中文
- [ ] 没有重复（不是 6~10 条）
- [ ] `translate_logs` 里 5 条 `manual_send`，字符数合计 = 5 条之和（不多不少）

### 3.5 ★核心★ API 慢 5 秒：5 秒内对方收不到中文原文

把通道切到一个明显偏慢的线路（或让运维临时加 5 秒延迟），输入中文后按 Enter。

- [ ] **5 秒内**对方**什么都没收到**（不是"先收到中文、5 秒后又收到英文"）
- [ ] 5 秒后只收到译文
- [ ] 这 5 秒里输入框显示的是翻译中状态，**再按一次 Enter 也不会多出一条**

> 这条是"原生发送抢跑"的直接检验：如果拦截失效，原文会**立刻**出去，
> 而不是等译文回来。原报告 §1 第 8 条讲的就是这类"抢跑"。

### 3.6 ★核心★ API 失败：对方什么都收不到

断网 / 把通道切成一个不可用的，然后输入中文按 Enter。

- [ ] 对方**什么都没收到**（这一条最容易失败，务必确认）
- [ ] 界面弹提示：**「翻译失败，消息尚未发送」**
- [ ] 提示里有 **「重试翻译」** 和 **「发送原文」** 两个按钮
- [ ] 原文**还在输入框里**（没丢）
- [ ] **不点任何按钮，等待 60 秒** → 对方依然什么都没收到

### 3.7 ★核心★ 余额不足：什么都收不到，并明确提示

用一个字符余额为 0 的子账号。

- [ ] 对方**什么都没收到**
- [ ] 提示里明确是**余额不足**（不是"翻译失败"这种笼统话）
- [ ] 明确告知"请联系主账号分配字符"

### 3.8 ★核心★ 「发送原文」必须由用户再次明确点击

承接 3.6。

- [ ] 点「**重试翻译**」→ 再翻一次；成功才发（若仍失败，依然一个字节都不发）
- [ ] 点「**发送原文**」→ **这时才**发未翻译的原文，且**只发一条**
- [ ] 点提示框里的按钮**不会**被误当成"点了发送"（不会自噬触发一轮翻译）

### 3.9 Enter 与发送按钮结果一致

把 3.2 用**点发送按钮**再做一遍。

- [ ] 结果与按 Enter **完全一致**（只收到 1 条译文）

### 3.10 群聊与私聊结果一致

- [ ] 群聊里发中文 → 群成员只收到 1 条英文
- [ ] 私聊里发中文 → 同上
- [ ] 两者在日志里都是 `trigger=manual_send`

### 3.11 Shift+Enter 换行：不能被误拦

- [ ] 输入中文后按 **Shift+Enter** → **只换行，不发送、不翻译**
- [ ] 之后按 Enter → 正常翻译并发送（只有一条）

### 3.12 中文输入法 composition 状态

用拼音输入法，在**候选词还没上屏**时按 Enter（选词）。

- [ ] 这一下 Enter **只用于选词**，不发送、不翻译
- [ ] 上屏后再按一次 Enter → 正常翻译并发送

### 3.13 翻译日志必须标且只标 manual_send

```bash
bash rc014-collect.sh after-log-check
```

- [ ] 服务端 `translate_logs.trigger` 里能查到 `manual_send`
- [ ] 每条发送**恰好一条** `manual_send` 记录（不重不漏）

### 3.14 每次成功只扣一次字符

- [ ] 每条消息的字符数扣减 = 该条**原文**长度（不是译文的、也不是两倍）
- [ ] 连发 5 条 = 扣 5 条

### 3.15 崩溃兜底（本版新增，建议抽验）

如果方便，在实例里手动制造一次异常（例如先用一个奇怪的超长/特殊字符内容），
观察界面是否给出提示而不是"静默什么都没发生"。

- [ ] 异常时**对方什么都没收到**
- [ ] 界面有提示，原文退回输入框

### 3.16 群聊接收自动翻译回归（别被本版改坏）

- [ ] 群消息按账号级设置正常自动翻译
- [ ] 只翻**真正需要翻**的消息，不刷屏
- [ ] 每条群消息**只扣一次**字符

### 3.17 Telegram 回归（别被本版改坏）

- [ ] Telegram 实例能正常打开、发送翻译正常
- [ ] 日志同样是 `trigger=manual_send`

### 3.18 桥健康提示（本版新增）

正常装好的客户端**不应该**看到任何红色提示条。

- [ ] 侧边栏每个 WhatsApp 窗口都**没有** ⚠ 标记
- [ ] guest 页面顶部**没有**红色横幅

> 如果看到了红色横幅或 ⚠，说明预加载脚本没装起来 —— 请立刻回传
> `rc014-collect.sh` 的输出，日志里会有具体原因。
