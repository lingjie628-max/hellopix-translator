# Hello Pix 0.1.32 真机复测手册

> **本版的重点是「开满不闪退」。** 请在**报障那台机器**上走完第 1～3 步。

---

## 0. 装之前先记一笔（很重要）

先在**出问题的那台机器**上打开**旧版** Hello Pix，反复开 / 关实例十几轮，
然后主界面 → 设置 → 「客户端日志」导出（或跑 `rc030-collect.sh`）。

> 为什么要这样：旧版在这个场景下会**闪退**，而闪退往往来不及写日志。
> 先把日志捞出来，能帮我们确认"崩之前最后发生了什么"。
>
> 另外记一下：**旧版你能开到第几个才崩？**（用户报的是 18 个左右）
> 这个数字对判断很有用 —— 它是你机器上句柄上限的直接体现。

---

## 1. 【核心】窗口不再"黑屏不说原因"

**准备**：把某个实例的代理改成一个**坏节点**（或直接拔网线）。
**步骤**：打开那个实例。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 表现 | 显示错误页：标题 + 建议 + **重新加载**按钮 | 一片深色空白，什么都不说 |
| 标题 | 「连接超时」「代理连不上」这类**具体原因** | 只说"打不开" |
| 建议 | 明确告诉你该做什么（查网络 / 查代理设置） | 只有一句"打不开" |
| 点击「重新加载」 | 真的重新加载 | 点了没反应 |
| 日志 | `load` 一行 warn，含错误码 | 无记录 |

> 这一版的核心：**把"网络问题"和"软件问题"区分开**。以前两者看起来一样（都是黑屏），
> 用户只能来问客服。

---

## 2. 【核心】「翻译桥未启动」不再误报

**准备**：一次开 **20 个以上**实例（越多越能复现旧版的误报）。
**步骤**：观察侧边栏和日志。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 20+ 实例时侧边栏 | **不再**大面积出现 ⚠ | 一大片 ⚠（那是旧版行为） |
| 日志级别 | 有 `DEBUG` 级"…继续观察" | 满屏 `ERROR`「未启动」 |
| 单个实例真的坏掉时 | 90 秒后**仍会**告警 | 完全不告警（那是漏报，也不行） |

> ⚠️ 注意：这版是**降低误报**，不是**取消告警**。真坏的实例仍必须报出来 ——
> 所以第 3 条也要测，否则可能是"改过头了"。

---

## 3. 窗口上限仍是内存水位（继承 0.1.31）

1. 开一堆实例 + 再开几个吃内存的程序，把内存推到 90% 以上。
2. 点「+」。

| 观察点 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 表现 | 弹原生提示框，标题「**运行内存不足**」 | 闪退 / 卡死 |
| 关掉一些后 | 又能继续开 | 仍被拒 |

## 4. 回归项（确认没改坏）

| 项 | 怎么测 | 期望 |
|---|---|---|
| 发送翻译 | WhatsApp 里发中文 | 译文发出 |
| 接收翻译 | 收到英文 / 对方中文 | 能译 |
| **节点检测**（0.1.29） | 填一个坏 SOCKS5 节点，点检测 | **8 秒内**返回明确错误，不转圈 |
| **新实例翻译桥**（0.1.29） | 承接上一步再开新实例 | **没有**「翻译组件未启动」横幅 |
| 译文可复制（0.1.27） | 选中译文 → Ctrl+C → 粘贴 | 能复制 |
| 图文一起发（0.1.28） | 先打字 → 加图 → 发 | 文字**也**翻译 |
| 带账密 SOCKS5（0.1.29） | 填正常带账密节点 | 检测**成功** |
| 多实例隔离 | 开 2 个不同平台实例 | 各自独立、登录态互不干扰 |

---

## 5. 收集日志发回

在**出问题的那台机器**上跑：

```bash
# Windows 用 Git Bash / WSL
bash rc030-collect.sh
```

或手动：主界面 → 设置 → 客户端日志 → 导出。连同以下信息一起发：

1. Windows / macOS 版本（Windows 跑 `winver`）
2. **旧版能开到第几个才崩**（第 0 步记下的数字）
3. 新版开到第几个开始提示
4. 复测时**卡在第几步**、屏幕上是什么
5. 特别要「**崩/提示那一瞬间**」附近的日志时间段

| 验收 | 结果 |
|---|---|
| `node --test test/tab-budget.test.js` | **23 / 23 通过** |

| 全量 `node --test test/*.test.js` | **1209 项 / 1195 通过 / 0 失败** |

真 Electron 实测的关键记录：

| 断言 | 实测值 |
|---|---|
| 每个实例消耗的句柄数 | **19.2 个**（预算按 26 算） |
| 20 个实例累计句柄 | 39 → **520** |
| 连续 30 次"拒绝"判断消耗的句柄 | **0**（87 → 87） |
| 拒绝之后能否正常建窗口 | **能** |
| 反复开关 30 次的永久泄漏 | 242 个句柄（≈8.1/次，Electron 33 原生行为） |

> 最后一条说明了为什么必须有**显式的窗口数上限**：
> 光看句柄水位会因历史泄漏而误判，而数字上限是确定的、可解释的。
