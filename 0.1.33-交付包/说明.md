# Hello Pix 0.1.33 交付说明

## 本轮改了什么

三处改动，全部围绕「节点」——起因是一次真机反馈：用户填入节点后一直提示「节点连不上」。

---

## 一、多目标并发预检（核心）

**改动文件**：`desktop/socks-relay.js`

### 改之前

预检只 CONNECT 一个固定目标 `api.ipify.org:443`，失败即判「节点连不上」。

### 问题

真机上抓到的节点，对不同目标返回**不同的** SOCKS5 应答码：

```
1.1.1.1:443      → 0x01  (通用故障)
8.8.8.8:53       → 0x08  (地址类型不支持)
api.ipify.org    → 0x08
```

只测一个目标，等于把「节点好坏」的判定权交给一次偶然。

### 改之后

并发试探四个目标，**任一成功即判可用**：

```
web.whatsapp.com    ← 用户真正要打开的站点，排第一
api.ipify.org
www.google.com
www.cloudflare.com
```

全部走域名（远程 DNS），与用户实际访问方式一致。

### 附带解决的「干等」问题

全部失败时，如果已经失败的目标里**最快的那个**在 1 秒内就返回了（说明节点是秒拒的），
立即以失败定论，不再陪着可能假死的目标耗满 8 秒超时。

实测真实节点：**148ms** 就给出结论（改之前是 8 秒超时或误判）。

## 二、0x08 的文案改准确

**改动文件**：`desktop/socks-relay.js` → `describeConnectReply()`

| | 文案 |
|---|---|
| 旧 | 节点不支持该地址类型（**可能只支持 IPv4**），请更换节点 |
| 新 | 节点拒绝了连接（可能是流量用尽、套餐到期或 IP 白名单未加），**请联系代理服务商** |

**为什么改**：0.1.32 的真机数据反证了「只支持 IPv4」——同一节点对纯 IPv4 字面量
`1.1.1.1` 也拒绝。既然 IPv4 也不放行，就不是地址类型的问题。

0x01 也一并改成「请联系代理服务商」，因为同样属于账号侧的可能。

> 保留 0x02~0x07 原有的「请更换节点」—— 那几个是明确的网络侧问题。

## 三、同节点复用中继

**改动文件**：`desktop/main.js`

### 改之前

一窗口一中继。开 60 个窗口 = 向节点开 60 条独立 SOCKS5 连接。

### 为什么改

参照同类产品（比特浏览器）的实现：它用 `md5(host+port+user+pass)` 做 key，
同一节点复用同一个本地端口。商业代理**常常限制单账号并发连接数**，
60 条连接很可能触发限流，表现就是「开到一定数量后新窗口连不上」。

### 改之后

`relayPool` 按 key 池化，**引用计数**管理：

```
entry.refs += 1     // 每个窗口持一份租约
if (entry.refs > 0) return   // 还有人在用，不关
relayPool.delete(key)        // 最后一个窗口关掉才真正 close
```

**为什么必须引用计数**：`createSocksRelay().close()` 会销毁该中继上的**所有** socket。
如果两个窗口共用一个实例而不计数，关掉 A 会顺手掐掉 B 的连接。

**隔离性没有削弱**：key 仍然是 `host + port + user + pass` 四项，一字不差才共享。
不同账号/线路永远落在不同 key 上，不可能串凭据。

## 四、验证

### 自动化

```
node --test test/*.test.js
  ℹ tests 1220 / pass 1206 / fail 0 / skipped 14
```

新增 `test/socks-multi-target.test.js`（11 条），覆盖：

- 只有 `web.whatsapp.com` 通 → 必须判可用（**单目标时代的误杀**）
- 全部被拒 → 判失败且给出节点侧原因
- 任一目标假死不拖死整体
- 成功后掐掉仍在飞行的探测，不留悬挂连接
- `PRECHECK_TARGETS` 必须含 WhatsApp Web
- 0x08 文案不得再出现 `IPv4`
- `pickWorstOutcome` 的优先级（账号密码错 > 网络问题）
- `relayPool` 引用计数与退出清理（源码级护栏）

### 真机（用本次事故的节点）

```
节点 186.240.232.207  →  ok=false  CONNECT_REFUSED  148ms
   结论: 节点拒绝了连接（可能是流量用尽、套餐到期或 IP 白名单未加），请联系代理服务商

节点 186.240.232.206  →  ok=false  CONNECT_REFUSED  149ms
   结论: 同上
```

**结论正确**：该节点的认证是通的（账号密码没错），但 CONNECT 被拒 —— Chromium 直接加载
也是 0.3 秒失败（`ERR_SOCKS_CONNECTION_FAILED`）。所以判定无误，只是提示改得更准、更快。

## 六、没有做的事（明确说明）

1. **没有引入外部 Chromium 内核**。分析比特浏览器时确认它用
   `puppeteer-core` + 私有编译内核 + `--fingerprint-config`（防检测指纹）。
   我们只做单一站点，Electron 自带 Chromium 够用，引入外部内核会带来
   签名、公证、体积、更新链路的额外复杂度，**收益不匹配**。

2. **没有改用 `socks-proxy-agent` 做探测**。比特在 Node 层用该库直接请求网页
   判断代理是否可用（能拿到内容才算通）。我们的预检只验证到 CONNECT 成功，
   没有验证「能否真的取到内容」。这是一条**已知的差距**，但改成 HTTP 层探测
   会把纯 Node、不依赖第三方库的现有实现推翻，本轮先不动。
   如果后续仍有「判可用但实际打不开」的客诉，这就是下一步方向。
