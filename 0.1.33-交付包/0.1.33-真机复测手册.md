# Hello Pix 0.1.33 真机复测手册

> 本轮改动集中在**节点检测**。验收重点是：好节点不被误判、坏节点报错说清楚、多窗口更稳。

---

## 准备

准备三个节点（用户真实环境下的）：

| 代号 | 类型 | 用途 |
|---|---|---|
| **A** | 能正常用的节点 | 验证「好节点必须判可用」 |
| **B** | 已知坏掉的节点（如流量用尽的） | 验证「坏节点报错准确」 |
| **C** | 如果手上有慢节点（响应 2 秒以上） | 验证「慢节点不被提前判死」 |

---

## ① 好节点必须判可用（最重要）

1. 新增代理，填节点 **A** 的类型 / 主机 / 端口 / 账号 / 密码
2. 点「节点检测」

**通过标准**

- [ ] 显示检测成功，**拿到 IP**
- [ ] 耗时合理（好节点应当在 1~3 秒内出结果）
- [ ] **不能**出现「节点拒绝」「节点连不上」

> ⚠️ 这一条是本次改动的核心。如果 A 节点在旧版被判失败、新版通过，说明修改生效。
> 反之如果旧版能过、新版过不了 —— 立刻停止验收并反馈，那是回归。

---

## ② 坏节点必须快速、准确报错

1. 填节点 **B**
2. 点「节点检测」

**通过标准**

- [ ] 提示为「**节点拒绝了连接（可能是流量用尽、套餐到期或 IP 白名单未加），请联系代理服务商**」
- [ ] **1~2 秒内**出结果（不允许停在「正在检测」超过 3 秒）
- [ ] 提示里**不能**出现「只支持 IPv4」
- [ ] 提示里**不能**出现 `reply=8` 这类原始数字

---

## ③ 慢节点不被提前判死（有节点 C 才做）

1. 填节点 **C**
2. 点「节点检测」

**通过标准**

- [ ] 如果 C 实际可用，必须判成功（不能因为慢就判失败）
- [ ] 最坏情况下，等待时间不超过约 8 秒

---

## ④ 多窗口共用中继（核心场景）

**前置**：用节点 A，同一个账号

1. 连续打开 **20 个** WhatsApp 窗口
2. 每个窗口检查是否能正常加载、正常翻译

**通过标准**

- [ ] 20 个窗口都能打开，没有「节点连不上」
- [ ] 中途关掉其中 5 个，**剩下的 15 个仍能正常收发和翻译**
      （这条专门验证引用计数：关窗口不能掐断其他窗口的连接）
- [ ] 全部关掉后重新开 3 个，仍能正常用

**日志里应当只看到一个中继端口**：

```bash
# macOS
lsof -nP -iTCP -sTCP:LISTEN | grep -E "node|Hello Pix" | head -20

# Windows（PowerShell）
netstat -ano | Select-String "LISTENING" | Select-String "127.0.0.1"
```

同一个节点下，**不应**出现 20 个不同的本地端口。

---

## ⑤ 改节点即时生效（护栏）

1. 窗口正在用节点 A，正常工作
2. 打开该窗口的代理设置，改成节点 B
3. 保存

**通过标准**

- [ ] 提示节点不可用（B 是坏的）
- [ ] 改回 A 后能恢复
- [ ] 过程中**其他窗口不受影响**

---

## ⑥ 退出清理（护栏）

1. 开 5 个窗口，用节点 A
2. 从托盘图标彻底退出

**通过标准**

- [ ] 进程完全退出，无残留
- [ ] 端口全部释放（`lsof` / `netstat` 里查不到遗留监听）

---

## 采集脚本

```bash
bash rc033-collect.sh before
# 做 ① ~ ⑥ 各一步
bash rc033-collect.sh after-<步骤名>
```

采集内容：版本、系统、网络出口、本地监听端口、日志尾部。

---

## 出问题时要带的东西

1. 「系统操作 → 打开日志目录」里的 **`hello-pix-<日期>.log`**
2. 出问题时填的**代理类型**（socks5 / http / ssh）
3. 是哪个节点（**主机地址可以打码，但要说明是「好节点」还是「坏节点」**）
4. 截图（特别是节点检测的结果区域）
